# Plugins: packaged extensions

A plugin is a packaged, optional extension for a workspace. Modules are the mechanism (the authoring contract lives in `docs/modules.md`); a plugin is the packaged unit: the exact extension-root overlay a workspace installs, plus the material that explains and tests it. The core stays zero-dependency: a plugin declares its own needs and brings nothing the base must install.

## Anatomy

```text
plugins/<name>/
  manifest               the package declaration: summary, version, kind, parts; a driver package adds its driver name, plus optional catalog metadata
  hooks/                 optional non-interactive package-level lifecycle scripts: probe, install, uninstall (a driver part carries its own driver hooks, prepare, finish, cleanup, inside its folder)
  .contexture/
    extensions/          the overlay: the extension-root tree the package installs
      modules/<name>/    a standard module folder: manifest, laws, data, config, part hooks, verbs, hooks, filters, and its private assets
      storage/drivers/<name>/  a storage driver (the driver kind, with optional config schema)
      rhythms/           rhythm files
  README.md              plugin-meta: adoption, the plugin's needs, contribution
  tests/                 plugin-meta: the plugin's own vitest project, never installed
  AGENTS.workspace.md    root overlay fragments: reference material, never installed
```

The plugin root mirrors the extension root: `.contexture/extensions/` installs at the same relative path it has here. Every other path is package meta or reference material: the manifest, the README, the tests, reference copies (docs-discipline's `docs/work.md`), and the root overlay fragments are never copied, and a package carries no root installer script of its own, since `ctx package install` and `ctx package uninstall` take its catalog name or its root; optional package-level lifecycle scripts live under `hooks/` (`hooks/probe`, `hooks/install`, `hooks/uninstall`) and run strictly non-interactively with stdin from `/dev/null` (see Adopt), and a driver part may carry its own driver hooks (`storage/drivers/<name>/hooks/prepare`, `finish`, `cleanup`), which the move of the record runs (docs/the-engine.md, Moving a record between backends). The root fragments' laws belong in the module's `laws` file, which the compose reads. A module's part hook may apply a package-root file at install (read through `$CTX_PACKAGE_ROOT`), which then counts as payload; no catalog plugin ships one: the docs discipline's rules ride its module's laws and rhythms, never a seeded corpus doc.

## Naming

A plugin's name says what it offers, and adopters address it as "the <name> plugin". The directory name is the plugin's name; when a plugin teaches ctx verbs, its module carries the same name (`toolchain-filters`), so the help entry and the plugin directory read the same.

## Kinds and parts

Every package carries the package manifest `manifest` at its root: required `# summary:`, `# version:`, `# kind: feature|driver`, one `# part: <type> <path>` per part, and, for a driver package, `# driver: <name>`, plus optional descriptive metadata (`# category:`, `# pitch:`, `# when:`, `# needs:`, `# tags:`, and a trailing `# description:` block last in the file). The parts are `module`, `driver`, `laws`, `rhythms`, `hooks`, and `filters`; each path is relative to the package's `.contexture/extensions/` tree (the install path). The installer overlays only the declared parts and refuses a payload file outside them; the module file stays the manifest for a module part. A `templates` part is not a type: an internal asset rides in its module (see The interface rule).

The two kinds:

- A **feature package** carries no driver. It may bring any non-driver parts, including none of the module kind: `toolchain-filters` is filters-only, `starter-rhythms` rhythms-only, `git` a module with its laws and no verbs, and a law-fragment-only package is the same shape. A feature package with a module is a module package; a feature package with no module file is module-less.
- A **storage-driver package** declares and installs its driver: exactly one `driver` part at `storage/drivers/<name>` and a `# driver: <name>` line. The driver package carries no module part (the manifest reader refuses one, since its install and uninstall move the record) and ships no module file, so the engine never lists the driver as a module; its package name may differ from the driver name: `storage-sqlite` declares `sqlite`. A driver package also declares its storage format version, `# format: <positive whole number>` (`storage-sqlite` declares `6`, its database's schema version): the shape of the data the driver stores, which a change of format moves through posix rather than through upgrade code in the driver. A driver may include an optional `config` schema file inside `storage/drivers/<name>/` (covered by the `driver` part), whose keys merge into the `storage` schema namespace (`ctx store config` and `ctx config`). Installing a driver package moves the record from posix into its driver and switches `storage.driver` to it, and uninstalling it moves the record back into posix, the old copy backed up or deleted as the human answers (`--backup-old` or `--delete-old`) and the driver's settings given at install as `--driver-config=<key>=<value>` (docs/the-engine.md, Moving a record between backends); `storage.driver: sqlite` resolves the installed driver through the extension tier. A driver reaches a workspace only as a driver package: the resolver finds the core posix driver and the installed driver packages' drivers alone, so a workspace's own driver ships as a driver package and installs from its package root path, and `storage.driver` and the driver's settings belong to the install and uninstall (`ctx store config` refuses a hand switch of the driver, and a change of a driver setting while its driver holds data). Its driver part may carry the driver hooks `prepare` (refusing a storage that already holds anything), `finish` (backing up or deleting its own storage after a move out), and `cleanup` (removing what a failed move made). A driver is held to posix by the storage core's differential behavior test, run in two scratch workspaces with the driver as one workspace's configured driver (`docs/the-engine.md`, The behavior test a driver meets); the installer runs it on an incoming driver part after the package files land and before the driver's prepare hook, so a driver author tests a driver by installing its package into a throwaway workspace. To be testable, and so installable, the driver meets the isolation requirement: run from a scratch workspace root as that workspace's configured driver with only the cleared environment the test passes, it keeps every byte it writes under that root (a file or database driver at its default place in the workspace's drawer); a driver that cannot is out of scope.

The three version lines are distinct: the package version (the manifest; install, upgrade, the generated law hash), the driver descriptor version (the driver's `capability`, `4.0.0` at contract 4, never checked), and the storage contract (`4` today): the store-only card that describes posix exactly, with the record's rules in the unit module over the storage layer. A `# requires:` line is reserved and refused, as in the module file.

The package version moves with the payload: a release that changes a plugin's payload, its installed `.contexture` tree, its `hooks/` lifecycle scripts, and any package-root file a part hook applies at install (no catalog plugin carries one today), bumps that plugin's manifest version by the version rule in the workspace overlay's `@git` section the git package contributes (PATCH for fixes and wording, MINOR for a feature, a MAJOR only on the human's call), and a single-module package moves its module file's `# version:` with it (docs-discipline's `docs` module and git's `git` module; a module file that carries no version line, as ast-doc-graph's, is exempt). The README, the tests, and the manifest itself are package meta: a change there alone bumps nothing. The bump rides the first payload change of a release cycle, since the governance `plugin-versions` check (see The test convention) reads red at once; nothing in the installer compares versions, so the version is how an adopter sees that a newer payload waits in the catalog (`docs/adoption.md`, Updating, whose step 8 also deletes the catalog paths a release removed, since package meta moves no version).

### The interface rule

The ctx interface is the only user/agent-facing surface: a package's verbs, its module summaries, and the help they declare (the header lines, which the engine renders for `ctx <module> help <verb>` and for a sole `--help` or `-h` after the verb, a declared subcommand's `# subcommand:` section rendered for `ctx <module> help <verb> <sub>` and a sole `--help` or `-h` after the subcommand, plus a verb's computed help through `# help-from: code`, so a packaged verb carries no help handler of its own). Anything a package does not serve through that interface stays module-private inside the module folder, a private script or a private asset without a `# summary:` line (the docs module's corpus grammar is the worked case: `scripts/doc.grammar`). Agents address the interface, never a file path. No standard shared folder exists for such assets: a module that needs one carries it in its own folder, so the extension root has no `templates/` part, no package declares one, and an internal asset is never shipped into a shared drawer location. The overlay ships only the extension-root tree; package meta and reference material (README, tests, manifest, reference copies, the root overlay fragments) are never copied.

## Adopt

1. Inspect the catalog read-only with `.contexture/ctx package catalog` (or `--names`, `--no-probe`, `--json`) and `.contexture/ctx package info <name>` to see each package's pitch, needs, install status, and live host readiness probe (`0` ready, `1` unmet, `3` partial, other error; an absent `hooks/probe` defaults to ready), and read the plugin's `README.md` whole: it carries the adoption flow, the plugin's needs, and the verification walk.
2. Ensure the base is adopted; its engine answers `ctx package install`, `ctx package uninstall`, `ctx package list`, `ctx package catalog`, and `ctx package info`.
3. On the human's explicit go at the act, install the package: `.contexture/ctx package install <name>`, resolving `.contexture/plugins/<name>` first and falling back to `./plugins/<name>`, or naming a package root path (a value holding a slash, read from the working folder). The verb checks no go, so the gate stays the human's, and the package always lands in the workspace whose engine runs it. The install reads the package `manifest` (summary, version, kind, parts, and the driver name and storage format for a driver package), overlays only the declared parts under `.contexture/extensions/`, records every installed path and its mode under `.contexture/extensions/.state/<name>.files` (with the law fragments the compose reads) while stashing optional `hooks/uninstall` at `.contexture/extensions/.state/<name>.uninstall` atomically, refuses the collision classes and a payload path outside the declared parts, runs the installed module folders' `install` part hooks after the record, and then runs optional package-level `hooks/install` (strictly non-interactive with stdin from `/dev/null`). The installer then recomposes the generated law layer through `ctx compose`, since every package version and law fragment feeds its sources hash; a compose refusal surfaces loudly, never as a stale layer. A re-install of the recorded files is an update.
4. Nothing applies by hand: the part hooks and package hooks apply what a package seeds, and the root overlay fragments' laws live in the module's `laws` file; docs-discipline writes no corpus doc at install, since its rules ride the module's laws and rhythms, and its `install` hook is a temporary guard of the one time corpus root move: under posix, while the corpus is empty and a corpus doc still sits at the old `docs/<repo>/` place, it refuses rc 1 naming those repos, so the installer stops rc 2 with the overlay and its record in place until the human moves them (`docs/adoption.md`, Updating).
5. Declare the plugin's needs: install nothing the README does not name; a plugin's dependencies are its own, never the core's.
6. Run the README's verification walk before any real work depends on the plugin.

The plugin's `tests/` folder never lands in a workspace: tests live with the plugin, at the plugin root. The install writes the package's `package.<name>: <source>` line into the workspace configuration (every alias `--as=<module>=<alias>` gave rides on it), a bare `.contexture/ctx package install` installs every declared package not yet installed but the driver packages, each left out with one line naming it since its install moves the record (a driver package installs only by name, `.contexture/ctx package install <name>`), and `.contexture/ctx package list` shows the declared against the installed, read only. A driver package's install moves the record from posix into its driver and its uninstall moves it back: the old copy answer is the human's too, given ahead as `--backup-old` or `--delete-old` or asked at a terminal, a run with no terminal refusing naming both flags while the old copy holds a record, so the agent relays it; a reinstall at the same storage format updates the files only when every namespace reads the same through the new version, and at another format moves the record out through posix and back in. Uninstall with `.contexture/ctx package uninstall <name> [--keep-data|--delete-data] [--backup-old|--delete-old]`, on the same go: when a module of the package declares data and holds a key, the keep or delete answer is the human's, given ahead by the flag or asked at a terminal, and a run with no terminal refuses naming each namespace with its key count and both flags, writing nothing, so the agent relays the question; then it runs the stashed `.contexture/extensions/.state/<name>.uninstall` hook first (so uninstall still runs cleanly even when the catalog folder is absent), then the module `uninstall` part hooks in ascending installed name order, keeps each data carrying module's declaration (so its data stays reachable and returns when the same package installs again) or deletes every key it holds, removes the unchanged recorded files, preserves and reports a file changed after install, removes the record and stashed hook, recomposes the generated law layer, and prints one line per namespace kept or deleted. `.contexture/ctx package list` names each kept namespace, and `.contexture/ctx package uninstall <name> --delete-data` deletes the kept data of a package no longer installed.

A plugin installs into an existing setup the same way: the extension-root overlay installs into any adopted workspace, whenever it wants it.

## The test convention

- A plugin's tests live at `plugins/<name>/tests/` as the plugin's own vitest project, rooted at the plugin and importing the shared harness helpers as `@support` (`tests/vitest.config.mts` declares a project by convention for every `plugins/<name>/tests/` that holds a test file, so a new plugin's tests run with no config edit; `bun run test:<name>` from `tests/` runs it, a script the governance `projects` check requires). They are plugin-meta like the README: never copied, never shipped into a workspace.
- A test exercises the plugin's own copy, resolved from the repository (`plugins/<name>/.contexture/...`) and staged into a sandbox beside the shipped base, never the workspace's adopted copy in the live drawer: the two drift, and a test pinned to the adopted copy passes on whatever was installed last. The harness stages the storage-sqlite driver copy into every sqlite sandbox, so the shared store contract tests of the `drivers` project hold that copy.
- A test with a declared need (sqlite3 3.44 or later for the sqlite driver, sqlite3 with FTS5 for the ast-doc-graph index, a TypeScript compiler API) skips when the need is absent, naming it, except in the pre-release set (`bun run test:prerelease`), where a missing sqlite3 3.44 or later with FTS5 fails the run, since a skipped case proves nothing.
- The upstream ship gate includes the plugin tests: `bun run test:prerelease` from `tests/` (the release gate) and `bun run test` (every default project during the work) run every project, the plugin projects among them; a red plugin test holds the ship breath. The tests run concurrently, so each stages its scratch in a fresh sandbox under the run root (`.contexture/tmp/vitest-*`, removed when the run ends), never a fixed name, and reads nothing from its stdin. The docs-discipline project tests its logic once, on posix, and keeps the store driver cases on sqlite (`store/`: the corpus round trip, the parity with posix, and the gate on git's delta, where a corpus the store holds reads untracked); the unit and lane verbs run once, on posix, in the vitest `unit-verbs` project, since a storage driver holds no record logic.
- The vitest `packages` project (`tests/packages`, `bun run test:packages` from `tests/`) holds the package manifest cases: the two kinds and the six package shapes, the parts coverage, the package and driver versions, the refused `requires`, the driver not listed as a module, and the extension-root reads (the rhythm list, the law-fragment record, the store-data owner scan, and the docs store under the extension root), and it runs the worked example's own test (`tests/fixtures/worked-package/tests/notes.test.ts`).
- The governance `plugin-versions` check (`tests/governance/plugin-versions.test.ts`) holds the version rule over the index, the payload the ship breath stages first: against the nearest release tag, a plugin whose version is unchanged reads red, naming the plugin, the tag that first shipped that version, and the changed paths, when its payload (`plugins/<name>/.contexture/**`, `plugins/<name>/hooks/**`, plus every literal `$CTX_PACKAGE_ROOT/<path>` its payload or hook scripts read, since the installer exports the package root to both package and module hooks and every script a hook runs inherits it) differs from that tag; a changed version must be a greater x.y.z. It runs in every governance run, and a plugin manifest or payload change selects the governance project under `bun run test:changed`. A shallow clone or a repository with no reachable release tag skips it naming the need, except in the pre-release set, where that need fails the run. The same file holds the single-module lockstep over the working tree: every catalog package whose manifest declares exactly one `module` part, and whose module file carries a `# version:` line, holds that version equal to its manifest's, both read as the installer reads them (blanks trimmed); a module file without a version line is exempt, and a planted mismatch reads red.
- No catalog package passes silently without tests: the governance `projects` check requires every `plugins/<name>/` to have its own project or a named no-suite reason; `starter-rhythms` (a rhythms payload with no code, its install and its rhythms in `ctx rhythm list` proven by the `packages` project) and `git` (a law and preamble package with no code, its install, its compose after `@update`, and its uninstall proven by the packages and laws projects) are the two today.
- The worked example package (`tests/fixtures/worked-package/`, linked from `docs/modules.md`) is the authoring reference for a feature package: its test stages the shipped base, installs it in a sandbox, and proves the module, the laws, the data declaration, the install part hook, the notes verbs, and the uninstall keeping the notes and the re-install bringing them back. It is upstream test material, never a catalog entry.
- A plugin change is not done until its tests pass; the plugin's README carries the roots and the maintenance contract, and the harness contract lives in `tests/README.md`.

## Contribute

Upstream contribution and workspace extension are the same story. Build the mechanism as a module per `docs/modules.md`, package it as a plugin (the mirror tree, the README, the tests), and name it for what it offers. A workspace-local plugin stays workspace-owned; an upstream plugin lands under `plugins/` and rides the tag as the tracked catalog, installed into a workspace when wanted and never removed at adoption close.

## The shipped plugins

- `starter-rhythms`: a feature package, rhythms only (`part: rhythms rhythms`); the work and debug rhythms to start from.
- `toolchain-filters`: a feature package, filters only (`part: filters modules/toolchain-filters/filters`); test runner and compiler filters, discovered by `ctx run`.
- `lane-isolation`: retired with its subagent clauses in the lane module's laws and its git clauses in the git package (the lane module is a base workspace modules root module, beside the rhythm module); the folder is removed from the catalog and it carried no package manifest.
- `docs-discipline`: a feature package with a module part (its laws, its private corpus grammar, and its two handler files on the unit's task-landing and load-end points inside the module) and rhythms (the `docs` module: the read verbs `ctx docs query|get|search|audit|check|gate|nudge` and the write verbs `ctx docs new|write|header|rule|pitfall|entry|section|replace|remove|ids`); every verb reaches the corpus through the configured storage driver and prints the logical address `docs/<repo>/<slug>.md`, and each write is checked against the grammar before it is stored. The [module README](plugins/docs-discipline/.contexture/extensions/modules/docs/README.md) carries the corpus contract and the [plugin README](plugins/docs-discipline/README.md) carries adoption.
- `ast-doc-graph`: a feature package with a module part (`part: module modules/ast-doc-graph`); an AST symbol graph linked with centralized documentation.
- `storage-sqlite`: a storage-driver package (`kind: driver`, `driver: sqlite`, `format: 6`, `part: driver storage/drivers/sqlite`): the SQLite storage driver, a twin of the posix driver holding the record and the module data in one database at contract 4, keys and values in one table at schema 6, answering `exact` alone as posix does; it answers the store contract natively, ships no module file (so the engine never lists it as a module), carries no verb of its own, needs sqlite3 3.44 or later, and its install moves the record and the corpus into it from posix (its uninstall moving them back), its `prepare`, `finish`, and `cleanup` hooks keeping the database. The [plugin README](plugins/storage-sqlite/README.md) carries adoption and needs; the [driver README](plugins/storage-sqlite/.contexture/extensions/storage/drivers/sqlite/README.md) carries the schema, the SQL layout, and the store cases.
- `git`: a feature package with a module part (`part: module modules/git`) and no verbs: its laws create the `@git` section after `@update` (the gitignore strategy, the branch and worktree on demand, the push, merge, and cleanup mechanics) and append the boot ground clause for a repository; the core names no git; the docs-discipline module's git dependency is its own fact.
