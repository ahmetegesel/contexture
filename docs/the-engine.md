# The engine

## What the engine is

The engine is the part of contexture that runs and checks: the instruction files, the grammars, and the scripts. It is plain files and plain awk all the way down: no service, no database, no runtime.

The division of labor is deliberate. The model does the work; the machinery holds the line. A record kept by memory drifts, so the parts that must not drift are mechanical instead: the shapes are pinned in files, the searches are plain shell tools, and the checks are small scripts that run at fixed points. Quality comes from the machinery, not from the model remembering.

## The instruction files: the loader every turn

A coding harness reads its repository instruction file before it acts. In a contexture workspace `AGENTS.md` is the loader: the only file guaranteed to be in front of the agent every turn, and deliberately a few lines. Its first instruction runs `.contexture/ctx compose` (which composes or verifies the generated layer), then loads `AGENTS.generated.md` whole from the workspace root, then chains `AGENTS.workspace.md` and `AGENTS.local.md`. The second instruction frames the layer it loads: its generic sections are `@laws`, `@layout`, `@module`, `@boot`, `@interact`, `@rhythms`, `@subagents`, `@refresh`, `@close`, `@handoff`, `@git`, and `@update`; every module adds its own sections, clauses, and duties, so the layer carries more than that list, and each duty is followed as steps in its framed order, gates included; the laws bind. An absent engine or a refused compose is a broken payload: the instruction stops and reports the compose's error line, which names the missing or refused path, never booting on a stale or partial layer.

The four delivery files split by ownership. `AGENTS.md` is the base loader; the generated layer is the composed law set, the core law source plus the installed modules' preambles and clauses; the workspace overlay is the shared, tracked amendment; the local file is the personal amendment. The loader is the every-turn cost, about a kilobyte; the generated layer and the overlays are boot reads. The generated layer is gitignored and built at install and boot, never edited. Measured at the v0.61.1 base: the three-file stack it replaces is 34,994 bytes every turn; the loader is 856 bytes, and the boot whole (the generated layer plus both overlays) measured 36,693 bytes with the docs module installed.

The sections below are the blocks the generated layer carries, in the order the core law source fixes:

| section | what it carries |
|---|---|
| `@laws` | the slug-addressed laws |
| `@layout` | where every file lives and what it is for |
| `@boot` | the sequence that starts every working period |
| `@record` | the artifact map: what each artifact records and why |
| `@journal` | the event workflow: formation, substance, liveness, markings |
| `@backlog` | the task workflow |
| `@query` | how the agent decides what to load |
| `@interact` | how the agent treats the human |
| `@rhythms` | the rhythm contract and the default design loop |
| `@subagents` | the dispatch contract |
| `@refresh` | the artifact sweep |
| `@close` | period end and unit close |
| `@handoff` | the proof before context death |
| `@git` | the gitignore strategy for the workspace |
| `@update` | how the base evolves upstream |

The core law source fixes the block order; the installed modules' law fragments append under these keywords, and a new keyword creates a custom section after `@update`. The module preambles stand after `@layout`, before `@boot`.

### The laws

The laws are the spine of the whole system, loaded whole at boot in the generated layer. Each law reads `slug: statement`, and a reference addresses the slug, as in `@laws#verify-before-close`. Core laws include:

- `source-of-truth`: the record is the work's durable memory, what a fresh context resumes from: the events that happened, the decisions made, and the state they left, across compaction, tool change, and break; because the work's continuity depends on it, it holds whatever else that continuity needs, the reasons, the open threads, and the evidence behind them; the workspace and the commands' results show what is, and the loaded layer and its sequences say what to do.
- `load-only-needed`: load only what the work needs; closed units stay untouched unless the task calls for them.
- `compact-streams`: all shell commands execute through the ctx runner to preserve context window capacity.
- `writer-holds-volume`: the schema holds the shape, the writer holds the volume.
- `process-free`: process is free and human-chosen; govern the output, not the process.
- `compose-from-record`: compose from the record, never from the conversation.
- `verify-before-close`: no done without evidence, and never a claim of verification not performed.
- `harvest-the-human`: durable knowledge is surfaced by question, crystallized, and landed by the agent's judgement when it meets the bar, never just to record; a candidate that does not drops.
- `workspace-confinement`: the workspace is the boundary; the agent never roams outside it.
- `cli-doorway`: the CLI (`.contexture/ctx`) is the single doorway to the runtime and the record: contracts are discovered through `ctx help`, the record is reached strictly through its ctx verbs (`ctx unit`, `ctx lane`, `ctx rhythm current`), and stderr is the diagnostic, with `--diagnose` on the engine subcommands for the runtime and storage state.

Slug addressing is what lets the set grow and the modules and overlays extend it. A positional name would force every reference to chase every insertion; a slug is stable for life, and a module or overlay can append its own laws at the end without renumbering anything. The core laws are the source's own; the docs module appends its laws and clauses, the lane module its dispatch and git clauses, and the workspace and local overlays append their own. Slugs are unique across the generated layer and both overlays; the compose refuses a duplicate at boot.

### The overlays beside it

`AGENTS.workspace.md` and `AGENTS.local.md` sit beside the loader and extend the generated layer, by section, with `@append` or `@replace`. The workspace overlay is shared and tracked with the work; the local file is personal and yields to the workspace when they disagree. Both amend; neither may contradict a law. The order is the loader, the generated layer, the workspace overlay, then the local one; the compose checks the law slugs across the generated layer and both overlays at boot, and a duplicate refuses. They have their own page; here it matters only that the generated layer plus its overlays is what the agent actually reads.

## The artifact shapes

The shapes live in the laws and the guides, never in a separate template file:

| artifact | its shape |
|---|---|
| the state, backlog, journal, and knowledge | `@record` and [The record](the-record.md); the unit verbs write them and the record audit parses them |
| a subagent's recipe and report | `ctx lane create` composes the recipe from its brief parameters, and the recipe's `REPORT` block names the report's sections ([Units and subagents](units-and-lanes.md)) |
| the overlays | [Overlays](overlays.md) |

Writing is filling, never inventing: an artifact is written by filling its shape directly, with the schema in hand as the complete form. The laws pin the record shapes and the guides carry the rest, so the shape is read without concrete content to copy.

The drift control is the write path where one exists: the record shapes stay exact because the verbs write them and the audit reads them, and the recipe stays exact because `ctx lane create` writes it from the dispatcher's parameters, its fixed blocks from the verb's own text. The overlay and report shapes have no parser: the guide is their home (the report's sections are the ones its recipe names), and the agent holds them by reading it.

### The shared dialect

All grammars speak one dialect, and it is contractual. Typed blocks start at column 0; bodies indent two; `::` opens an indented block value; `|` means alternation only; `[ ]` wraps optional parts; `->` means flow; `#` starts a comment. Whitespace is load-bearing: a block that starts at the wrong column silently breaks every query written against it.

Spellings are contractual too. A pointer names its target exactly, a section and step (`@refresh`) or a path and symbol (`finding#NAME`); a vague mention is a defect. The reason is mechanical: the workspace queries with plain search, and a vocabulary word with two spellings is a search that silently misses.

The dialect governs form, never volume. It compresses how things are written, never how much: the schema holds the shape, the writer holds the volume. The grammars name the elements an artifact must carry; the rest is freestyle. The artifacts themselves, and the fields they carry, are the record page's material.

## The scripts

The runtime ships as one POSIX sh file at `.contexture/ctx`: discovery, help assembly, dispatch, the run engine, and the hook runner. Discovery reads two roots, the workspace modules root and the extension root (`.contexture/extensions/modules/`), listing the workspace modules first; an extension module whose name collides with a workspace module, a builtin, or a reserved name is warned and skipped, never a silent shadow, and an absent extension root is silent. Around it, modules declare their surface and the engine does the rest. The record engine is the unit module, its verbs as extension-less scripts under `.contexture/modules/unit/scripts/`, one file per verb, each carrying its `# summary:` and its `# usage:` lines; each verb is a thin POSIX sh script over the shared library in `.contexture/modules/unit/lib/` (the verb shell `verb.sh`, the answer flattener `json.awk`, the one renderer `render.awk`) that makes one storage call and renders its answer, and the posix driver under `drivers/posix/` is POSIX sh and awk too, which means no dependencies, no model tokens, and the same answer every time. A module is the standard folder ([Modules](modules.md)): the manifest `module` with its summary, version, and description block, beside its optional `laws`, `data`, `install`, and `uninstall` files and its `scripts/`, `hooks/`, and `filters/`. The engine reads the summary and validates the manifest through the private `ctx _module` reader; the compose reads the summary, description, and laws; the package installer validates a module part and reads the package manifest's version and parts through the private `ctx _package` reader; the storage reads the data. The engine assembles `ctx help`, `ctx <module> help`, and `ctx <module> help <verb>` from the `scripts/` declarations, so help is engine-owned and no module ships a help script. Dispatch validates the verb engine-side, anchors every command at the workspace root, and passes arguments, streams, and exit codes through. The engine answers `run`, `compose`, and `package` itself, before discovery, so none is a module and the engine itself prints no discovery warning for them (a package's part hooks run module verbs, which discover): `ctx compose [--check]` execs the core's private composer with its arguments, output, and exit code unchanged, refuses rc 2 naming a missing composer, and answers a sole `--help` or `-h` with its own usage. `ctx package install <package>` and `ctx package uninstall <package>` are one builtin group with its own sub-verb table: a catalog name resolves to `plugins/<name>` at the workspace root and a value holding a slash is a package root path read from the working folder; a usage error, a malformed name, an absent catalog package, or a missing private script refuses with one line before anything runs; otherwise the verb sets `CTX_ROOT` to its own workspace and execs the core's private installer or uninstaller from there, so the package always lands in that workspace. An install or uninstall runs only on the human's explicit go at the act, which the verb never checks. `ctx unit` fronts the record engine's verbs; `help` (or `--help`, or `-h`) prints the full contract table, so no one reads a script to learn one. After a verb, `--help` or `-h` alone prints that verb's own table: a shell verb answers it itself, and for an awk verb the engine prints the table `ctx <module> help <verb>` prints, since an awk interpreter would read a leading dash argument as its own option and the verb would never see it. Nothing needs installing.

Alongside the record engine, `ctx run` provides zero-parameter discoverable stream compaction and command execution. It operates both as a direct runner prefix (`ctx run <cmd>`, full path `.contexture/ctx run <cmd>`) preserving exact exit codes, and as a standard Unix pipe (`cmd | ctx run`). Runner mode selects the filter by the wrapped command's identity, read from the `# command: <regex>` header, and falls back to the signature scan when no command claims the line; stdin mode selects by the stream signature (`# match: <regex>`), sampled from the first 40 lines. The directive text reaches awk through the environment, so backslash escapes in a signature survive verbatim. ANSI escape sequences are stripped before selection and filtering, while the raw bytes stay untouched for the fail-safe comparison. Capture files for runner mode prefer the workspace's gitignored `.contexture/tmp/` when it is writable, and fall back to the caller's TMPDIR only when the drawer cannot hold them. The capture files are created in that drawer and unlinked before the command runs; the runner keeps open handles, so a recursive command cannot find or read its own captured output.

Filters live in the run module's `.contexture/modules/run/filters/*.awk` and in any module's `filters/` directory; the scan takes the run module first, then the other modules by name, the workspace modules before the extension modules. Their headers are the contract: `# match:` for the stream signature, `# command:` for the command identity, `# default` for the fallback, `# stream: merged` for filters that need the command's stderr inside the filtered stream, and `# format-only:` for filters whose marker-less reductions are layout rather than lost content. Core Contexture ships low-risk filters for Git unified diffs (`diff.awk`), directory listings (`list.awk`), and generic log deduplication (`log.awk`). The guards are strict: empty or grown output falls back to raw, a shrinking filter without a notice line falls back to raw unless it declares `# format-only`, a notice-only output passes through so a false-green signal is never hidden, and command stderr stays visible, whole on failure or empty stdout and tail-capped with its own notice otherwise. `COMPACT_DISABLE=1` bypasses compaction entirely; `COMPACT_DEBUG=1` reports the selection on stderr.

Building your own verb, hook, or filter? The module contract is in [Modules](modules.md).

### The storage contract (contract 3)

The record engine is decoupled from how any backend stores its bytes, and the record logic lives in one place. Base maps every unit and lane command to one storage function (one of the record's 35 operations or `search.query`, or the driver's own `capability` or `storage.health`), sends it the command's parameters, and renders the data it returns. The unit module answers the record's operations once, in its data script (`.contexture/modules/unit/scripts/data`), over the configured driver's generic store: it keeps the record as one store value per artifact in the current file shapes, parses and renders the canonical record text, enforces every record rule, and lands each write through the store. The driver is store-only: it answers `capability`, `storage.health`, the seven store data functions, and the store search, keeps every value as opaque bytes, and never parses the record, implements a record rule, materializes a unit, or delegates to another backend. The posix driver keeps a namespace's keys as files under its root, so the record's artifacts are the markdown files under `.contexture/units/<unit>/` (a unit not yet moved still under `.contexture/sessions/<unit>/`, the deprecated root it reads after the root), and it is the only code that touches them; the fts5 driver keeps the same values in its SQLite store. No markdown crosses the command interface: the record travels as typed data, and the configured backend is the single store, so a verb never opens a record artifact itself.

This section is the record rules the unit module implements over the store; the vitest project `unit-record` (`tests/unit-record`) is their executable form, run once on posix through the unit data script, while the drivers project (`tests/drivers`) holds every driver to the store contract, so a backend is compliant when it passes that contract; the unit-shaped profile of the store fuzzer (`tests/drivers/store-fuzz.test.ts`) is the standing differential proof beside the fixed cases: the record logic runs once in the unit module, so only the driver varies, and the profile drives it with unit keys, prefix lists, and multi-put batches of record-sized values. The earlier contracts differ: the v0.54.0 drivers spoke contract 1, whose verb layer fetched whole artifacts and rendered the files itself, and a contract 2 driver implemented the record functions and their rules itself; the contract 3 handshake refuses either at dispatch, since its card carries the store alone.

#### The wire

A call is the callee (the unit module's data script for a record function, the driver through the resolver for its own two methods) run with the function name and its bounded identifiers as argv (a unit, a slug or NAME, a lane, an artifact word, filter tokens such as `--limit=N`), and every free-text field on stdin as payload lines `key=value`. The value is escaped: backslash as `\\`, newline as `\n`, tab as `\t`, carriage return as `\r`, so a value of any size or content survives exactly and never meets the platform argument limit. A list travels as `<key>.count=N` followed by `<key>.1` to `<key>.N`; `<key>.count=0` is the empty list, and an absent key is an absent field. A list of records travels as `<key>.count=N` and `<key>.<n>.<field>`, and a list inside a record nests the same way (`closers.1.targets.count=2`, `closers.1.targets.1=...`). A single document (a recipe, a report) is the raw stdin itself and the function takes no other payload. A function without payload keys never needs stdin.

The answer is rc 0 and exactly one line on stdout: one compact JSON object (no whitespace between tokens) with its keys in the order this section lists them and every listed field present, `null` when absent. Strings are UTF-8 in one JSON form, the form `JSON.stringify` writes: `\"` and `\\`, the short escapes `\b`, `\f`, `\n`, `\r`, `\t`, `\u00XX` (lower-case hex) for the other characters below 0x20, and every other character raw, `/` and non-ASCII included. Integers are plain decimals; a score is a JSON number. Because the form is fixed, the same record answers the same bytes from every backend, and `--json` on a verb prints the function's answer unchanged.

A refusal is rc 1 (the caller's input or the record's rules) or rc 2 (storage or driver failure), nothing on stdout, and exactly one stderr line `<function>: error: <message> (<CODE>)`. The message is fixed per code, so every backend prints the same line:

| code | tier | message |
|---|---|---|
| `ERR_INVALID_ARGUMENT` | 1 | the detail of the shape at fault (a missing or malformed identifier, a malformed payload line, an empty search query) |
| `ERR_ENTITY_NOT_FOUND` | 1 | `<kind> '<x>' not found in unit '<u>'` (kind `task`, `entry`, `finding`, `lane`, and `artifact` for `session.board` and `session.audit` of a unit whose journal is absent: `artifact 'journal' not found in unit '<u>'`); `unit '<u>' not found` |
| `ERR_ENTITY_EXISTS` | 1 | `<kind> '<x>' already exists in unit '<u>'` (a lane entry reads `lane entry '<lane>/<slug>'`); `unit '<u>' already exists` |
| `ERR_UNIT_CLOSED` | 1 | `unit '<u>' is CLOSED; a closed unit takes no writes` |
| `ERR_INVALID_TRANSITION` | 1 | `<kind> '<x>' is <STATUS>; <function> moves only from <allowed>`, allowed `TODO` (task.start), `TODO or IN_PROGRESS` (task.complete), `IN_PROGRESS or DONE` (task.reopen), `TODO or DONE; reopen an IN_PROGRESS task before dropping it` (task.drop), `ACTIVE` (session.close), `CLOSED` (session.reopen) |
| `ERR_CAPABILITY_UNSUPPORTED` | 1 | `mode '<m>' is not supported; declared modes: <modes joined by , >` |
| `ERR_CAPABILITY_UNSUPPORTED` | 2 | `unknown function '<f>'` (the function name at dispatch) |
| `ERR_STORAGE_READ`, `ERR_STORAGE_WRITE`, `ERR_STORAGE_LOCKED`, `ERR_STORAGE_CORRUPT` | 2 | the backend's detail |
| `ERR_STORAGE_SCHEMA` | 2 | `the store is at schema <v>; this driver reads <w> and has no upgrade path: move the store aside and re-enter the record into a fresh one through the ctx verbs` (fts5) |
| `ERR_DRIVER_NOT_FOUND`, `ERR_DRIVER_PROTOCOL` | 2 | the resolver's |

The order of refusals: the argv shape first (`ERR_INVALID_ARGUMENT`), then the unit (`ERR_ENTITY_NOT_FOUND`), then a write to a `CLOSED` unit (`ERR_UNIT_CLOSED`, before any other record rule), then the function's own rules. A write refused at any point writes nothing.

#### The error shape

The one-line protocol covers every storage surface: the record's 35 operations through the unit module, the seven store data functions, the store search entry, the module-facing library's store functions, and its ref interface. A success is rc 0 with the function's one answer; a refusal is rc 1 (the caller's input or the record's rules) or rc 2 (storage or driver failure), nothing on stdout, and exactly one stderr line `<function>: error: <message> (<CODE>)`, the function being the public function or the module data operation name and the message naming the namespace, key, ref, unit, action, or field at fault, never a storage path. The code table above is the whole core vocabulary: the store reuses it, and no new core code joins it.

The batch names the failing action: `store.batch: error: action <n> (<op> '<key>'): <message> (<CODE>)`, the action counted from 1 in the submitted order; a malformed action list before its first action completes reads `action 1 (? '?')`; a malformed action is `ERR_INVALID_ARGUMENT`, an action refusal keeps the underlying code, and a driver failure keeps its code with the same context. Only the first failure prints, nothing is written, and the answer is never partial. The batch cases of the drivers project (`tests/drivers/store-contract.test.ts`, with the planted second-action write failure in `store-faults.test.ts` and the fts5 trigger in `plugins/storage-fts5/tests`) pin it on both drivers.

The scan's refusals use the same codes: a missing or malformed argv, a malformed namespace, or a malformed data declaration is `ERR_INVALID_ARGUMENT`; a namespace no data file declares is `ERR_ENTITY_NOT_FOUND`; an unreadable key or store is `ERR_STORAGE_READ`; a driver that does not serve the store answers its unknown-function line at tier 2. A scan stages its answer and prints it whole, so a read failure midway prints nothing on stdout; the drivers project's `store-contract.test.ts` pins the answer and the refusal lines on both drivers, the planted encoder failure included.

The ref interface (`data_get`, `data_emit`) follows the same lines: a malformed ref is `ERR_INVALID_ARGUMENT`, a missing target module or entity is `ERR_ENTITY_NOT_FOUND`, and the target's own refusal keeps its code and message re-framed with the source function and the ref, `data_get: error: ref '<ref>': <message> (<CODE>)`; a chain over 8 hops or a repeated ref in the chain refuses `ERR_INVALID_ARGUMENT` naming the ref and the limit or the cycle. The source write's half of the ref shape is the unit module's: the source write re-frames the same failure with its own function, `task.add: error: ref '<ref>': <message> (<CODE>)`, and refuses before writing. The library's half is pinned by the drivers project's `library.test.ts` on both drivers; the source write's half by the `unit-record` project's module data cases (`module-data.test.ts`).

A record function whose own store call refuses re-frames the store's line the same way: one stderr line with the record function's name, the store's message, and the store's code, `session.board: error: cannot read key '<unit>/journal' in namespace 'unit' (ERR_STORAGE_READ)`, its rc as before and the store's own line never reaching the verb; the resolver's own `driver-resolver: ` line rides whole as the message, and a store that printed neither its refusal line nor a resolver line (nothing, or only a foreign line) leaves the fixed line of its call, `the store read failed (ERR_STORAGE_READ)`, `the store list failed (ERR_STORAGE_READ)`, or, for the batch, `the store batch failed (ERR_STORAGE_WRITE)`, so the line always carries a code. One helper of the unit module carries its `store.get` and `store.list` reads and the write's `store.batch` (the unit module's README names it); the `unit-verbs` project's `storage-faults.test.ts` pins it over an unreadable state and journal, a store list that cannot make its scratch, a held namespace lock, and a wrapper resolver making each of the three calls print nothing or only a foreign line, or a foreign line before the store's own refusal.

Module-owned codes stay at tier 1: a module's data script or verb may mint its own code (the docs module's `ERR_SCHEMA_VIOLATION` is the precedent, rc 1 and nothing written); the core's codes are reserved for core and driver semantics, and a module never redefines one.

The resolver is the one shape exception: its diagnostic is `driver-resolver: ERROR: <detail> (ERR_DRIVER_NOT_FOUND|ERR_DRIVER_PROTOCOL|ERR_CAPABILITY_UNSUPPORTED)`, uppercase and outside the `<function>: error:` form; the library passes it through unchanged, and a module verb that asks a capability may re-frame it in its own line. The handshake stays one line when it refuses: the driver's own refusal line folded into `driver-resolver: ERROR: capability handshake failed for driver '<name>': <driver line>`, or the resolver's `ERR_DRIVER_PROTOCOL` line when the driver printed none. The drivers project's `resolver.test.ts` pins the resolver line as the exception.

The interrupt rule stands: rc 0 means the write landed; after an interrupt any other exit means check with a read before writing again (Exit tiers, atomicity, and interruption).

#### The functions

Thirty-eight functions, each called by the verb in the last column: the driver's own two (`capability` and `storage.health`, reached through the resolver), then the record's 35 operations and `search.query`, which the unit module's data script answers over the store; the eight module store functions (the seven data functions and the search) and the optional promotion (`store.promote`) follow them, under The module store. Schemas are in the data model. No function moves a record between backends: `unit.export`, `unit.import`, and the dump format left the contract (below, Moving a record between backends). Outside the 35, as `data_get` is, the data script answers `unit.promote` (`<unit>...` or `--all`, answering `{promote, migrated}`), the sweep behind `ctx unit migrate`, which moves units between the declared roots of the one posix store.

#### The record data model

Every block artifact (the journal, the backlog, the knowledge, a lane journal) is a preamble followed by items in order. The preamble is the text before the first item head, as stored; `null` means the artifact is absent, `""` present with nothing before the first item. In a journal and a lane journal only a column-0 `@entry ` or `@anchor ` line starts an item, so any other column-0 text (a comment, a continuation line, an unknown `@` word) belongs to the preceding item; in a backlog and a knowledge artifact every column-0 `^@[A-Za-z]` line starts an item, a head other than `@task` (in the backlog) or `@finding` (in the knowledge) making an opaque item.

Every item is typed data and renders in one canonical layout: its canonical lines (per kind, below), each newline terminated, followed by one empty line when a next item exists and is not an anchor, and by nothing when the next item is an anchor or the item is the last. That text is the item's span, the one every read prints on every backend; no answer carries an item's stored bytes, so field order, spacing, quoting, blank lines, and line endings are layout, never data, and the same record prints the same text everywhere. What the typed fields cannot hold in their schema is content the model still holds, in named fields: an item's extra fields (a field line beyond its schema, or a repeated one, key and value in line order), its extra lines (a line no field holds, as stored), its head text (text after the id on the head line), an entry's legacy status, a closer's extra text (a word of its target part that names no date-slug), an opaque item's head and lines. Every item a view renders carries `next`, the kind of the following item (`entry`, `anchor`, `task`, `finding`, `opaque`, or `null`), so base computes the separator without seeing the neighbor.

The append rule, for every write that adds an item: remove the artifact's trailing empty lines, write one empty line unless the new item is an anchor or the artifact holds nothing, then the new item's canonical lines. So a journal never ends with an empty line, an anchor follows its predecessor directly, and an entry follows one empty line.

A write that touches an item (a task status move, `task.update`, `finding.update`, a state write by `session.refs`, `session.stamp`, `session.close`, `session.reopen`) sets its typed fields and stores the item in its canonical lines from them, every field it holds kept (its extra fields, extra lines, head text, legacy status); a drop removes the item, then the artifact's trailing empty lines go. The unit module keeps every other byte of the stored value as it stands, on every driver: an artifact keeps its bytes until a write touches one of its items, and then only that item's span (its lines to the next head) is rewritten canonical, a rewritten last item leaving the value ending with a newline; an append after a legacy item keeps that item's bytes (only the artifact's trailing empty lines go). A block value (a DESCRIPTION, ACCEPTANCE CRITERIA, IMPLEMENTATION DETAILS, or SUMMARY body) drops its trailing whitespace-only lines on every write and every read, a value of blanks alone reading `""`, since the dialect cannot tell such a line from the separator after the item.

The derived fields: `ordinal` and an opaque item's `seq` count every item of the backlog or the knowledge from 1, opaque items included; `seq` counts every journal (or lane journal) item from 1, anchors included; `occurrence` counts the occurrences of a slug up to this one from 1, so a legacy repeat reads 2 and up. Liveness is positional: an entry occurrence is closed exactly when a closer standing after it names its slug; `closed_by` is the slug of the first such closing entry and `close_reason` its parenthesis, `<verdict>: <reason>` with a verdict, the reason alone without one, null when both are absent. `superseded_by` is the NAME of a finding whose supersedes names this one, and `active` is true when there is none. The board's `live` holds every entry occurrence no later closer names, in journal order; `open_tasks` every task whose status is not DONE, in backlog order; `open_threads` every live entry whose thread is set and not `none`, its anchor the entry's ANCHOR or `""`. An Audit finding's `slug` names the entry or task it is about (for DANGLING_CLOSER the closing entry, with the absent target in `detail`; for BRACKETED_FIELD the owning entry, with the field text in `detail`); `line` is the line of the stored journal value the finding stands on, counted by the unit module on every driver (null for DONE_WITHOUT_EVENT, a backlog finding), `first_line` the line of a repeated slug's first occurrence, and `occurrence` is set for LEGACY_DUPLICATE_SLUG, which only a posix file can hold (the functions refuse a repeated slug).

The canonical lines, what every read prints and every write stores:

- state: its extra lines, then `status: <s>`, `current_anchor: <a>`, `objective: "<o>"`, `repos: [<a, b>]`, `ref_sessions: [<c, d>]` when not null, then each extra field as `<key>: <value>` (a value's later lines following it as stored); a legacy `next_action` line and its continuation lines are consumed and dropped by the parse, never rendered, and the next state write erases them.
- task: `@task <slug>` (then ` <head text>` when set), its extra lines, `  STATUS: <s>`, `  OBJECTIVE: "<o>"`, `  REFS: [<a, b>]` when refs is not empty, then `  DESCRIPTION ::`, `  ACCEPTANCE CRITERIA ::`, `  IMPLEMENTATION DETAILS ::` for each non-null section, each followed by its body lines prefixed by four spaces, an empty body line written empty, then its extra fields.
- entry (the main journal and a lane journal alike): `@entry <slug>` (then its head text), its extra lines, its extra fields, then, each when set, `  ANCHOR: <a>`, `  STATUS: <legacy status>`, `  WHAT: "<w>"`, `  GROUP: <g>`, `  RHYTHM: <r>`, `  THREAD: <t>`, one `  REF: "<r>"` per ref, one closer line per closer (`  <KIND>: <targets joined by one space>`, then ` <extra text>` when set, then ` (<verdict>: <reason>)`, or ` (<reason>)` without a verdict, or nothing without either), and `  KNOWLEDGE: true` when set. The extra fields stand before the schema lines because the parse types the last occurrence of a one-line label.
- anchor: `@anchor <A> <date>` when date is set (the stamp form); else `@anchor <A> ("continues <P>", attention: <text>)` when both are set (the A1 of `session.create`, or a legacy receipt); else `@anchor <A>` followed by its head text; then its extra lines.
- finding: `@finding <NAME>` (then its head text), its extra lines, `  SUPERSEDES: <old> (<reason>)` when set, one `  REF: "<r>"` per ref, `  SUMMARY ::` and its body lines as a task's, then its extra fields.
- opaque: its head line, then its lines.
- a one-line field holding a newline (a legacy WHAT or OBJECTIVE over several lines) renders as a block scalar (`  WHAT ::` and its body); an extra field renders as `  <KEY>: <value>` with its value as stored, or as a block scalar when the value holds a newline.

The parse rules, how the unit module reads every stored value, and with it every legacy shape the convention once accepted, into these fields (a legacy unit stays readable without repair and no value is lost on read; strictness applies to new writes only):

- The content of an item is its lines after the head up to its trailing blank lines. A field line is `  <LABEL>: <value>` (label upper case with underscores); a block scalar opens with `  <LABEL> ::`, text after the `::` being its first body line, and its body is the following lines indented four spaces or more, blank lines inside it kept as empty lines, four spaces removed from each, its trailing whitespace-only lines dropped. Every other line (a continuation, a comment) is an extra line of the item.
- A line ending in a carriage return (a legacy CRLF line) parses without it, so every typed string stays LF only; the carriage return stays in the file's bytes until a write touches its item.
- A quoted value that opens with `"` on a WHAT or OBJECTIVE line and does not close on it continues over the following content lines until one ends with `"`; the value is those lines joined by newlines as stored.
- Unquoting removes a leading and a trailing double quote (a value that only opens a quote loses its leading one); a REF loses a surrounding pair.
- Entries: for ANCHOR, GROUP, RHYTHM, THREAD, and STATUS the last one-line occurrence is typed (STATUS reads into legacy_status); the last WHAT, a line or a block, is the what; KNOWLEDGE is true when its last line reads `true`; REF, CLOSES, and SUPERSEDES are lists in line order; every other field line (an earlier occurrence, a KNOWLEDGE line not typed, an unknown label, a block of a one-line label) is an extra field in line order with its value as stored.
- A closer's targets are its value cut at the first ` - ` or ` (`, every blank-separated date-slug token of the part before the cut, its other tokens its extra text. After the cut, a parenthesis read to its last closing parenthesis (a legacy reason may hold parentheses of its own) whose text reads `<verdict>: <reason>` with a known verdict gives both; other parenthesis text is the reason with a null verdict; ` - <text>` is the reason with a null verdict.
- Tasks: the first STATUS (a statusless task reads `TODO`), the first OBJECTIVE (a line unquoted, or a block), the first REFS as a list (`[a, b]` split on commas, or blank-separated bare refs), the first of each block section; every other field line is an extra field.
- Findings: SUPERSEDES `<old> (<reason>)` gives the name (its first token) and the reason (the parenthesis text to its last closing parenthesis, `""` without one); every REF unquoted; the first SUMMARY, a block or a line (`""` when absent); every other field line an extra field. The two block orders both read; SUPERSEDES, REF, SUMMARY is canonical.
- Anchors: a `YYYY-MM-DD` date alone after the anchor gives the date; `("continues <P>", attention: <text>)` gives continues and attention, the attention losing a surrounding pair of quotes; any other text after the anchor is its head text; the lines after the head are its extra lines.
- State: each `<key>: <value>` line at column 0 opens a key, and the indented lines after it continue its value (joined by newlines as stored) until a blank line or the next column-0 line; the first line of each of the five keys is typed (objective unquoted, repos and ref_sessions lists, ref_sessions null without its line); every other key (unknown, or a later occurrence) is an extra field, every other line an extra line; a legacy `next_action` key and its continuation lines are consumed and dropped, never an extra field.
- The head line of a task, finding, or entry gives the id (its second token) and the head text (anything after it).

A store that holds only what the verbs write (fts5, since no command moves a record into it) never holds legacy text: its answers carry legacy_status null, extra_fields, extra_lines `[]`, head_text and extra_text null, and no opaque item.

#### The record rules

Base checks only the input shape before any call (slug and NAME shapes, no newline in a one-line field, no carriage return anywhere, required flags, the THREAD shape on `record` and `lane record` (what the unit or lane awaits, or `none`; never empty, `true`, or `false`), the explicit closer form `<slug> (<verdict>: <reason>)`, the two REF shapes `<target>#<symbol>` and a whole target path holding a `/` and ending in a name (a root-level file as `./README.md`; never a lone `/`, a trailing `/`, or `./`), one token without blanks or control characters, the search flags with `--mode` required, the resolve forms, unknown flags refused, and the bytes: every flag value, payload field, and document (a lane report) must be valid UTF-8 and hold no NUL byte, else rc 1 `<verb>: error: <field> is not valid UTF-8 (ERR_INVALID_ARGUMENT)` (a lane verb as `lane <verb>`) or `<field> holds a NUL byte`, naming the payload field (`what`, `objective`, `query`, ...), the `ctx lane create` flag (`goal`, `scope`, ...), or the document (`the report`), so every backend answers such a value alike; a slug-shaped value refuses any other byte by its shape first; the bodies of the `ctx docs` write verbs are the docs plugin's to check; a legacy posix file holding such bytes keeps reading) and keeps its v0.54.0 messages where it had them. #### Search

`search.query` answers `{unit, query, mode, total_matches, results}` with each result `{entity_type, entity_id, section, snippet, score}`. The entity types are `session`, `task`, `entry`, `finding`, `lane`, `lane_entry` (the id `<lane>/<slug>`); the sections `state`, `backlog`, `knowledge`, `journal`, `lane_recipe`, `lane_journal`, `lane_report`. `--limit` defaults to 20, `--entity` to all. There is no default mode: base refuses a search without `--mode` before any call, naming the modes the configured backend declares in its descriptor, so a caller always names the mode it wants and never gets a backend's silent choice (a function call without `--mode` is outside the contract). `exact` is the one mode the contract defines, the unit module's own rule, answered alike under every driver; a ranked mode is the store's search, declared in the driver's descriptor, which the unit module asks over the record's document set and maps back to the record's ids, and a mode the driver does not declare refuses `ERR_CAPABILITY_UNSUPPORTED` naming the declared ones.

The exact rule, one text the unit module searches under every driver: the searched text of a unit is, in order, the state text, the backlog (preamble, then every item's span), the knowledge, the journal, then every lane in bytewise order (the recipe, the lane journal, the report); an absent artifact contributes nothing. It is the text a read renders (the state and every item in their canonical lines), never the stored bytes, so a legacy item matches as it reads. A line matches when the query is a substring of it after ASCII case folding (A to Z fold to a to z, nothing else folds); a line starting with `#` never matches. A line belongs to the session for the state and the main preambles, to its task, finding, or entry for a span, to the session for a main journal anchor, to the lane for the recipe, the report, and the lane journal preamble, to its lane entry for a lane entry span; a lane anchor and an opaque item keep the attribution of the line before them. The attribution follows the head lines as the unit module's `lib/search.awk` reads them, in every searched text alike: a column-0 `@task <id>`, `@finding <id>`, or `@entry <id>` line (the id its second token, cut at a `(`) moves the attribution to that task, finding, or entry (a lane entry inside a lane's texts), even where it stands inside a recipe, a report, or another item's span, and a column-0 `@anchor` line of a main text moves it back to the session; any other column-0 `@` word leaves it unchanged. One result per (entity_type, entity_id, section), its snippet the first matching line in text order with its blanks trimmed, then a leading upper-case label and colon (`[A-Z_]+:`) with its following blanks removed, then one leading and one trailing double quote with their adjacent blanks; `total_matches` counts those pairs, results follow text order and stop at `--limit`, and every exact result scores 0. The unit module's `lib/search.awk` is this rule as code, run over the canonical render of the values the store holds, so no driver implements it.

#### The descriptor and the handshake

`capability` answers `{"driver","version","contract":"3","store":[...],"search_modes":[...],"optional":[...]}`: contract 3 is the store-only card, so it carries no `functions` family; `store` the seven store data functions in the fixed order `list`, `get`, `put`, `delete`, `changes`, `batch`, `scan`, named unprefixed (the family carries the `store.` prefix); `search_modes` its modes (`exact` always); `optional` its optional capabilities (`store`, `store.changelog` where the driver keeps a log, `search.schema` where the driver consumes a declared search schema, and `store.promote` where the driver reads a declared fallback root and moves a key prefix from it to the root), and no other token. The store family is required and implies the `store` token, so a descriptor may omit the token; a name outside the seven refuses, and `store.changelog` or `search.schema` outside the family refuses. The store search entry is not a descriptor field: the family, the search modes, and the `search.schema` token declare it. `capability` and `storage.health` are the driver's own methods, never descriptor families: the handshake and `ctx unit diagnose` call them. The driver version is `3.0.0`. Posix declares the seven, `["exact"]`, and `["store","store.promote"]`; fts5 the seven, `["exact","hybrid","trigram"]`, and `["store","store.changelog","search.schema"]`. The driver descriptor version is distinct from the package version: a storage-driver package's manifest declares the package version (install, upgrade) and names the driver, while the driver's `capability` answer declares the descriptor version and the capabilities.

Before a driver serves a call the resolver runs its handshake (stdin from `/dev/null`): the descriptor must read contract `"3"`, carry no record function family, declare the seven store data names in the fixed order, and declare `exact` among its search modes; the family and the optional tokens must agree, and an optional token outside `store`, `store.changelog`, `search.schema`, and `store.promote` refuses (the resolver's `capability` and `check` hold the bundled posix driver to the same list); else the call halts rc 2 `ERR_DRIVER_PROTOCOL` naming what is missing, before the function runs. A record-only driver (no store family) refuses, because contract 3 serves the store alone. The handshake runs at dispatch for every driver except the bundled posix driver, and its verdict is cached in the scratch drawer (`.contexture/tmp/driver-verdicts/`, one file per driver path) and stays valid while the driver executable exists and the verdict is strictly newer than it and than the workspace configuration (`.contexture/config`, when it exists), so a driver that reads configuration is verified again after a configuration change; `driver-resolver capability` and `check` (and `ctx unit diagnose`) run it afresh. A caller that needs an optional capability or a search mode asks first: `driver-resolver require <capability>...` exits 0 when the driver declares every one and 2 `ERR_CAPABILITY_UNSUPPORTED` naming the missing ones, `driver-resolver has <capability>` exits 0 or 1 and prints nothing; a search mode reads as `search.mode.<m>`, and the store family implies `store` even when the token is omitted. A passing `require` verdict is cached per driver path and capability set (sorted), apart from the dispatch verdict, which it never answers or overwrites, and `require` and `has` find the driver there and executable before any cached verdict answers, so a removed driver refuses rc 2 `ERR_DRIVER_NOT_FOUND` whatever verdict it left; `has` reads such a verdict and writes none, so the cache names exactly the sets callers required. A drawer that cannot hold a verdict caches neither kind: the resolver verifies on every call and adds nothing to stderr.

#### The module store

The storage core (`.contexture/storage/`) owns the driver resolver, the generic module store contract, the module-facing library, and the posix driver; it is not a module, so `ctx help` does not list it. Every caller (the unit and lane verbs and the docs module) resolves the configured driver and asks its capability questions through the core resolver directly; the session module's compatibility wrapper retired with the unit module. The store serves module-owned data only: the docs corpus reaches the store through the docs module's own typed layer, and the record's module-side implementation is the unit module at `.contexture/modules/unit`. Its data file declares the record as one store value per artifact (namespace `unit`, root `.contexture/units`, the deprecated fallback root `.contexture/sessions`, suffix `.md`, the key `<unit>/<path...>`, and the document-set search rules), and its data script answers the 35 record operations over the store's `get`, `list`, and `batch` with the module's own parser and canonical render: the values are the current file shapes, a multi-key write lands through one `store.batch`, the exact search is the record rule over the canonical render, a ranked mode is the store's document-set search filtered to the unit, and the canonical `unit#<unit>/...` refs resolve through the module's `data_get`. The driver is store-only under contract 3: it keeps capability, `storage.health`, the seven store functions, and the store search, and the unit verbs reach the record through the unit module data script over the store; `ctx unit` is the record surface, and `ctx session` is retired naming it. The core reads and validates a module's data file; it never calls the module's code, and no module's parser enters base.

A module declares its data in a `data` file beside its `module` file, one `field: value` line per field and a line starting with `#` a comment. Only `namespace` and `key` are required; `root`, `fallback_root`, `suffix`, `changes`, and the search keys are optional:

```text
namespace: <name>
key: <segment>/<segment>            # or a final <segment...> for a variable-depth key
root: <workspace-relative folder>   # optional; default: the namespace
fallback_root: <folder>             # optional; a deprecated root read after the root
suffix: <suffix>                    # optional; default: empty
changes: true                       # optional; default: false
search: flat|documents              # optional; the search schema form
format: text|json                   # optional; flat only; default text
fields: <field>, <field>            # optional; flat only; the JSON fields to rank
title: <field>|key|head             # optional; flat default key, documents default head
snippet: line                       # optional; default line
modes: exact, hybrid, trigram       # optional; default exact; exact is required
document: <key-pattern> <section> <entity-type> <head-marker|->   # repeatable
```

The namespace is a lowercase token of letters, digits, dot, underscore, and hyphen; the key pattern carries one `<name>` placeholder per slash-separated segment, and its final segment may instead be `<name...>`, which admits one or more key segments (a module's main files and its deeper lane files share one pattern: `key: <unit>/<path...>` admits `unit/state` and `unit/lanes/x/report`). The root is a workspace-relative folder inside the workspace and defaults to the namespace; the fallback root, when declared, is such a folder too, neither equal to the root nor nested with it (one inside the other): a deprecated root a file store reads after the root and never writes, so a module can move its root while the data at the old one still reads; the suffix defaults to empty; `changes` is `true` or `false` and defaults to `false`. A module may override each default: the docs module declares root `docs`, suffix `.md`, and `changes` true, and the unit module's declaration, expressible before its install, is root `.contexture/units`, fallback root `.contexture/sessions`, suffix `.md`, key `<unit>/<path...>`, and `changes` false.

The search schema has two forms. `flat` makes one document per key, section `body`: `format: text` indexes the raw value, `format: json` with `fields` extracts those top-level JSON fields, and `title` names the field whose value titles the document (`key` keeps the key). `documents` declares one repeated rule per document group: the key pattern (placeholders and literal segments, with the final `<name...>` admitted), the section, the entity type, and the `-` or a column-0 head marker such as `@task`; a marker with an id starts a new entity, a marker whose entity type is the section's default joins the default document (the journal's `@anchor`), and a key no rule covers stays searchable as one generic document. `snippet: line` is the only snippet rule. `modes` names the modes the module asks for; `exact` is required and always answered, a ranked mode answers only where the driver declares it. A duplicate field, an unknown field, a document rule without the document form, a flat field with a document rule, a repeated mode, and modes without `exact` all refuse. The module directory beside the data file is the owner, and a second data file declaring the same namespace refuses. A module's data file ships beside its module file; the docs module's values and root are in its module README.

A module's script sources `.contexture/storage/scripts/library` and calls the store through it (`store_list`, `store_get`, `store_put`, `store_delete`, `store_changes`, `store_batch`, `store_scan`, `store_search`, `store_promote` where the driver declares it, `store_require`, `store_has`); the module never names the driver. `store_roots` reads the declarations instead of the driver: one line per declared root, the namespace and the root separated by a tab, sorted by namespace, a declared fallback root on its own line after its root, from the core's data reader in its listing mode (`store-data --list`, one `<namespace><TAB><root>` line per valid declaration with a declared fallback root as a third column, which leaves out a malformed declaration, a data file with no namespace, and a doubly declared namespace, each with one line on stderr, and answers rc 2 with no module drawer). The per-namespace answer `store-data <namespace>` is twelve fixed lines and the document rules, never the fallback root, so a parser reading by position ignores the field; `store-data <namespace> --with-fallback` answers the fallback root as line 13 (an empty line when none is declared) and the rules from line 14, the form the posix driver reads; any other second argument refuses rc 1. The docs module's nudge reads it to refuse a backlog file inside another module's store root, and refuses rc 2 on a base whose library lacks it. The library also carries the module data interface: `data_get <ref>` resolves a `<module>#<symbol>` reference by running the target module's data script (in the workspace modules, the workspace extensions, or the base mirror of either: `modules/<module>/scripts/data` and `extensions/modules/<module>/scripts/data`) and printing the envelope that script emits through `data_emit <ref> <data>`; a ref chain is bounded at 8 hops and a repeated ref in the chain refuses as a cycle. The source write's validation of a new ref is the unit module's (the `unit-record` project's module data cases pin it). The docs module reads its corpus through the library.

| function | argv | stdin | answer |
|---|---|---|---|
| `store.list` | `<namespace> [<prefix>]` | none | `{"namespace","keys"}`: every key the module pattern admits, bytewise; the optional literal key prefix narrows it (the per-unit read) |
| `store.get` | `<namespace> <key>` | none | the raw bytes of the key, no JSON; absent rc 1 `ERR_ENTITY_NOT_FOUND` |

| `store.delete` | `<namespace> <key> [--op=<op>] [--head=<sha>\|none]` | none | `{"namespace","key","op"}`; the default op is `remove` |

The seven data functions and the search entry are the contract 3 card itself: the store family is required, since the record reaches a driver only through it, so a driver without it fails the handshake and serves nothing, the record included. Keys are exact: a key that ASCII-case-folds onto another in the namespace refuses, a read or delete acts on the exact key alone, list is bytewise, and no key holds a blank, a control character, a leading slash, a backslash, or a `.` or `..` segment. The module pattern filters list and scan and refuses a key outside it; a final `<name...>` placeholder admits one or more key segments, so a variable-depth declaration covers a module's main and deeper keys under one pattern. The bounded `--op` and `--head` flags are checked before the module data file and the key, so a malformed argv answers the same first refusal on every driver. The posix mapping is `<root>/<key><suffix>` under the workspace root, written by a same-directory temp moved over the key under one namespace scope lock, so a put lands whole or not at all. A namespace declaring a `fallback_root` reads from its root first, then from the fallback: `store.get`, `store.list` (the union, each key once, the root's copy shadowing), `store.scan`, `store.search`, and the key probe; `store.put` and `store.batch` write the root alone, and a delete, alone or as a batch action, removes the key from both roots, so an old value never resurfaces; before it writes, a put, a delete, or a batch (after its validation) moves each written key's top segment folder from the fallback to the root under the namespace lock it already holds, when the fallback alone holds it, by one `mv` (the root made first when absent), so a module's write moves its folder whole with no call of its own, and the move that empties the fallback root removes that root in the same call (one `rmdir`, which refuses silently while any folder or file remains, so a root still holding one stays), while a folder already in the root or a namespace without a fallback costs one folder check at most and no process, and a folder both roots hold refuses rc 1 `ERR_ENTITY_EXISTS` naming the prefix (a batch in its action line) with nothing written; a call that served a key from the fallback and answers rc 0 prints one stderr line, `<function>: notice: namespace '<ns>' was read from its deprecated fallback root`, naming no folder, while a refusal keeps its one line. `store.promote` moves one prefix's folder from the fallback to the root by one `mv` under the namespace lock, the root's parent folders made first and a killed writer's residue moving with the folder, and removes the fallback root as the write path does when its move empties it, and an empty fallback root when it answers `none`; fts5 holds namespace and key with no root, never reads a fallback, and does not declare the token. The batch holds that lock once, validates its whole action list against the live keys, stages a value per put, and commits every key under one store-scope undo log, so a planted second-action failure restores the first and prints only that action's line; fts5 runs the whole list in one `BEGIN IMMEDIATE` transaction with one `store_changes` row per action. A filesystem can fold more than ASCII (a Unicode case variant): the posix store refuses a key its root cannot represent exactly beside a stored key, and removes what it just wrote, so a successful put always lists the key it echoes; fts5 holds the two exact keys. `store.changes` is optional per namespace: a namespace declaring `changes: false`, or a driver without the log, refuses rc 1 `ERR_CAPABILITY_UNSUPPORTED`. The posix driver keeps no change log (the module's delta is git); fts5 keeps the generic log.

`store.search` answers one shape on every driver. `exact` is the record rule over the raw stored value: a line of the value matches when the query is a substring of it after ASCII case folding, a column-0 comment never matches, one row per entity and section, its snippet the first matching line with its upper-case label and quote pair trimmed, every score 0. The answer carries the entity identity the document rules derive: `entity_type` and `entity_id` beside the key, the flat and generic fallbacks answering the one document with its key as the id. The exact walk collects every match before printing, so `total_matches` counts every entity and section pair and the limit applies after the walk, results following bytewise key and line order; `limit` 0 answers every result, the unlimited read a module uses to sort into its own text order and cap there. The searched text is the stored value: the canonical source is the module's canonical render, which the module writes through the store, and the core never re-renders a module's grammar (a legacy value is searched as stored). The document set follows the schema: the flat form is one document per key in section `body` (the raw value for text, the declared fields for JSON), the document-set form is the per-entity extraction the data file declares, derived at write time by the fts5 store and indexed in its store FTS tables; a key no rule covers and a module with no schema use the generic raw value. A ranked mode (`hybrid`, the RRF of the fts5 porter and trigram indexes, or `trigram` alone) answers only where the driver declares it in `search_modes` and the optional `search.schema` token; a mode the module does not declare or the driver does not serve refuses rc 1 `ERR_CAPABILITY_UNSUPPORTED` naming the declared modes. The fts5 store re-derives a namespace's documents whole when its stored schema signature differs.

The descriptor is the contract 3 store-only card: the seven store data functions in `store` (unprefixed, fixed order), with the optional tokens `store` (implied by the family), and, where the driver keeps one, `store.changelog`, and, where the driver consumes a declared search schema, `search.schema`, and, where the driver reads a declared fallback root, `store.promote`; the driver version is `3.0.0`, and the card carries no record function family. The drivers project's `store-contract.test.ts` pins the card and checks the seven-name family and the token agreement; the record itself runs through the unit module data script in the `unit-record` project. The vitest drivers project (`tests/drivers`) holds both drivers to the seven functions in one parameterized set over a docs-shaped synthetic namespace: the exact list answer and order and the optional key prefix, the raw bytes of a document, the key rule, the data file grammar, the namespace lock, the atomic put, the all-or-none batch and its first-failure line, the scan's base64 values, empty namespace, and staged answer, the exact rule with its entity identity and the document-set extraction, the limit after the walk and the unlimited read, the ranked modes' identity and the generic fallback, the search schema's shape refusals, the re-framed search-engine failure, each with a planted difference where the instrument needs a null check (the no-base-to-docs census is the governance project's `base-docs-census`); the plugin's own project (`plugins/storage-fts5/tests`) carries the fts5 store cases. Its `library.test.ts` proves the library's store seven and its ref interface (`data_get` and `data_emit`, the depth-8 and cycle refusals) over a fixture module on both drivers. The committed store fuzzer (`tests/drivers/store-fuzz.test.ts`) is the standing differential proof beside the fixed cases: a seeded write sequence over both stores, every answer and every read compared byte for byte, a run that writes nothing reading as an instrument blind rather than SAME, and a planted extra byte on the fts5 list reading DIFF; its unit-shaped profile drives the store calls the unit module makes (unit keys, prefix lists, multi-put batches of record-sized values).

#### Exit tiers, atomicity, and interruption

Every function answers in three tiers: `0` success; `1` a semantic refusal (the input or a record rule); `2` a storage or driver failure (driver not found, a failed handshake, an IO error, lock contention, a write the backend refused). A backend never prints a success answer for a write that did not land: a replace the store refuses removes its temp and exits 2 `ERR_STORAGE_WRITE`. Each write function lands whole or not at all: the unit module reads the unit under its unit lock, stages every artifact the write changes, and lands them through one `store.batch` (posix: a temp file and a rename per key under the namespace lock, and an undo log: every file a step replaces or removes is first hard-linked into the stage, so a failed rename or removal rolls every earlier step of the batch back before the call exits 2 `ERR_STORAGE_WRITE`; fts5: one `BEGIN IMMEDIATE` transaction), and concurrent writers of one unit serialize. An interrupted call (HUP, INT, TERM) exits through its cleanup on every sh, dash included: the unit module's write removes its scratch and releases its unit lock, a store driver's call, a read included, removes the scratch files it made (each named for the cleanup the moment it exists), a posix batch interrupted among its renames is rolled back the same way, and a held namespace lock is released, while a writer interrupted as it still waits for a lock removes nothing, so the live holder keeps it; a SIGKILL cannot be trapped, so a posix batch killed among its renames can leave part of its write, but its locks are recoverable: each lock folder carries its holder pid, a waiter removes a lock whose pid is gone (`kill -0`) and proceeds, and a live holder still ends in `ERR_STORAGE_LOCKED` after 600 polls 0.1 s apart (60 s of sleep). The unit lock and each driver's namespace lock share that one wait, never a folder (the unit locks keep their own, so no unit name meets a namespace lock): the recovery clears every dead holder, so the wait only bounds a live one, busy or hung, and it is sized from measured holds so six writers queued on a 1 MB unit under load still land (the unit module's README carries the numbers). The wait is a poll, not a queue: whoever polls first after a release wins, so bursts land while writers looping without pause can starve to the bound; that bound is the accepted design, revisited if parallel writers start ending in `ERR_STORAGE_LOCKED`. An interrupted write may or may not have landed, and the exit code of an interrupted call does not say which: the fts5 driver interrupted after its `COMMIT` has landed the write though the call exits with the signal's code before its answer prints. The rule for every caller: rc 0 means the write landed; after an interrupt, any other exit means check with a read (`ctx unit board`, `entry show`, `task show`, `lane show`) before writing again, since a retried write can repeat an act that already landed.

#### Split-brain prevention

If a non-posix driver is configured (such as `fts5`) and its executable cannot be resolved or fails its handshake, the engine halts immediately with exit code 2 (`ERR_DRIVER_NOT_FOUND`, or `ERR_DRIVER_PROTOCOL` when the capability call fails or the descriptor is not a complete contract 3; a driver whose capability call refuses with its own line has that line passed through the handshake's one line, its code ending it). The engine never falls back silently to `posix` when another driver was configured, and no verb opens an artifact outside the driver, so records never diverge between storage engines. Two guards hold every verb to the driver: the governance project's static store-bypass check reads every module line that names the record store, a driver, the resolver's answer, sqlite3, or the lock area against an exact allow-list, and the pre-release SQLite smoke set (`bun run test:sqlite-smoke`, in `bun run test:prerelease`) drives every command family under fts5, so a verb re-pointed at the files turns both red. Beside them the governance drawer literal census holds the storage core and the drivers (and the engine, the composer, the package overlay, and the module roots) to the drawer layout's owners: the record root, the fts5 database name, and the lock literals appear only on their owner lines (The drawer layout, below).

#### Available drivers

- Baseline POSIX driver (`posix`): zero-dependency POSIX sh and awk driver in the storage core at `.contexture/storage/drivers/posix/`, keeping each key of a declared namespace as a file under its root (`<root>/<key><suffix>`), so the unit module's values are the record's markdown files under `.contexture/units/<unit>/`, a unit not yet moved read from `.contexture/sessions/<unit>/` (`store`, `store.promote`; no change log, `store.changes` refuses and the module's delta is its own). A module's declared data file maps its keys under its root through the store, so the module's verbs read and write the same files they always did; the module's delta stays on its own source (git under posix). It runs on the system awk, written to the common subset of BWK awk, mawk, gawk, and busybox awk (no container matrix runs; the governance awk census guards the known trap statically), and every payload and JSON encoder doubles a backslash by concatenation, since a `gsub` replacement of four backslashes yields one backslash under busybox awk and `gawk --posix` (the authoring rule in `docs/modules.md`).
- SQLite FTS5 driver (`fts5`, from the `storage-fts5` storage-driver package): a SQLite-backed store-only driver (schema 5: the generic store, its change log, and the derived store documents) holding the module data, the record among it as the unit module's values, with dual full-text indexing and the ranked modes `hybrid` and `trigram` beside `exact` (the store documents derived per key at write time from the module's declared search schema, `search.schema`); the record's typed tables left with contract 3; it needs the system sqlite3 with FTS5, ships no module file (the engine never lists it as a module), and carries no verb of its own (the v0.54.0 `ctx storage-fts5 migrate` retired); a record reaches it through the ordinary verbs and its corpus through the `ctx docs` write verbs. The [plugin README](../plugins/storage-fts5/README.md) carries adoption and needs; the [driver README](../plugins/storage-fts5/.contexture/extensions/storage/drivers/fts5/README.md) carries the schema, the SQL layout, and the store cases.

### Semantic CLI verbs

Every unit and lane verb is a thin sh script over the shared verb library (`.contexture/modules/unit/lib/verb.sh`): it checks the input shape, makes one storage call, and renders the answer through the one flattener (`lib/json.awk`) and the one renderer (`lib/render.awk`), so every backend prints the same text for the same record; `--json` prints the function's answer unchanged (compact, in the contract key order). The typed flags are the only write inputs: no verb reads a markdown block from stdin, so no markdown crosses the command interface (a lane report, the one document, travels whole; `lane create` takes the brief as one line flags and composes the recipe itself). Every verb refuses an unknown flag or an extra positional argument rc 1 (`<verb>: error: unknown option '<flag>'` or `unexpected argument '<arg>'`, `ERR_INVALID_ARGUMENT`), and every one-line value refuses an embedded newline or carriage return before any write. Every REF and REFS element a write carries (`record --ref`, `finding add`, `update`, and `supersede --ref`, `lane record --ref`, `lane create --ref`, `task add` and `update --refs`) takes one of the two pointer shapes of the laws (@record references): `<target>#<symbol>`, a `#` with text on both sides (`journal#<slug>`, `knowledge#<NAME>`, `lanes/<lane>/report#<claim>`, `<file>#<symbol>`), or a whole target path, holding a `/` and ending in a name (`lanes/<lane>/recipe`, `/abs/file`, `../x`, a repository file path, a root-level file as `./README.md`); one token, no blank, no control character, no double quote (an ASCII control byte counts as a blank, and so does a Unicode blank of the White_Space set: NEL, NBSP, U+1680, U+2000 to U+200A, U+2028, U+2029, U+202F, U+205F, U+3000); anything else (free text, an empty value, a bare word, a root-level file name without `./` or `#`, a lone `/`, `//`, a trailing `/` as in `lanes/`, `./`) refuses rc 1 before any call, naming both shapes (`<verb>: error: malformed ref '<value>': a reference is <target>#<symbol> or a whole target path holding a / and ending in a name (a root-level file as ./<file>), one token without blanks, control characters, or double quotes (ERR_INVALID_ARGUMENT)`); `###` passes (text on both sides of a `#`), as do the invisible characters that are no blank (U+200B, U+200D, the BOM, a C1 control other than NEL). The check is forward only: a legacy REF already stored reads as it stands. The record rules (a `CLOSED` unit, the status moves, repeated keys, closer targets) are the unit module's, the same under every driver: such a refusal prints the function's one fixed line, `<function>: error: <message> (<CODE>)`, with the texts of the contract above. The engine names one per-verb scratch root under the workspace drawer and exports it as `CTX_SCRATCH_ROOT`; a verb stages its scratch inside it and removes it on return, and the next dispatch sweeps a root whose holder pid is gone (a SIGKILLed verb).

#### Task operations: ctx unit task
- `ctx unit task add <unit> <slug> --objective="..." [--desc="..."] [--criteria="..."] [--details="..."] [--refs="..."]`: creates a `TODO` task; `--refs` takes the references blank or comma separated, brackets optional.
- `ctx unit task update <unit> <slug> [--objective="..."] [--desc="..."] [--criteria="..."] [--details="..."] [--refs="..."]`: replaces the given fields (an empty value leaves its field as it is); `--refs` replaces the list and `--refs=""` clears it. The flags are its only input (stdin is not read): an update carrying no field refuses rc 1 `ERR_INVALID_ARGUMENT` before any driver call. The task is stored in its canonical lines from its fields (a legacy task too, every value it holds kept, its extra fields, head text, and extra lines among them); every other item keeps its bytes.
- `ctx unit task start <unit> <slug>`: moves a `TODO` task to `IN_PROGRESS`; the state is not written, since the next move is derived from the backlog at presentation. An extra argument, `--pointer` included, refuses rc 1.
- `ctx unit task complete <unit> <slug> --evidence="..."`: moves a `TODO` or `IN_PROGRESS` task to `DONE` and appends its receipt entry in the same write: slug `<date>-<slug>-completed` (a same-day repeat takes `-1`), `WHAT: "backlog/<slug>: DONE (<evidence>)"`, `THREAD: none`, the current anchor.
- `ctx unit task reopen <unit> <slug>`: moves an `IN_PROGRESS` or `DONE` task back to `TODO`.
- `ctx unit task drop <unit> <slug> [--reason="..."]`: removes the task and appends its receipt (`<date>-<slug>-dropped`, `WHAT: "backlog/<slug>: DROPPED (<reason>)"`, the reason defaulting to `task dropped`) in one write; an `IN_PROGRESS` task refuses (reopen it first); the slug can be added again afterwards.
- `ctx unit task list <unit> [--status=todo|progress|done|all]`: one `  [<status>] <slug>: <objective>` line per task in backlog order; the verb maps the words to `TODO`, `IN_PROGRESS`, `DONE`, and every status and refuses another word rc 1.
- `ctx unit task show <unit> <slug> [--json]`: prints the task's canonical block (its `REFS` included, as a bracketed list; a legacy task prints canonical too, every value it holds kept, its extra fields and lines among its canonical lines, never its stored bytes); `--json` prints `task.get`'s answer.

Every other move refuses `ERR_INVALID_TRANSITION` with the task unchanged. `add`, `start`, `complete`, `reopen`, and `drop` fire the task-landing hooks (`CTX_ACT` naming the act, [Modules](modules.md)); `update` fires none. A malformed slug (letters, digits, underscore, dash; starts alphanumeric) refuses rc 1 before any driver call.

#### Journal event recording: ctx unit record
- `ctx unit record <unit> --what="..." [--group=...] [--thread=...] [--rhythm="<name> <N> <GATE>"] [--ref=...]... [--closes=...]... [--supersedes=...]... [--knowledge] [--slug=...]`: appends an immutable event. The unit module takes the unit's current anchor, composes the slug `<date>-event-<epoch>` from the date and time the verb sends (a slug the journal holds takes `-1`), and writes the canonical field order (`ANCHOR`, `WHAT`, `GROUP`, `RHYTHM`, `THREAD`, `REF`, `CLOSES`, `SUPERSEDES`, `KNOWLEDGE`). `--thread` defaults to `none`; `--rhythm` must name a step and gate of the named rhythm, checked through the rhythm module's resolve (the workspace copy first, then the installed one; the rhythm's `@rhythm` line must name its file, else `ERROR: RHYTHM <name> declares @rhythm <declared>; a rhythm's file name and its @rhythm line must agree`; a missing rhythm reads `ERROR: no such rhythm: <name> (ctx rhythm list names them)`, a missing step `ERROR: RHYTHM step <N> not in <name>`), and a stamped write prints, after `recorded entry: <slug>`, the next gate line `rhythm: <name> at <N> <GATE>; next gate: <N+1> <GATE>: <outcome>` (at the last step `rhythm: <name> at <N> <GATE>, its last gate`); `--ref`, `--closes`, and `--supersedes` repeat, one line each. A closer takes only the explicit form `<slug> (<verdict>: <reason>)`: one or more date-slug targets, then the parenthesis with a verdict of `done`, `superseded`, `dropped`, or `folded` and a non-empty reason holding no parenthesis (the law puts the resolution in the closer, so nothing is copied from the WHAT); a bare target list, a missing or unknown verdict, an empty reason, or text after the parenthesis refuses rc 1 `ERR_INVALID_ARGUMENT` naming that form (`record: error: --closes takes <slug> (<verdict>: <reason>) ...`), and a reason holding a parenthesis refuses naming the rule (`a closer reason holds no parenthesis`), before any write. Every closer target must name an entry the journal already holds, else rc 1 and nothing is written. `--slug` takes today's date as a prefix when it carries none and refuses a slug the journal holds.

#### Journal entry inspection: ctx unit entry
- `ctx unit entry show <unit> <slug> [--json]`: prints the entry's canonical block (`REF`, `CLOSES`, `SUPERSEDES`, `RHYTHM`, and `KNOWLEDGE` included; the last occurrence of a repeated legacy slug); `--json` prints `entry.get`'s answer, the closure (`closed`, `closed_by`, `close_reason`) derived by position: the first later closer naming the occurrence.
- `ctx unit entry list <unit> [--anchor=A<N>] [--group=<token>] [--json]`: one `  [<anchor>] <slug>: <what>` line per entry occurrence in journal order, open or closed; `--group` is the topic thread across anchors, `--anchor` one period; the unit module filters by the exact values, so the text and the JSON agree.
- `ctx unit entry closure <unit> <slug> [--json]`: `closure <unit> <slug>: open`, or `closed (<verdict>)` with the first closer's verdict, then per closer an empty line, `closer <slug> (<anchor>)`, and the closer's line; positional, so only a closer standing after the entry counts; an absent slug refuses rc 1.

#### Finding lifecycle CRUD: ctx unit finding
- `ctx unit finding add <unit> <NAME> --summary="..." [--ref=...]... [--supersedes=...]`: adds a finding; a new NAME is upper case letters, digits, and underscores, a NAME the knowledge carries refuses rc 1 (`ERR_ENTITY_EXISTS`), and a `--supersedes` predecessor must exist.
- `ctx unit finding show <unit> <NAME> [--json]`: prints the finding's canonical block, with `SUPERSEDED_BY: <successor>` after its head line when a later finding supersedes it.
- `ctx unit finding update <unit> <NAME> [--summary="..."] [--ref=...]...`: replaces the summary, the references, or both (either flag alone works); `--ref` replaces the whole list; stdin is not read, and an update carrying no field (an empty `--summary` alone included) refuses rc 1 `ERR_INVALID_ARGUMENT`. The finding is stored in its canonical lines from its fields (`SUPERSEDES`, `REF`, `SUMMARY`, then any extra field), a legacy finding too, every value kept; every other item keeps its bytes.
- `ctx unit finding supersede <unit> <old-name> <new-name> --summary="..." [--ref=...]...`: records forward-only supersession; a missing predecessor or a held successor NAME refuses rc 1.
- `ctx unit finding drop <unit> <NAME>`: removes an invalidated finding.
- `ctx unit finding list <unit> [--active-only] [--json]`: one `  <NAME>: <summary>` line per finding, `--active-only` leaving out every finding a `SUPERSEDES` names.

Every finding write refuses a `CLOSED` unit.

#### Universal search: ctx unit search
- `ctx unit search <unit> "<query>" --mode=MODE [--limit=N] [--entity=TYPE] [--json]`: searches across all entity domains. Every driver returns one shape: `{"unit","query","mode","total_matches","results":[...]}`, each result carrying `entity_type` (session, task, entry, finding, lane, lane_entry), `entity_id`, `section` (the artifact the hit came from: state, backlog, knowledge, journal, lane_recipe, lane_journal, lane_report), `snippet`, and `score` (0 for every exact result; a ranked mode's own number, higher is better). `total_matches` counts every result before the cap, `--limit` caps the results (default 20), `--entity` keeps one entity type (`all` for every one). `--mode` is required and has no default: a search without it refuses rc 1 `ERR_INVALID_ARGUMENT` before any call, naming the modes the configured driver declares (read from its descriptor; `ctx unit diagnose` lists them too). `exact` means one thing on every driver: a line of the record text matches when it carries the query as a substring, ASCII letters compared without case (every other byte matches exactly) and a column-0 comment never matching; the result is one row per matching entity and section (a task matching on three lines is one row), in record order (state, backlog, knowledge, journal, then each lane's recipe, journal, report), its snippet the first matching line with its field label and quotes trimmed, and `total_matches` counts those rows. A ranked mode is a driver's own, asked for by the name its descriptor declares (the fts5 driver's are in its paragraph under Available drivers); a mode the driver does not declare refuses rc 1 `ERR_CAPABILITY_UNSUPPORTED` naming its declared modes (posix declares `exact` alone). An empty query refuses rc 1 `ERR_INVALID_ARGUMENT`. The text view prints a count line and one line per result; `--json` prints the answer.

#### Reference resolution: ctx unit resolve
- `ctx unit resolve <unit> <ref> [--json]`: resolves abstract domain references (`task#slug`, `entry#slug`, `finding#NAME`, and the lane shape `lane#<lane>/<recipe|journal|report>[#<claim>]`), the legacy lane form `lanes/<lane>/<recipe|journal|report>[#<claim>]`, the canonical unit refs (`unit#<unit>/task/<slug>`, `unit#<unit>/entry/<slug>`, `unit#<unit>/finding/<NAME>`, `unit#<unit>/lane/<lane>/<recipe|journal|report>`; a canonical ref carries its own target unit), and the legacy file forms (`backlog.md#slug`, `journal.md#slug`, `knowledge.md#NAME`, `lanes/<lane>/report.md#claim`) on every driver. Base parses the reference and makes exactly one call (`task.get`, `entry.get`, `finding.get`, or `lane.get`); the text view prints the item's span (its canonical lines, its trailing separator included); a recipe or report claim is cut from the last head naming it, an `@<claim>` or `@claim <claim>` line running to the next column-0 `@` line, a column-0 `<KEY> ::` line, its text on that line or its body below (trailing blanks ignored), to the next non-blank column-0 line, blank lines kept; a journal claim names a lane journal entry slug and prints the span of the last entry carrying it, as `ctx lane show` prints that entry; a claim on any other artifact name is an unsupported form; a whole lane artifact, in any of the three shapes, prints byte for byte what `ctx lane show` prints, and an absent recipe or report refuses rc 1 as a miss in both views (`ctx lane show` keeps its one empty line); `--json` prints the function's answer. A miss refuses rc 1 (`resolve: error: reference '<ref>' not found in unit '<unit>' (ERR_ENTITY_NOT_FOUND)`), an unsupported form rc 1 `ERR_INVALID_ARGUMENT`.

#### The named looks: ctx unit list and refs-to
- `ctx unit list [--active|--all] [--repo=<repo>]`: the default and `--active` print each ACTIVE unit bytewise by name, its slug, `current_anchor`, derived `next:` line, and objective lines, a blank line between units, then `closed: <n>`; `--all` prints one line per unit, ACTIVE and CLOSED, `<slug> [<STATUS>] <current_anchor>`, the status as stored; `--repo=<repo>` keeps the units whose repos name the repo in either form (the `--active` closed count then counting the CLOSED units touching it), and a repo no unit touches refuses rc 1 naming the repos the units know; a store not created yet prints `no units yet` whatever the flags; `--active` with `--all`, a repeated flag, an empty `--repo`, any other flag (`--json` among them), or an argument refuses rc 1 with the usage; a refusal prints its line alone, never the deprecation warning. The retired `active` and `units` verbs of `ctx unit` each refuse rc 1 as an unknown verb, and `list` takes their place among the reserved module names.
- `ctx unit refs-to <unit> [--json]`: `refs-to <unit>: <n> units`, then one `  <unit>` line per unit whose `ref_sessions` name it; none refuses rc 1.

Together with `entry show`, `entry list`, `entry closure`, `finding show`, and `resolve`, these answer the foreseeable questions over the record in bounded form, so no one improvises a grep that over-reads: every miss is loud, rc 1 with a named error, never a plausible empty.

### Subagent lane management: ctx lane

Subagent operations are governed through the dedicated top-level `ctx lane` module:

```bash
.contexture/ctx lane create <unit> <lane-slug> --goal="..." --branch="..." --writes="..." --scope="..."... --report="..."... [--ref=...]... [--task=backlog#<slug>]... [--decision=journal#<slug>]... [--rhythm="<name> <N> <GATE>"] [--fact="..."]... [--substrate="..."]
.contexture/ctx lane show <unit> <lane-slug> [recipe|journal|report] [--json]
.contexture/ctx lane record <unit> <lane-slug> --what="..." [--slug=...] [--thread=...] [--ref=...]...
.contexture/ctx lane report <unit> <lane-slug> [--body="..." | stdin] [--json]
```

- `create`: the dispatcher's act: the verb composes the recipe from the brief flags (the five required ones, `--goal`, `--branch`, `--writes`, `--scope`, and `--report`, the last two repeatable, and the optional `--ref`, `--task`, `--decision`, `--rhythm`, `--fact`, and `--substrate`, each as `--name=value` or `--name value`), writes the fixed `BOUNDARY`, `BOOT`, `JOURNAL`, and `REPORT` blocks from its own text, stores the recipe with an empty lane journal (`lane.create`, the composed recipe its one document), and prints `lane created: <lane> in <unit>`, an empty line, the label line, and the three line dispatch prompt, which is never stored. It never reads stdin. Before its one storage call it refuses rc 1 with one stderr line: the missing required flags in one line naming each with its purpose (`lane create: error: missing --goal (...), --scope (...); the brief comes only as flags, stdin is never read: ctx lane help create (ERR_INVALID_ARGUMENT)`), an empty value counting as missing; an empty `--ref`, `--task`, or `--decision`, refused as malformed like every other REF write; an unknown flag or an extra argument; a trailing flag with no value; a single flag given twice; a value holding a newline or a carriage return; a value that is not valid UTF-8 (`lane create: error: <flag> is not valid UTF-8`); a malformed unit, lane, ref, task (`backlog#<slug>`), or decision (`journal#<slug>`); and a rhythm by the rule `ctx unit record` checks it by, with its refusal lines. No task, entry, or ref is looked up. An existing lane refuses rc 1 (`ERR_ENTITY_EXISTS`) with its recipe unchanged. The recipe lands through this command, never as a file the dispatcher writes.
- `show`: prints the recipe, the journal, or the report (the report by default) as stored, its trailing newlines collapsed to one; an absent document prints one empty line rc 0.
- `record`: logs action traces into the subagent's lane journal; the unit module composes the slug from the date and time the verb sends, a second event in the same second taking `-1`; a given slug the lane journal carries refuses rc 1; `--ref` repeats; an absent lane refuses rc 1.
- `report`: writes the lane report from `--body` or stdin, printing one line with the stored size (`lane report written: <lane> in <unit> (<bytes> bytes)`), or reads it back when neither is given; the body reaches the unit module raw on stdin and the store as one value, so a report of any size lands (a 2 MB report is a gate case). With no `--body`, it reads stdin whenever stdin is not a terminal, and no POSIX sh tells an idle open pipe from a slow writer, so under an open pipe it waits until the writer closes. The scripted read path is `ctx lane show <unit> <lane-slug> report`, which never reads stdin; `report`'s read mode is for a terminal (or a call fed `</dev/null`).

A refusal the shared verb library prints for a lane verb (a value or a document that is not valid UTF-8, a NUL byte, a missing unit module data script) names the verb as its own refusals do (`lane <verb>: error: ...`). Every lane write refuses a `CLOSED` unit with rc 1, and a report holding a NUL byte or bytes that are not valid UTF-8 refuses rc 1 (`lane report: error: the report holds a NUL byte (ERR_INVALID_ARGUMENT)`, or `is not valid UTF-8`) before any write: the document lands in a file before any other read, so a NUL is refused rather than dropped. `--json` prints `lane.get`'s answer for a read (`content` holds the document) and `lane.write_report`'s for a write.

Isolating lane operations into `ctx lane` prevents accidental pollution of the unit's main journal upon argument omission.

### ctx unit load: the load and the refs form

Returns the map plus one page of the load: state, backlog, knowledge, the live journal, and any declared `ref_sessions` under read-only banners. The unit module answers the unit whole over the store (`session.load`, or `session.refload` for the refs form) and base renders and pages it. The map names each section with its line count and pages, then the write-scope trailer, which names the unit (`WRITE SCOPE: unit <unit> + repos: [...]`), never a storage location; pages cut at block boundaries, never mid-body: a page ends before the block that would pass about 500 lines or about 40KB, whichever binds first, and a single block larger than the budget renders whole on its own page. The backlog section renders its DONE task blocks compactly, keeping only the task line, `STATUS`, `OBJECTIVE`, and `DESCRIPTION`; open and statusless blocks render whole, and the record itself is never edited, so the full body stays one `resolve` away. An incomplete call opens with `LOAD INCOMPLETE` and instructs the next call in its last line; the final page opens with `LOAD COMPLETE` and hands off to stamping the new period (`stamp the new period: ctx unit stamp <unit>`).

```bash
.contexture/ctx unit load <unit>
.contexture/ctx unit load refs <ref_1> ... <ref_N> [<page>]
```

Read every page the map reports. A missing state is fatal (`ERROR: missing state: unit <unit>`); a missing backlog, knowledge, or journal is loud and nonfatal, with a placeholder standing in its section; the warning names the artifact and its unit (`WARNING: missing knowledge: unit <unit>`), never a storage location, so a reference unit the configured store does not hold reads the same under every driver. Every verb message follows that form: an error or warning names the artifact and its unit (`<artifact>: unit <unit>`, a lane artifact as `lane <lane> <artifact>: unit <unit>`), never a record path, whatever the driver. The journal section renders the board from the same answer, so the extraction has one home; the board's open threads and open tasks ride that section unchanged.

The cut is budgeted twice, about 500 lines or about 40KB, whichever binds first, so a page stays under the harness's output cap in practice; the one residual is a single block that exceeds the budget alone, and it renders whole on its own page. If a harness still truncates such a page, it prints a notice naming its saved copy of the command's output: that copy is the command's own output, and reading it is sanctioned by `@laws#workspace-confinement`, read-only, that named file alone. Routing the same content through temp files stays unsanctioned. The in-workspace fallbacks need nothing outside: `ctx unit board`, `ctx unit task show`, and `ctx unit resolve` recover the same content through the verbs.

The refs form is the on-demand consult: it streams the named units alone, each composed exactly as the unit load composes a reference, and pages them locally with its own map, banner, and tail, so a large reference never truncates. A missing ref is fatal; zero refs, or a numeric token in a ref position, prints the usage at rc 1; a unit named `refs` stays reachable through the escape hatch `ctx unit load refs refs`.

### ctx unit stamp: the new period

The unit module moves `current_anchor` from `A<N>` to `A<N+1>` and appends the anchor line `@anchor A<N+1> <date>` (today's date, which the verb sends) in one atomic write (`session.stamp`); the verb prints the transition after the stamp hooks. The anchor carries the period's number and date, no receipt text: a text argument refuses rc 1 `ERR_INVALID_ARGUMENT` naming the form (`stamp: error: stamp takes the unit alone (ctx unit stamp <unit>) ...`), a `CLOSED` unit rc 1, and a malformed stored anchor rc 2 (`ERR_STORAGE_CORRUPT`), with no partial write. An anchor written by an earlier release with its receipt text (`("continues A<N-1>", attention: ...)`) keeps that text as content and reads back as stored.

```bash
.contexture/ctx unit stamp <unit>
```

`.contexture/ctx unit entry list <unit> --anchor=A<N>` lists the entries written in one period; `entry list` without a filter prints every entry with its anchor, the map of periods.

### ctx unit board: the board

Returns the live board: every unclosed entry with its body whole, then the open task slugs and the open threads with their targets, each list under its nudge line; an empty list prints nothing. Live means unclosed: the set is the journal entries that no later closure names. Takes one form, a unit slug:

```bash
.contexture/ctx unit board <unit>
```

The unit module answers the board (`session.board`): the live entry occurrences in journal order with their spans, the backlog slugs whose status is not DONE, and the live threaded entries; base renders them under the opener that names the counts, and a missing backlog is loud on stderr with no tail. Liveness is positional: a closer closes the occurrences of each target slug that stand before it, and the closure parse reads the target field only, so a slug mentioned in a closure's reason prose can never close anything. The output is the set, whole, with no hand-picking and no per-entry reads. Any other invocation of `ctx unit board` fails loudly: a path, an extra argument, or a flag.

`ctx unit load` renders this board for the load's journal section; run directly, `ctx unit board` is the updated board: the open entries, the open threads, and the open tasks in one stream. The refs form renders the board per reference unit, so a consulted unit streams its live entries too.

The board ends with the rhythm in force line, the line `ctx rhythm current <unit>` prints, at no added dispatch: `session.board`, which already reads the whole journal, also answers the unit's last stamp in record order, open or closed (`rhythm`: its slug and stamp, null when none), and the board verb turns it into the line through the rhythm module's resolve, run by path after the render, never a nested ctx call or a second entry listing. So a board served from the deprecated root still prints one warning, a board run outside ctx keeps a silent stderr, and with the rhythm module absent the board prints its view alone. `ctx unit refresh` carries the line through the board; the load's journal page renders the board view without it, since the load reaches the rhythm in force one boot step later through `ctx rhythm current`.

### The state acts: refs, close, reopen

```bash
.contexture/ctx unit refs <unit> [<unit> ...]
.contexture/ctx unit close <unit>
.contexture/ctx unit reopen <unit>
```

The next move is not a state act: `ctx unit list` derives it from the backlog (the first `IN_PROGRESS` task, else the first open task, the board's rule of every status but `DONE`; a legacy or unknown status reads as stored), and the load's backlog page carries it, so no verb stores a pointer and `ctx unit next` retired (below). `refs` sets the read-only mounts; every named unit must exist and differ from the unit, no name twice; zero units clears them. `close` marks the unit `CLOSED`: the unit module answers the unit's audit and its open tasks with the move, base prints them as warnings on stderr (it never refuses for them), then the close hooks fire. `reopen` marks a `CLOSED` unit `ACTIVE` again so its work can resume; each refuses a unit already in the target status (`ERR_INVALID_TRANSITION`). Every form validates its inputs before any write: a refusal is loud, rc 1 with zero partial writes, and a landing prints what it wrote.

### Retired verbs

`append`, `amend`, `query`, `flip`, and `drop` left `ctx unit` in v0.55.0 with the record contract, since no markdown crosses the interface and every act has its typed verb; `next` left when the pointer became a presentation-time derivation, since it had nothing to write. The names stay reserved (no module may claim them), and each call, or `ctx unit help <name>`, prints its replacement with rc 1:

| retired | its replacement |
|---|---|
| `append` | `record`, `task add`, `finding add` |
| `amend` | `task update` |
| `query` | `entry show`, `entry list` (`--group`, `--anchor`), `entry closure`, `finding show`, `resolve`, `search`, `list`, `refs-to`, `lane show` |
| `flip` | `task start`, `complete`, `reopen` |
| `drop` | `task drop` |
| `next` | `list` (the next task is derived from the backlog) |

The raw block stdin inputs of `record`, `task add` and `update`, `finding add` and `update`, and `ctx lane record` retired with them.

### Moving a record between backends

No command moves a record between storage backends, since a move can need judgment a verb would hide (legacy shapes only a posix file holds, files outside the record, a write one backend refuses and another accepts). A record reaches another backend through the agent re-entering it with the ordinary verbs under that backend (`bootstrap`, `task add` and its moves, `finding add` and `supersede`, `record`, `stamp`, `lane create`, `lane record`, `lane report`), and a docs corpus through the `ctx docs` write verbs; switching `storage.driver` stays the human's act. So an fts5 store holds only what the verbs write, and legacy record shapes live in posix files alone. `unit.export`, `unit.import`, and the dump format, added while v0.55.0 was built and never released, left the contract before it shipped. Today's `ctx unit migrate` is no backend move: it moves units between the declared roots of the one posix store (below, The record root and its deprecated root), and its backend flags are no unit and refuse rc 1.

### The record root and its deprecated root

The record lives under `.contexture/units/`; releases before the move kept it under `.contexture/sessions/`, which the unit module now declares as its fallback root. The move is gradual and needs no step of its own: the posix store reads a unit from the root first and then from the fallback, and its own write (the unit module's one `store.batch`) moves the unit's folder from the fallback to the root by one rename under the namespace lock it already holds, before it writes, so a unit moves whole at its first landing write, usually the boot stamp, and a write stays the one store call it was before the move; a refused write and every write to a CLOSED unit move nothing, and a unit both roots hold refuses the write with nothing written. The move that empties the fallback root removes `.contexture/sessions/` in the same call (one `rmdir`, which refuses silently while any folder or file remains, so a root still holding one stays). A run whose reads came from the fallback and that ends rc 0 prints, after its answer, one line, `WARNING: the record was read from its deprecated root; each unit moves at its next write, and ctx unit migrate --all moves the rest when the human chooses`, which every verb relays (audit, board, and diagnose among them); a refusing run prints its refusal alone. The line is a reminder, not an instruction to an agent: the sweep is the human's choice. `ctx unit migrate <unit>...` or `ctx unit migrate --all` sweeps the units nobody writes, the closed ones among them: it prints `migrated: <n>` (a second run `migrated: 0`), stops at its first refusal naming the unit, removes the deprecated root once it is empty, even when it moves nothing (a fully moved workspace keeps no empty `.contexture/sessions/`, while a store holding no unit keeps its empty root, the sweep then promoting nothing), and under a store that keeps no fallback root (fts5) prints that nothing moves. The fallback read, the promotion, and the sweep are temporary; a later release retires them once no unit remains under the old root. The fts5 database keeps its name, `.contexture/sessions.db`.

### ctx unit diagnose: the storage view

`ctx unit diagnose [--json]` prints the workspace root, the configuration, the resolved storage driver with its source and status, then the driver's descriptor as lines (`contract`, `driver`, the version, the store function count, the declared search modes, the optional capabilities), the storage health (`storage.health unit`: the backend alone, over the unit namespace's own store and lock, so a docs write never reads as a locked record; a probe that cannot answer prints `error` with the store absent), and the ACTIVE unit count from the record's own listing (`session.list`), never from the health answer; a listing that refuses leaves the count unknown, never 0: the line reads `active units: unknown (<message>)`, carrying the listing's refusal message and code (for example `unknown (cannot read key '<unit>/state' in namespace 'unit' (ERR_STORAGE_READ))`), and nothing reaches stderr. `--json` prints one compact object `{workspace_root, config {status, driver}, driver {name, source, status, descriptor}, storage {health, detail, store, active_units}}`, the descriptor being the capability answer and `active_units` the record's count, `null` when the listing refused. Every line prints whatever a read answered, a part it could not read named in its own line (a driver error, a health error, an unknown count), and diagnose exits 0; an unrecognized option exits 1, and a missing storage resolver or scratch folder 2. The descriptor is read through the resolver's handshake, afresh on every call.

### ctx unit audit: the repair instrument

Returns the record's defects, each flagged with a line or a slug, and exits nonzero when any fires. Takes one form, a unit slug:

```bash
.contexture/ctx unit audit <unit>
```

The unit module checks the record (`session.audit`) over the stored values and answers its findings as data; base prints them in a fixed order (the line-ordered grammar group first, then each record check ordered by position), so the output never depends on an awk's hash order. The record checks (dangling closer, unharvested knowledge, done without event, missing thread, the legacy duplicate warning) and the grammar checks (dateless slug, inline marker, bracketed field, slugless closer) run alike under every driver, the grammar checks finding broken text only a posix store can hold (a hand edit or a legacy file), and a finding that stands on a journal line prints its ` at line <n>`, the line of the stored journal value, under every driver. When the run is clean the verb also prints the open-thread tail: the entries whose `THREAD` names an act outside the unit and that no later closure names, each with its target. The tail is a display, never an enforcement: a thread that pauses stays open, and its line in the tail is the reminder it exists. The presence check runs from the enforcement era: an entry dated at or after `2026-09-18` that carries no `THREAD` line flags `MISSING THREAD` (the constant lives in the unit module's audit), so pre-era records stay quiet.

A task whose status is a legacy or unknown spelling is open by the board's rule (every status but `DONE`) and the derived next reads it, so the audit neither flags nor normalizes it.

The classes, and what each one asks for:

| flag | the defect | the repair |
|---|---|---|
| dangling closer | a `CLOSES:` or `SUPERSEDES:` names a slug no entry carries | the human's edit of the slug or the closer |
| slugless closer | a closer carries no valid date-slug target | the human's edit, pointing it at real entries |
| dateless entry slug | an entry name does not match the date-slug grammar | the human's edit of the entry's slug to the date-slug grammar |
| inline marker | `THREAD:` or `KNOWLEDGE:` sits on the `@entry` line | the human's edit, moving it to its own field line |
| bracketed field | a field line wrapped in brackets, as a shape's optional marker copied verbatim | the human's edit, writing the field bare or omitting it |
| missing thread | a post-era `@entry` with no `THREAD` line | the human's edit, declaring the `THREAD` line: what it awaits, or `none` |
| unharvested knowledge | a `KNOWLEDGE: true` entry that no closer names | harvest it at the next refresh; the entry then closes by reference |
| done without event | a `STATUS: DONE` task with no `backlog/<slug>: DONE` line in the journal | record the completion event |
| legacy duplicate slug (warning) | an older journal repeating an entry slug | nothing: it reads by position and leaves rc unchanged; a new repeat is refused at the write |

The audit is a repair instrument: fix what it flags and fill what is missing before the period ends; a note about a flag is not a repair. The verbs repair two classes: unharvested knowledge (a closer at the next refresh, `ctx unit record --closes`) and done without event (the completion event through `ctx unit record`, or `ctx unit task reopen` then `complete`, which writes the receipt). Every other class is a finding no verb can repair: it goes to the human, never to an agent's hand edit of the record or to an entry minted only to quiet it. The audit runs at refresh, close, and handoff, and close and handoff expect exit 0.

### ctx rhythm: the rhythm module

The rhythm module ships with the base in the workspace modules root, beside the lane module, and is the one surface for rhythms: an agent selects, reads, and resumes a rhythm through it and never reads a rhythm file by its path. Its three verbs:

```bash
.contexture/ctx rhythm list
.contexture/ctx rhythm show <name>
.contexture/ctx rhythm current <unit>
```

- `list`: one line per effective rhythm, `<name> | <origin> | use when: <trigger> | activation: <propose|auto>`, the workspace rhythms (`.contexture/rhythms/`) before the extension rhythms (`.contexture/extensions/rhythms/`), each in name order; a name both carry lists once, its origin reading `workspace, shadows the extension copy`. A rhythm is named by its file name; a file with no `use when:` line prints `(missing)`, and an activation the file does not state, or states as anything but `auto`, reads `propose`. The last line is the select line: a propose match is proposed and waits for the human's confirm, an auto match applies and says so, no match runs the design loop, and `ctx rhythm show <name>` reads a rhythm. Each grammar defect of a listed rhythm warns on stderr (`rhythm list: warning: <name> (<origin>): <defect>`) and the rhythm still lists; a file holding no `@rhythm` line is no rhythm and warns that it holds none. Two absent roots print the select line alone rc 0: the base payload ships no rhythms, and a workspace may carry none, so a bare base-only install completes its boot step. An argument refuses rc 1 with the usage.
- `show <name>`: the effective copy byte for byte (the workspace copy when it shadows an installed one), then the stamp line, `stamp: ctx unit record <unit> --rhythm="<name> <N> <GATE>" on each entry that advances this rhythm`; an unknown name refuses rc 1 (`ERR_ENTITY_NOT_FOUND`), and a name failing the slug rule (a slash, a leading dot) refuses rc 1 before any file is read (`ERR_INVALID_ARGUMENT`).
- `current <unit>`: one line from the unit's last stamped entry in record order, open or closed, read from `ctx unit entry list <unit> --json` through the unit module's `lib/json.awk`, never a search snippet: `rhythm in force: <name> at <N> <GATE> (entry <slug>); next gate: <N+1> <GATE>: <outcome>`, `rhythm completed: <name> at its last gate <N> <GATE> (entry <slug>)`, `rhythm stale: <stamp> (entry <slug>) matches no step of the effective rhythm; read it: ctx rhythm show <name>` (a step that no longer reads its gate, a rhythm that no longer resolves, or a legacy stamp of another shape), or `rhythm none in force in <unit>: the design loop runs until the human confirms a rhythm (ctx rhythm list)`. A malformed unit refuses rc 1 before any read; a missing unit refuses with the listing's own line, and a unit served from the deprecated root prints its line with the one warning.

The module's one rule lives in its private `scripts/resolve`, which carries no summary line, so ctx never lists or dispatches it: the verbs run it by path, the unit verb library runs it by path (found as it finds the storage resolver) for the stamp check of `ctx unit record` and `ctx lane create` and for the board's closing line, and the governance grammar census reaches it through `ctx rhythm list`. It reads the two rhythm roots of the drawer it sits in and answers tab separated lines: the origin, whether the copy shadows the other root, the declared `@rhythm` name, the use when and activation values, one line per step (number, gate, outcome), and one line per grammar defect. The grammar: a step line is any line opening with a number, a dot, and a blank, its gate the text before the first colon in `[A-Z][A-Z_+]*`, the steps numbered 1 to N; the defects are a missing use when line, an activation neither propose nor auto, an `@rhythm` name that is not the file name, a break in the numbering, a gate outside the stamp grammar (counted once, never also as a gap), and no step line. Each verb answers a sole `--help` or `-h` with the table `ctx rhythm help <verb>` prints. The module holds no laws file (the `@rhythms` law stays in the core) and no data file (it reads no store).

### ctx unit fold: the consolidation fold

`ctx unit fold` is one stateless verb over the record; the command keeps no cursor, file, config, or table. The record is the state: a fold start entry (the plan JSON, the carried threads, and the batch rule), the lanes' ordinary consolidated entries, and the finish receipt. The consolidated entry is a normal journal entry: the `WHAT` is the batch's synthesis, the `REF` lines name every constituent (the carried open threads included) plus any external report, and the `CLOSES` lines fold the same constituents except the open threads. A fold compacts history, never obligations: open threads stay live and are carried.

```bash
.contexture/ctx unit fold <unit>                 # plan (first call) or progress
.contexture/ctx unit fold <unit> --lane=<lane>   # fetch: the next batch, its entries, the lane's remaining chunks, and the next act
.contexture/ctx unit fold <unit> --lane=<lane> --merge   # the same fetch plus the immediately following chunk's entries, the only merge partner
.contexture/ctx unit fold <unit> --check         # the read-only coverage, partition, and audit check
.contexture/ctx unit fold <unit> --finish        # the receipt; the fold start closed done
```

The first no-lane call computes the live scope of the unit (every live entry at that call), partitions it once into chunks in journal order at the mechanical seams (task receipts, releases, decisions, part and lane series, group switches), coalesces the mechanical series, splits any chunk still over 12 constituents at the last seam in its first 12 (or at the last entry with `(cap split: no seam)` recorded), records the fold start, and prints the plan with the carried open threads listed, the first lane's `ctx lane create` command and its manual, and the first act. The open threads stay in the scope and in the chunks. A chunk ends at the next semantic milestone (`TASK_DONE`, `RELEASE`, `DECIDE`, `HANDOFF`, `PERIOD_CLOSE`, `HARVEST`, `LANE_REPORT`, `HUMAN`); the live entries after the last milestone are one `TAIL` chunk; an anchor with no milestone is one `ANCHOR` chunk. Each anchor's chunks share a deterministic lane (`fold-<epoch>-<n>`); the orchestrator creates each lane with the `ctx lane create` command the plan and the progress print. A fetch returns the lane's next unclosed chunk, its entries, the lane's remaining chunks (never another chunk's entries), and the next act, and never advances; a `--merge` fetch adds the immediately following chunk's entries, the one permitted merge partner; at a lane boundary it returns the next lane's instruction instead. The lane writes one ordinary entry with `ctx unit record`; the command does not write it. A merge covers only that next chunk and records its same-topic reason in the `WHAT` as `(merged: <reason>)`; the check refuses a whole-anchor batch. A carried open thread is `REF`'d as context and never closed. `--check` reads the fold start's plan and the live post-plan entries: a consolidated entry is a live entry whose `CLOSES` target scoped slugs; its closer set is the batch. A scoped live entry carrying `THREAD` other than none is carried, never `SCOPED_LIVE`. Every target must be in the scope and carry a `journal#<slug>` REF, every closer must be `folded` with a reason, the batches must partition the scope into whole consecutive chunks in one lane, every batch `REF`s the carried threads in its chunks, the closed receipts are the scope minus the carried threads, and the audit must be clean (its open-thread tail prints); the defect classes are named in docs/the-record.md. `--finish` re-runs the check and, when clean, writes the receipt `FOLD FINISH v4 <fold-start> batches=<b> covered=<n> carried=<m> open threads :: coverage zero; audit clean` and closes the fold start done; the carried threads stay live and a live receipt refuses a second one. The command reads and writes only through the existing record operations (`session.board`, `entry.get`, `entry.record`, `session.audit`, and `lane.get` for the lane names); the storage SPI is unchanged. The operational protocol and the synthesis standard live in docs/the-record.md; the plan call prints the lane manual, and `ctx unit fold --help` prints the command manual.

### One audit per grammar

The runtime and the built-in modules are payload instruments, shipped with the convention and identical everywhere. A unit can also carry an audit of its own for a grammar the payload does not know yet; the unit's bank audit is the precedent. It stays unit-local until its grammar proves generic, then it can promote to the payload as a sibling. The separation is deliberate: no experimental checks inside a shipped script, and each audit derives its siblings rather than being handed their paths. Refresh and handoff run every audit in play, and the receipt carries the results.

## The completeness loop

The loop is what the machinery does with the record: it makes gaps visible at fixed points and demands repair instead of notes. Taking the stations in the order a unit meets them:

- **Boot** runs `ctx unit list` and `ctx rhythm list` for the proposal, then `ctx unit load` and `ctx rhythm current`. The load is the subtraction, not a judgment call, so the agent pays for what is open and nothing else; the rhythm in force names where the process stood.
- **Work** journals events as they happen and flags knowledge-worthy entries where they land. The flag is the harvest's input; nothing needs to be collected later.
- **Refresh** runs at every rhythm boundary and inside close. It sweeps the artifacts: events journaled, backlog statuses advanced, the derived move read from the backlog. It runs the harvest: every open flag, one candidate each; a candidate that meets the bar lands in knowledge and its entry closes by reference, and a candidate that does not drops. Then it runs the audit, and what it flags is fixed.
- **Close** closes the period's done events by reference and requires the audit to exit 0.
- **Handoff** runs before context death, whether that is a compaction, a tool change, or a long break. The period-end writes run if they are not done, then the bounded cold read: run `ctx unit load` and read the map and the state page, the backlog section with its open tasks whole, the journal's tail (this period's entries), and the knowledge tail when this period landed findings; the full-body pass belongs to the next boot, a fresh context. While the context is still full, improve the quality and fix what was missed; the gaps close now, never after compaction. `ctx unit audit` exits 0.

Why this holds together:

- The record is append-only and schema-driven, so "missing" is a mechanical fact rather than a memory test: an absent closer, an unrecorded done event, a task absent from the board are all visible to a small script.
- The checks run at fixed points, and they are cheap: a few awk commands, no model tokens, the same answer every time. Frequency is the point; the open-flag sweep at each refresh is the check, not a rare batch at the end. When harvesting waited for period end, older flags slipped past every close.
- An instrument earns trust by failing on the defect it guards. A check that returns the same answer whether or not the failure is present proves nothing, so the instruments are proved against planted defects before they are trusted, and a green run means exactly the classes it checks are clean. It is never a claim that the record is complete.

## The drawer layout

Everything the convention installs or uses lives under `.contexture/`, except the files that sit at the repository root: the loader a harness must find there, the overlays, and the generated law layer beside them:

```text
AGENTS.md            the loader: compose or verify, then load the generated layer whole; delivered every turn
AGENTS.workspace.md  the shared overlay
AGENTS.local.md      your amendments
AGENTS.generated.md  the generated law layer: composed by ctx compose at install and boot; gitignored, never edited
plugins/             the tracked catalog of packaged overlays: copied into a workspace when wanted
.contexture/
  ONBOARDING.md      the adoption guideline (removed when the adoption closes)
  ctx                the runtime: discovery, help assembly, dispatch, the run engine, and hooks
  package-install    the package overlay installer, private behind ctx package install: overlays a package's .contexture/extensions tree, records it, runs the part hooks
  package-uninstall  the package overlay remover, private behind ctx package uninstall: runs the part hooks, removes the recorded files, preserves a changed file
  laws/              the law sources: core.md the core law source, and the composer, private behind ctx compose
  modules/           unit (the record engine), run (stream filters), lane (the subagent lanes), rhythm (the process surface), and workspace additions
  extensions/        the package overlay root: modules/ for package feature modules, storage/drivers/ for package drivers, rhythms/ for package rhythms, .state/ for the installed-path records
  rhythms/           your process patterns
  units/             the units of work (sessions/, the deprecated root, holds a unit until it moves and is removed once it is empty)
  tmp/               gitignored scratch: engines and agents prefer it over system temp (created on demand; each verb stages under its own root, removed on return and swept by the next dispatch after a kill)
```

Three drawer facts each have one owner, and the rest of the product reaches them through it. The record root and its deprecated fallback root are the unit module's data file (its `root` and `fallback_root` lines, read by the storage core's `store-data`; the posix driver maps the record's keys under the root, reads the fallback after it, moves a written unit's folder from it, and probes its health over both, and the docs module's backlog file guard lists both through the library's `store_roots`). The fts5 database's default name, `.contexture/sessions.db`, is the fts5 driver's (`storage.database` relocates it). The lock layout is the unit data script's unit lock (`locks/unit/<unit>.lock`, its `u_lock`) beside each driver's namespace lock (`store-<namespace>.lock`, its `store_lock` and `store_lock_held`), both under the drawer's scratch folder while it is writable, else under the per-user `contexture-<user>` folder in the system temp. The governance drawer literal census (`tests/governance/drawer-literals.test.ts`) refuses the record roots, the database name, and the lock literals anywhere else in the storage core, the plugin drivers, the engine, the composer, the package overlay, and the module roots; the tests read the same facts through one helper, `tests/support/drawer.ts` (the record root and the fallback root parsed from the unit module's data file), and the census refuses the literals in every other test file.

The root belongs to the harness: AGENTS.md has to sit where the harness looks for repository instructions, and the overlays and the generated law layer sit beside it. Everything else lives in the drawer. An adopting workspace keeps its own files at the root, freely; the drawer's contents are the convention's, and the two never mix. The repository that builds the convention tracks this layout mirrored under `base/` (`base/AGENTS.md`, `base/.contexture/`); its own installation at the root is untracked working state.

### One home, three classes

Placement follows the class of the file, never convenience:

| class | paths | fate |
|---|---|---|
| update payload | `base/`: the mirrored core (`base/AGENTS.md`, `base/.contexture/{ctx,package-install,package-uninstall,storage,laws,modules/lane,modules/rhythm,modules/run,modules/unit,ONBOARDING.md}`) | applied onto the live root from tags, byte for byte |
| catalog | `plugins/`: packaged overlays | copied into a workspace when wanted; never deleted at adoption close |
| live workspace | the untracked root: `AGENTS.md`, `.contexture/` (units and the deprecated sessions, rhythms, tmp, workspace-added modules) | never touched by an update |

The classes exist because the files have different lives. The payload evolves with the convention and must stay identical across every workspace: it is tracked in one mirrored tree and applied onto the live root as-is, so what the tag tracks under `base/` is exactly what lands. The catalog holds the optional overlays: a workspace installs one when it wants it, and the folder is no longer deleted at adoption close. The record (units, and the deprecated sessions folder while units remain in it), rhythms, tmp, and workspace-added modules are the workspace's own state, and no update may touch them. `.contexture/ONBOARDING.md` rides the payload as adoption material; it is used once and removed when the adoption closes.

### The sync derives from the tag

There is no manifest. `base/` is the payload: `git archive <tag> base/` copies it, `git ls-tree` enumerates it, and a comparison per file verifies it. Whatever the tag tracks under `base/` is the set; a file cannot silently join or leave the payload without changing the tag.

### The layout bounds the load

The drawer is also the context mechanism, and the reason is structural. When the agent works a unit, it reads that unit (`.contexture/units/<unit>/` under posix, through the verbs) and the convention's files it needs, never a global blob of everything. The filesystem is the index, and the folder is the boundary: no rule has to say "do not read the rest", because the layout has already said it.

The record page covers what the artifacts hold and how liveness works; units and subagents covers the container and the dispatch; rhythms covers the process layer; overlays covers the amendment grammar; adoption covers the install.
