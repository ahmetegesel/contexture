# The engine

## What the engine is

The engine is the part of contexture that runs and checks: the instruction files, the grammars, and the scripts. It is plain files and plain awk all the way down: no service, no database, no runtime.

The division of labor is deliberate. The model does the work; the machinery holds the line. A record kept by memory drifts, so the parts that must not drift are mechanical instead: the shapes are pinned in files, the searches are plain shell tools, and the checks are small scripts that run at fixed points. Quality comes from the machinery, not from the model remembering.

## The instruction files: the loader every turn

A coding harness reads its repository instruction file before it acts. In a contexture workspace `AGENTS.md` is the loader: the only file guaranteed to be in front of the agent every turn, and deliberately a few lines. Its first instruction runs `.contexture/ctx compose` (which composes or verifies the generated layer), then loads `AGENTS.generated.md` whole from the workspace root, then chains `AGENTS.workspace.md` and `AGENTS.local.md`. The second instruction frames the layer it loads: its generic sections are `@laws`, `@layout`, `@module`, `@boot`, `@interact`, `@rhythms`, `@subagents`, `@refresh`, `@close`, `@handoff`, and `@update`; every module adds its own sections, clauses, and duties, so the layer carries more than that list, and each duty is followed as steps in its framed order, gates included; the laws bind. An absent engine or a refused compose is a broken payload: the instruction stops and reports the compose's error line, which names the missing or refused path, never booting on a stale or partial layer.

The four delivery files split by ownership. `AGENTS.md` is the base loader; the generated layer is the composed law set, the core law source plus the installed modules' preambles and clauses; the workspace overlay is the shared, tracked amendment; the local file is the personal amendment. The loader is the every-turn cost, about a kilobyte; the generated layer and the overlays are boot reads. The generated layer is gitignored and built at install and boot, never edited. Measured at the v0.61.1 base: the three-file stack it replaces is 34,994 bytes every turn; the loader is 856 bytes, and the boot whole (the generated layer plus both overlays) measured 36,693 bytes with the docs module installed.

The sections below are the blocks the generated layer carries, in the order the core law source fixes:

| section | what it carries |
|---|---|
| `@laws` | the slug-addressed laws |
| `@layout` | where every file lives and what it is for |
| `@boot` | the sequence that starts every working period |
| `@record` | the artifact map: what each artifact records and why |
| `@journal` | the event workflow: formation, substance, liveness, markings |
| `@backlog` | the task workflow |
| `@query` | how the agent decides what to load |
| `@interact` | how the agent treats the human |
| `@rhythms` | the rhythm contract and the default design loop |
| `@subagents` | the dispatch contract |
| `@refresh` | the artifact sweep |
| `@close` | period end and unit close |
| `@handoff` | the proof before context death |
| `@update` | how the base evolves upstream |

The loader names the generic core sections only: `@laws`, `@layout`, `@module`, `@boot`, `@interact`, `@rhythms`, `@subagents`, `@refresh`, `@close`, `@handoff`, and `@update`. The four record sections (`@record`, `@journal`, `@backlog`, `@query`) are the unit module's framing, supplied by its laws file; each `@module` preamble belongs to its module.

The core law source fixes the block order; the installed modules' law fragments append under these keywords, and a new keyword creates a custom section after `@update`. The git package is the worked example: its laws create the `@git` section after `@update`. The module preambles stand after `@layout`, before `@boot`.

### The laws

The laws are the spine of the whole system, loaded whole at boot in the generated layer. Each law reads `slug: statement`, and a reference addresses the slug, as in `@laws#verify-before-close`. Core laws include:

- `source-of-truth`: the record is the work's durable memory, what a fresh context resumes from: the events that happened, the decisions made, and the state they left, across compaction, tool change, and break; because the work's continuity depends on it, it holds whatever else that continuity needs, the reasons, the open threads, and the evidence behind them; the workspace and the commands' results show what is, and the loaded layer and its sequences say what to do.
- `load-only-needed`: load only what the work needs; closed units stay untouched unless the task calls for them.
- `compact-streams`: all shell commands execute through the ctx runner to preserve context window capacity.
- `writer-holds-volume`: the schema holds the shape, the writer holds the volume.
- `process-free`: process is free and human-chosen; govern the output, not the process.
- `compose-from-record`: compose from the record, never from the conversation.
- `verify-before-close`: no done without evidence, and never a claim of verification not performed.
- `harvest-the-human`: durable knowledge is surfaced by question, crystallized, and landed by the agent's judgement when it meets the bar, never just to record; a candidate that does not drops.
- `workspace-confinement`: the workspace is the boundary; the agent never roams outside it.
- `cli-doorway`: the CLI (`.contexture/ctx`) is the single doorway to the runtime and the record: contracts are discovered through `ctx help`, the record is reached strictly through its ctx verbs (`ctx unit`, `ctx lane`, `ctx rhythm current`), and stderr is the diagnostic, with `--diagnose` on the engine subcommands for the runtime and storage state.
- `dont-fool-yourself`: every failure here returns something indistinguishable from a correct result, so only a mechanical check catches it; null-check the instrument (would it answer the same if the thing sought did not exist?); grep locates and reading answers; absence claims are the highest-evidence claim and license deletion; the parts must sum to the named whole; read the exit code of the command you care about; read the primary record over a derived view.

Slug addressing is what lets the set grow and the modules and overlays extend it. A positional name would force every reference to chase every insertion; a slug is stable for life, and a module or overlay can append its own laws at the end without renumbering anything. The core laws are the source's own; the docs module appends its laws and clauses, the lane module its dispatch clauses, the unit module its `sweep-consent` law beside its record clauses, the store module its store laws, the git package its git laws, and the workspace and local overlays append their own. Slugs are unique across the generated layer and both overlays; the compose refuses a duplicate at boot.

### The overlays beside it

`AGENTS.workspace.md` and `AGENTS.local.md` sit beside the loader and extend the generated layer, by section, with `@append` or `@replace`. The workspace overlay is shared and tracked with the work; the local file is personal and yields to the workspace when they disagree. Both amend; neither may contradict a law. The order is the loader, the generated layer, the workspace overlay, then the local one; the compose checks the law slugs across the generated layer and both overlays at boot, and a duplicate refuses. They have their own page; here it matters only that the generated layer plus its overlays is what the agent actually reads.

## The artifact shapes

The shapes live in the laws and the guides, never in a separate template file:

| artifact | its shape |
|---|---|
| the state, backlog, journal, and knowledge | `@record` and [The record](the-record.md); the unit verbs write them and the record audit parses them |
| a subagent's recipe and report | `ctx lane create` composes the recipe from its brief parameters, and the recipe's `REPORT` block names the report's sections ([Units and subagents](units-and-lanes.md)) |
| the overlays | [Overlays](overlays.md) |

Writing is filling, never inventing: an artifact is written by filling its shape directly, with the schema in hand as the complete form. The laws pin the record shapes and the guides carry the rest, so the shape is read without concrete content to copy.

The drift control is the write path where one exists: the record shapes stay exact because the verbs write them and the audit reads them, and the recipe stays exact because `ctx lane create` writes it from the dispatcher's parameters, its fixed blocks from the verb's own text. The overlay and report shapes have no parser: the guide is their home (the report's sections are the ones its recipe names), and the agent holds them by reading it.

### The shared dialect

All grammars speak one dialect, and it is contractual. Typed blocks start at column 0; bodies indent two; `::` opens an indented block value; `|` means alternation only; `[ ]` wraps optional parts; `->` means flow; `#` starts a comment. Whitespace is load-bearing: a block that starts at the wrong column silently breaks every query written against it.

Spellings are contractual too. A pointer names its target exactly, a section and step (`@refresh`) or a path and symbol (`finding#NAME`); a vague mention is a defect. The reason is mechanical: the workspace queries with plain search, and a vocabulary word with two spellings is a search that silently misses.

The dialect governs form, never volume. It compresses how things are written, never how much: the schema holds the shape, the writer holds the volume. The grammars name the elements an artifact must carry; the rest is freestyle. The artifacts themselves, and the fields they carry, are the record page's material.

## The scripts

The runtime ships as one POSIX sh file at `.contexture/ctx`: discovery, help assembly, dispatch, the run engine, and the hook runner. Discovery reads two roots, the workspace modules root and the extension root (`.contexture/extensions/modules/`), listing the workspace modules first; an extension module whose name collides with a workspace module, a builtin, or a reserved name is warned and skipped, never a silent shadow, a module in either root whose name breaks the module name rule (lowercase letters, digits, dot, underscore, and dash, starting with a letter or digit, the namespace rule, since a module's namespace is its name) is warned and skipped too, and an absent extension root is silent. Around it, modules declare their surface and the engine does the rest. The record engine is the unit module, its verbs as extension-less scripts under `.contexture/modules/unit/scripts/`, one file per verb, each carrying its `# summary:` and its `# usage:` lines; each verb is a thin POSIX sh script over the shared library in `.contexture/modules/unit/lib/` (the verb shell `verb.sh`, the one renderer `render.awk`) and the storage core's answer flattener (`.contexture/storage/scripts/json.awk`) that makes one storage call and renders its answer, and the posix driver under `drivers/posix/` is POSIX sh and awk too, which means no dependencies, no model tokens, and the same answer every time. A module is the standard folder ([Modules](modules.md)): the manifest `module` with its summary, version, and description block, beside its optional `laws`, `data`, `install`, and `uninstall` files and its `scripts/`, `hooks/`, and `filters/`. The engine reads the summary and validates the manifest through the private `ctx _module` reader; the compose reads the summary, description, and laws; the package installer and catalog readers validate a module part and read the package manifest's required fields (`summary`, `version`, `kind`, `parts`, `driver`) and optional metadata (`category`, `pitch`, `when`, `needs`, `tags`, and trailing `description` block, with `requires` reserved and refused) through the private `ctx _package` reader; the storage reads the data. The engine assembles `ctx help`, `ctx <module> help`, and `ctx <module> help <verb>` from the `scripts/` declarations, so help is engine-owned and no module ships a help script. Dispatch validates the verb engine-side, anchors every command at the workspace root, and passes arguments, streams, and exit codes through. The engine answers `run`, `compose`, `package`, and `search` itself, before discovery, so none is a module and the engine itself prints no discovery warning for them (a package's part hooks run module verbs, which discover, and the search runs its discovery quiet): `ctx compose [--check]` execs the core's private composer with its arguments, output, and exit code unchanged, refuses rc 2 naming a missing composer, and answers a sole `--help` or `-h` with its own usage. `ctx package` is one builtin group with five sub-verbs (`install`, `uninstall`, `list`, `catalog`, `info`): a bare catalog name resolves `.contexture/plugins/<name>` first and falls back to `plugins/<name>` at the workspace root, and a value holding a slash is a package root path read from the working folder; `ctx package list`, `ctx package catalog [--names] [--no-probe] [--json]`, and `ctx package info <package> [--no-probe] [--json]` are read-only and need no human go (running optional `<pkg>/hooks/probe` non-interactively with stdin from `/dev/null`: rc `0` ready, `1` unmet, `3` partial, other error, absent probe defaulting to ready); for `install` and `uninstall`, a usage error, a malformed name, an absent catalog package, or a missing private script refuses with one line before anything runs (naming the package installer or uninstaller alone, never its private path), otherwise the verb sets `CTX_ROOT` to its own workspace and execs the core's private installer or uninstaller from there, stashing any `<pkg>/hooks/uninstall` at `.contexture/extensions/.state/<pkg>.uninstall` atomically and running package-level `<pkg>/hooks/install` and stashed uninstall hooks non-interactively (`< /dev/null`) in LIFO order alongside module part hooks, so the package always lands in that workspace. An install or uninstall runs only on the human's explicit go at the act, which the verb never checks. `ctx unit` fronts the record engine's verbs; `help` (or `--help`, or `-h`) prints the full contract table, so no one reads a script to learn one. After a verb, `--help` or `-h` alone prints that verb's own table: a shell verb answers it itself, and for an awk verb the engine prints the table `ctx <module> help <verb>` prints, since an awk interpreter would read a leading dash argument as its own option and the verb would never see it. Nothing needs installing.

Alongside the record engine, `ctx run` provides zero-parameter discoverable stream compaction and command execution. It operates both as a direct runner prefix (`ctx run <cmd>`, full path `.contexture/ctx run <cmd>`) preserving exact exit codes, and as a standard Unix pipe (`cmd | ctx run`). Runner mode selects the filter by the wrapped command's identity, read from the `# command: <regex>` header, and falls back to the signature scan when no command claims the line; stdin mode selects by the stream signature (`# match: <regex>`), sampled from the first 40 lines. The directive text reaches awk through the environment, so backslash escapes in a signature survive verbatim. ANSI escape sequences are stripped before selection and filtering, while the raw bytes stay untouched for the fail-safe comparison. Capture files for runner mode prefer the workspace's gitignored `.contexture/tmp/` when it is writable, and fall back to the caller's TMPDIR only when the drawer cannot hold them. The capture files are created in that drawer and unlinked before the command runs; the runner keeps open handles, so a recursive command cannot find or read its own captured output.

Filters live in the run module's `.contexture/modules/run/filters/*.awk` and in any module's `filters/` directory; the scan takes the run module first, then the other modules by name, the workspace modules before the extension modules. Their headers are the contract: `# match:` for the stream signature, `# command:` for the command identity, `# default` for the fallback, `# stream: merged` for filters that need the command's stderr inside the filtered stream, and `# format-only:` for filters whose marker-less reductions are layout rather than lost content. Core Contexture ships low-risk filters for Git unified diffs (`diff.awk`), directory listings (`list.awk`), and generic log deduplication (`log.awk`). The guards are strict: empty or grown output falls back to raw, a shrinking filter without a notice line falls back to raw unless it declares `# format-only`, a notice-only output passes through so a false-green signal is never hidden, and command stderr stays visible, whole on failure or empty stdout and tail-capped with its own notice otherwise. `COMPACT_DISABLE=1` bypasses compaction entirely; `COMPACT_DEBUG=1` reports the selection on stderr.

Building your own verb, hook, or filter? The module contract is in [Modules](modules.md).

### The storage contract (contract 3)

The record engine is decoupled from how any backend stores its bytes, and the record logic lives in one place. Base maps every unit and lane command to one storage function (one of the record's 35 operations or `search.query`, or the driver's own `capability`, `storage.health`, `storage.leftovers`, or `storage.sweep`), sends it the command's parameters, and renders the data it returns. The unit module answers the record's operations once, in its data script (`.contexture/modules/unit/scripts/data`), over the configured driver through the storage layer: it keeps the record as one store value per artifact in the current file shapes, parses and renders the canonical record text, enforces every record rule, and lands each write through the storage layer. The driver is store-only: it answers `capability`, `storage.health` (and, the posix driver, `storage.leftovers` and `storage.sweep`), the seven store data functions, and the store search, keeps every value as opaque bytes, and never parses the record, implements a record rule, materializes a unit, or delegates to another backend. The posix driver keeps a namespace's keys as files under its root, so the record's artifacts are the markdown files under `.contexture/units/<unit>/` (a unit not yet moved still under `.contexture/sessions/<unit>/`, the deprecated root it reads after the root), and it is the only code that touches them; the fts5 driver keeps the same values in its SQLite store. No markdown crosses the command interface: the record travels as typed data, and the configured backend is the single store, so a verb never opens a record artifact itself.

This section is the record rules the unit module implements over the storage layer; the vitest project `unit-record` (`tests/unit-record`) is their executable form, run once on posix through the unit data script, while the drivers project (`tests/drivers`) holds every driver to the store contract, so a backend is compliant when it passes that contract; the unit-shaped profile of the store fuzzer (`tests/drivers/store-fuzz.test.ts`) is the standing differential proof beside the fixed cases: the record logic runs once in the unit module, so only the driver varies, and the profile drives it with unit keys, prefix lists, and multi-put batches of record-sized values. The earlier contracts differ: the v0.54.0 drivers spoke contract 1, whose verb layer fetched whole artifacts and rendered the files itself, and a contract 2 driver implemented the record functions and their rules itself; the contract 3 handshake refuses either at dispatch, since its card carries the store family alone.

#### The wire

A call is the callee (the unit module's data script for a record function, the driver through the resolver for its own methods) run with the function name and its bounded identifiers as argv (a unit, a slug or NAME, a lane, an artifact word, filter tokens such as `--limit=N`), and every free-text field on stdin as payload lines `key=value`. The value is escaped: backslash as `\\`, newline as `\n`, tab as `\t`, carriage return as `\r`, so a value of any size or content survives exactly and never meets the platform argument limit. A list travels as `<key>.count=N` followed by `<key>.1` to `<key>.N`; `<key>.count=0` is the empty list, and an absent key is an absent field. A list of records travels as `<key>.count=N` and `<key>.<n>.<field>`, and a list inside a record nests the same way (`closers.1.targets.count=2`, `closers.1.targets.1=...`). A single document (a recipe, a report) is the raw stdin itself and the function takes no other payload. A function without payload keys never needs stdin.

The answer is rc 0 and exactly one line on stdout: one compact JSON object (no whitespace between tokens) with its keys in the order this section lists them and every listed field present, `null` when absent. Strings are UTF-8 in one JSON form, the form `JSON.stringify` writes: `\"` and `\\`, the short escapes `\b`, `\f`, `\n`, `\r`, `\t`, `\u00XX` (lower-case hex) for the other characters below 0x20, and every other character raw, `/` and non-ASCII included. Integers are plain decimals; a score is a JSON number. Because the form is fixed, the same record answers the same bytes from every backend, and `--json` on a verb prints the function's answer unchanged.

A refusal is rc 1 (the caller's input or the record's rules) or rc 2 (storage or driver failure), nothing on stdout, and exactly one stderr line `<function>: error: <message> (<CODE>)`. The message is fixed per code, so every backend prints the same line:

| code | tier | message |
|---|---|---|
| `ERR_INVALID_ARGUMENT` | 1 | the detail of the shape at fault (a missing or malformed identifier, a malformed payload line, an empty search query) |
| `ERR_ENTITY_NOT_FOUND` | 1 | `<kind> '<x>' not found in unit '<u>'` (kind `task`, `entry`, `finding`, `lane`, and `artifact` for `session.board` and `session.audit` of a unit whose journal is absent: `artifact 'journal' not found in unit '<u>'`); `unit '<u>' not found` |
| `ERR_ENTITY_EXISTS` | 1 | `<kind> '<x>' already exists in unit '<u>'` (a lane entry reads `lane entry '<lane>/<slug>'`); `unit '<u>' already exists` |
| `ERR_UNIT_CLOSED` | 1 | `unit '<u>' is CLOSED; a closed unit takes no writes` |
| `ERR_INVALID_TRANSITION` | 1 | `<kind> '<x>' is <STATUS>; <function> moves only from <allowed>`, allowed `TODO` (task.start), `TODO or IN_PROGRESS` (task.complete), `IN_PROGRESS or DONE` (task.reopen), `TODO or DONE; reopen an IN_PROGRESS task before dropping it` (task.drop), `ACTIVE` (session.close), `CLOSED` (session.reopen) |
| `ERR_CAPABILITY_UNSUPPORTED` | 1 | `mode '<m>' is not supported; answerable modes: <modes joined by , >` |
| `ERR_CAPABILITY_UNSUPPORTED` | 2 | `unknown function '<f>'` (the function name at dispatch) |
| `ERR_STORAGE_READ`, `ERR_STORAGE_WRITE`, `ERR_STORAGE_LOCKED`, `ERR_STORAGE_CORRUPT` | 2 | the backend's detail |
| `ERR_STORAGE_SCHEMA` | 2 | `the storage layer's database is at schema <v>; this driver reads <w> and has no upgrade path: move the database aside and re-enter the record into a fresh one through the ctx verbs` (fts5) |
| `ERR_DRIVER_NOT_FOUND`, `ERR_DRIVER_PROTOCOL` | 2 | the resolver's |

The order of refusals: the argv shape first (`ERR_INVALID_ARGUMENT`), then the unit (`ERR_ENTITY_NOT_FOUND`), then a write to a `CLOSED` unit (`ERR_UNIT_CLOSED`, before any other record rule), then the function's own rules. A write refused at any point writes nothing.

#### The error shape

The one-line protocol covers every storage surface: the record's 35 operations through the unit module, the seven store data functions, the store search entry, the module-facing library's store functions, and its ref interface. A success is rc 0 with the function's one answer; a refusal is rc 1 (the caller's input or the record's rules) or rc 2 (storage or driver failure), nothing on stdout, and exactly one stderr line `<function>: error: <message> (<CODE>)`, the function being the public function or the module data operation name and the message naming the namespace, key, ref, unit, action, or field at fault, never a storage path. The code table above is the whole core vocabulary: the storage layer reuses it, and no new core code joins it.

The batch names the failing action: `store.batch: error: action <n> (<op> '<key>'): <message> (<CODE>)`, the action counted from 1 in the submitted order; a malformed action list before its first action completes reads `action 1 (? '?')`; a malformed action is `ERR_INVALID_ARGUMENT`, an action refusal keeps the underlying code, and a driver failure keeps its code with the same context. Only the first failure prints, nothing is written, and the answer is never partial. The batch cases of the drivers project (`tests/drivers/store-contract.test.ts`, with the planted second-action write failure in `store-faults.test.ts` and the fts5 trigger in `plugins/storage-fts5/tests`) pin it on both drivers.

The scan's refusals use the same codes: a missing or malformed argv, a malformed namespace, or a malformed data declaration is `ERR_INVALID_ARGUMENT`; a namespace no data file declares is `ERR_ENTITY_NOT_FOUND`; an unreadable key or store is `ERR_STORAGE_READ`; a driver that does not serve the store family answers its unknown-function line at tier 2. A scan stages its answer and prints it whole, so a read failure midway prints nothing on stdout; the drivers project's `store-contract.test.ts` pins the answer and the refusal lines on both drivers, the planted encoder failure included.

The library's caller lookup follows the same lines: a script it cannot place (one run by a relative path, or one in no module folder) refuses `ERR_INVALID_ARGUMENT` with one line under the store function's name. The module-addressed ref interface (`data_get`, `data_emit`) retired with it, since a module reads another module's entity through that module's `ctx` verbs. The source write's half of the ref shape is the unit module's: the source write re-frames the same failure with its own function, `task.add: error: ref '<ref>': <message> (<CODE>)`, and refuses before writing. The library's half is pinned by the drivers project's `library.test.ts` on both drivers; the source write's half by the `unit-record` project's module data cases (`module-data.test.ts`).

A record function whose own store call refuses re-frames the storage layer's line the same way: one stderr line with the record function's name, the storage layer's message, and the storage layer's code, `session.board: error: cannot read key '<unit>/journal' in namespace 'unit' (ERR_STORAGE_READ)`, its rc as before and the storage layer's own line never reaching the verb; the resolver's own `driver-resolver: ` line rides whole as the message, and a store that printed neither its refusal line nor a resolver line (nothing, or only a foreign line) leaves the fixed line of its call, `the storage layer read failed (ERR_STORAGE_READ)`, `the storage layer list failed (ERR_STORAGE_READ)`, or, for the batch, `the storage layer batch failed (ERR_STORAGE_WRITE)`, so the line always carries a code. One helper of the unit module carries its `store.get` and `store.list` reads and the write's `store.batch` (the unit module's README names it); the `unit-verbs` project's `storage-faults.test.ts` pins it over an unreadable state and journal, a store list that cannot make its scratch, a held namespace lock, and a wrapper resolver making each of the three calls print nothing or only a foreign line, or a foreign line before the storage layer's own refusal.

`ERR_SCHEMA_VIOLATION` is a tier 1 code the module library owns, outside the core code table above: the library's field validator answers it for a write that breaks a container's declaration (an unknown field, a value outside its one-of set, a required field left absent), and the docs module answers it for a write its grammar refuses (a field its edit engine checks: an unknown field, a value outside its set, a required field removed; or a result that fails its grammar audit), rc 1 and nothing written in both. Module-owned codes stay at tier 1 too: a module's data script or verb may mint its own code; the core's codes are reserved for core and driver semantics, and a module never redefines one.

The resolver is the one shape exception: its diagnostic is `driver-resolver: ERROR: <detail> (ERR_DRIVER_NOT_FOUND|ERR_DRIVER_PROTOCOL|ERR_CAPABILITY_UNSUPPORTED)`, uppercase and outside the `<function>: error:` form; the library passes it through unchanged, and a module verb that asks a capability may re-frame it in its own line. The handshake stays one line when it refuses: the driver's own refusal line folded into `driver-resolver: ERROR: capability handshake failed for driver '<name>': <driver line>`, or the resolver's `ERR_DRIVER_PROTOCOL` line when the driver printed none. The drivers project's `resolver.test.ts` pins the resolver line as the exception.

The interrupt rule stands: rc 0 means the write landed; after an interrupt any other exit means check with a read before writing again (Exit tiers, atomicity, and interruption).

#### The functions

Forty functions, each called by the verb in the last column: the driver's own four (`capability`, `storage.health`, and the posix driver's `storage.leftovers` and `storage.sweep`, reached through the resolver), then the record's 35 operations and `search.query`, which the unit module's data script answers over the storage layer; the eight module store functions (the seven data functions and the search) and the optional promotion (`store.promote`) follow them, under The storage layer. Schemas are in the data model. No function moves a record between backends: `unit.export`, `unit.import`, and the dump format left the contract (below, Moving a record between backends). Outside the 35, the data script answers `unit.migrate` (`[--dry-run] <unit>...` or `--all`, answering `{promote, moved, rewritten, migrated}`, and `--collect <unit>...` or `--all`, the address forward's candidate listing, answering `{collected}`), the record's migrations behind `ctx unit migrate`, which moves units between the declared roots of the one posix store, and `unit.sweep` (`[--dry-run] [--delete] <unit>...` or `--all`, answering `{mode, dry_run, calls}` and leaving each storage layer answer in the verb's sweep folder), the sweep behind `ctx unit migrate --sweep`.

| function | argv | payload | answer | called by |
|---|---|---|---|---|

#### The record data model

Every block artifact (the journal, the backlog, the knowledge, a lane journal) is a preamble followed by items in order. The preamble is the text before the first item head, as stored; `null` means the artifact is absent, `""` present with nothing before the first item. In a journal and a lane journal only a column-0 `@entry ` or `@anchor ` line starts an item, so any other column-0 text (a comment, a continuation line, an unknown `@` word) belongs to the preceding item; in a backlog and a knowledge artifact every column-0 `^@[A-Za-z]` line starts an item, a head other than `@task` (in the backlog) or `@finding` (in the knowledge) making an opaque item.

Every item is typed data and renders in one canonical layout: its canonical lines (per kind, below), each newline terminated, followed by one empty line when a next item exists and is not an anchor, and by nothing when the next item is an anchor or the item is the last. That text is the item's span, the one every read prints on every backend; no answer carries an item's stored bytes, so field order, spacing, quoting, blank lines, and line endings are layout, never data, and the same record prints the same text everywhere. What the typed fields cannot hold in their schema is content the model still holds, in named fields: an item's extra fields (a field line beyond its schema, or a repeated one, key and value in line order), its extra lines (a line no field holds, as stored), its head text (text after the id on the head line), an entry's legacy status, a closer's extra text (a word of its target part that names no date-slug), an opaque item's head and lines. Every item a view renders carries `next`, the kind of the following item (`entry`, `anchor`, `task`, `finding`, `opaque`, or `null`), so base computes the separator without seeing the neighbor.

The append rule, for every write that adds an item: remove the artifact's trailing empty lines, write one empty line unless the new item is an anchor or the artifact holds nothing, then the new item's canonical lines. So a journal never ends with an empty line, an anchor follows its predecessor directly, and an entry follows one empty line.

A write that touches an item (a task status move, `task.update`, `finding.update`, a state write by `session.refs`, `session.stamp`, `session.close`, `session.reopen`) sets its typed fields and stores the item in its canonical lines from them, every field it holds kept (its extra fields, extra lines, head text, legacy status); a drop removes the item, then the artifact's trailing empty lines go. The unit module keeps every other byte of the stored value as it stands, on every driver: an artifact keeps its bytes until a write touches one of its items, and then only that item's span (its lines to the next head) is rewritten canonical, a rewritten last item leaving the value ending with a newline; an append after a legacy item keeps that item's bytes (only the artifact's trailing empty lines go). A block value (a DESCRIPTION, ACCEPTANCE CRITERIA, IMPLEMENTATION DETAILS, or SUMMARY body) drops its trailing whitespace-only lines on every write and every read, a value of blanks alone reading `""`, since the dialect cannot tell such a line from the separator after the item.

The derived fields: `ordinal` and an opaque item's `seq` count every item of the backlog or the knowledge from 1, opaque items included; `seq` counts every journal (or lane journal) item from 1, anchors included; `occurrence` counts the occurrences of a slug up to this one from 1, so a legacy repeat reads 2 and up. The board's `live` holds every entry occurrence no later closer names, in journal order; `open_tasks` every task whose status is not DONE, in backlog order; `open_threads` every live entry whose thread is set and not `none`, its anchor the entry's ANCHOR or `""`. An Audit finding's `slug` names the entry or task it is about (for DANGLING_CLOSER the closing entry, with the absent target in `detail`; for BRACKETED_FIELD the owning entry, with the field text in `detail`); `line` is the line of the stored journal value the finding stands on, counted by the unit module on every driver (null for DONE_WITHOUT_EVENT, a backlog finding), `first_line` the line of a repeated slug's first occurrence, and `occurrence` is set for LEGACY_DUPLICATE_SLUG, which only a posix file can hold (the functions refuse a repeated slug).

The canonical lines, what every read prints and every write stores:

- state: its extra lines, then `status: <s>`, `current_anchor: <a>`, `objective: "<o>"`, `repos: [<a, b>]`, `ref_sessions: [<c, d>]` when not null, then each extra field as `<key>: <value>` (a value's later lines following it as stored); a legacy `next_action` line and its continuation lines are consumed and dropped by the parse, never rendered, and the next state write erases them.
- task: `@task <slug>` (then ` <head text>` when set), its extra lines, `  STATUS: <s>`, `  OBJECTIVE: "<o>"`, `  REFS: [<a, b>]` when refs is not empty, then `  DESCRIPTION ::`, `  ACCEPTANCE CRITERIA ::`, `  IMPLEMENTATION DETAILS ::` for each non-null section, each followed by its body lines prefixed by four spaces, an empty body line written empty, then its extra fields.
- entry (the main journal and a lane journal alike): `@entry <slug>` (then its head text), its extra lines, its extra fields, then, each when set, `  ANCHOR: <a>`, `  STATUS: <legacy status>`, `  WHAT: "<w>"`, `  GROUP: <g>`, `  RHYTHM: <r>`, `  THREAD: <t>`, one `  REF: "<r>"` per ref, one closer line per closer (`  <KIND>: <targets joined by one space>`, then ` <extra text>` when set, then ` (<verdict>: <reason>)`, or ` (<reason>)` without a verdict, or nothing without either), and `  KNOWLEDGE: true` when set. The extra fields stand before the schema lines because the parse types the last occurrence of a one-line label.
- anchor: `@anchor <A> <date>` when date is set (the stamp form); else `@anchor <A> ("continues <P>", attention: <text>)` when both are set (the A1 of `session.create`, or a legacy receipt); else `@anchor <A>` followed by its head text; then its extra lines.
- finding: `@finding <NAME>` (then its head text), its extra lines, `  SUPERSEDES: <old> (<reason>)` when set, one `  REF: "<r>"` per ref, `  SUMMARY ::` and its body lines as a task's, then its extra fields.
- opaque: its head line, then its lines.
- a one-line field holding a newline (a legacy WHAT or OBJECTIVE over several lines) renders as a block scalar (`  WHAT ::` and its body); an extra field renders as `  <KEY>: <value>` with its value as stored, or as a block scalar when the value holds a newline.

The parse rules, how the unit module reads every stored value, and with it every legacy shape the convention once accepted, into these fields (a legacy unit stays readable without repair and no value is lost on read; strictness applies to new writes only):

- The content of an item is its lines after the head up to its trailing blank lines. A field line is `  <LABEL>: <value>` (label upper case with underscores); a block scalar opens with `  <LABEL> ::`, text after the `::` being its first body line, and its body is the following lines indented four spaces or more, blank lines inside it kept as empty lines, four spaces removed from each, its trailing whitespace-only lines dropped. Every other line (a continuation, a comment) is an extra line of the item.
- A line ending in a carriage return (a legacy CRLF line) parses without it, so every typed string stays LF only; the carriage return stays in the file's bytes until a write touches its item.
- A quoted value that opens with `"` on a WHAT or OBJECTIVE line and does not close on it continues over the following content lines until one ends with `"`; the value is those lines joined by newlines as stored.
- Unquoting removes a leading and a trailing double quote (a value that only opens a quote loses its leading one); a REF loses a surrounding pair.
- Entries: for ANCHOR, GROUP, RHYTHM, THREAD, and STATUS the last one-line occurrence is typed (STATUS reads into legacy_status); the last WHAT, a line or a block, is the what; KNOWLEDGE is true when its last line reads `true`; REF, CLOSES, and SUPERSEDES are lists in line order; every other field line (an earlier occurrence, a KNOWLEDGE line not typed, an unknown label, a block of a one-line label) is an extra field in line order with its value as stored.
- A closer's targets are its value cut at the first ` - ` or ` (`, every blank-separated date-slug token of the part before the cut, its other tokens its extra text. After the cut, a parenthesis read to its last closing parenthesis (a legacy reason may hold parentheses of its own) whose text reads `<verdict>: <reason>` with a known verdict gives both; other parenthesis text is the reason with a null verdict; ` - <text>` is the reason with a null verdict.
- Tasks: the first STATUS (a statusless task reads `TODO`), the first OBJECTIVE (a line unquoted, or a block), the first REFS as a list (`[a, b]` split on commas, or blank-separated bare refs), the first of each block section; every other field line is an extra field.
- Findings: SUPERSEDES `<old> (<reason>)` gives the name (its first token) and the reason (the parenthesis text to its last closing parenthesis, `""` without one); every REF unquoted; the first SUMMARY, a block or a line (`""` when absent); every other field line an extra field. The two block orders both read; SUPERSEDES, REF, SUMMARY is canonical.
- Anchors: a `YYYY-MM-DD` date alone after the anchor gives the date; `("continues <P>", attention: <text>)` gives continues and attention, the attention losing a surrounding pair of quotes; any other text after the anchor is its head text; the lines after the head are its extra lines.
- State: each `<key>: <value>` line at column 0 opens a key, and the indented lines after it continue its value (joined by newlines as stored) until a blank line or the next column-0 line; the first line of each of the five keys is typed (objective unquoted, repos and ref_sessions lists, ref_sessions null without its line); every other key (unknown, or a later occurrence) is an extra field, every other line an extra line; a legacy `next_action` key and its continuation lines are consumed and dropped, never an extra field.
- The head line of a task, finding, or entry gives the id (its second token) and the head text (anything after it).

A store that holds only what the verbs write (fts5, since no command moves a record into it) never holds legacy text: its answers carry legacy_status null, extra_fields, extra_lines `[]`, head_text and extra_text null, and no opaque item.

#### The record rules

Base checks only the input shape before any call (slug and NAME shapes, no newline in a one-line field, no carriage return anywhere, required flags, the THREAD shape on `record` and `lane record` (what the unit or lane awaits, or `none`; never empty, `true`, or `false`), the explicit closer form `<slug> (<verdict>: <reason>)`, the full address REF shape `<owner>#<path>`, one token without blanks, control characters, or double quotes (each target then looked up through its owner's get, still before the call; see Semantic CLI verbs), the search flags (`--mode` defaulting to `exact`, its name shape checked), unknown flags refused, and the bytes: every flag value, payload field, and document (a lane report) must be valid UTF-8 (the storage core module library's one check, `lib_utf8_ok` and `lib_utf8_file_ok`, which the unit verb library and `ctx lane create` call) and hold no NUL byte, else rc 1 `<verb>: error: <field> is not valid UTF-8 (ERR_INVALID_ARGUMENT)` (a lane verb as `lane <verb>`) or `<field> holds a NUL byte`, naming the payload field (`what`, `objective`, `query`, ...), the `ctx lane create` flag (`goal`, `scope`, ...), or the document (`the report`), so every backend answers such a value alike; a slug-shaped value refuses any other byte by its shape first; the bodies of the `ctx docs` write verbs are the docs plugin's to check; a legacy posix file holding such bytes keeps reading) and keeps its v0.54.0 messages where it had them. #### Search

`search.query` answers `{unit, query, mode, total_matches, results}` with each result `{entity_type, entity_id, section, snippet, score}`. The entity types are `session`, `task`, `entry`, `finding`, `lane`, `lane_entry` (the id `<lane>/<slug>`); the sections `backlog`, `knowledge`, `journal`, `lane_recipe`, `lane_journal`, `lane_report` (the unit state is no entity and never searched). `--limit` defaults to 20 (0 answers every result, which the search verb asks for, each unit uncapped), `--entity` to all. The search verb always sends `--mode` (its default is `exact`), so a function call without it is outside the contract. `exact` is the one mode the contract defines, the unit module's own rule, answered alike under every driver; a ranked mode is the storage layer's search, declared in the driver's descriptor, which the unit module asks over the record's document set and maps back to the record's ids, and a mode the unit's records cannot answer refuses `ERR_CAPABILITY_UNSUPPORTED` naming the answerable ones.

The exact rule, one text the unit module searches under every driver: the searched text of a unit is, in order, the backlog (preamble, then every item's span), the knowledge, the journal, then every lane in bytewise order (the recipe, the lane journal, the report); an absent artifact contributes nothing. It is the text a read renders (every item in its canonical lines), never the stored bytes, so a legacy item matches as it reads. A line matches when the query is a substring of it after ASCII case folding (A to Z fold to a to z, nothing else folds); a line starting with `#` never matches. A line belongs to the session for the main preambles, to its task, finding, or entry for a span, to the session for a main journal anchor, to the lane for the recipe, the report, and the lane journal preamble, to its lane entry for a lane entry span; a lane anchor and an opaque item keep the attribution of the line before them. The attribution follows the head lines as the unit module's `lib/search.awk` reads them, in every searched text alike: a column-0 `@task <id>`, `@finding <id>`, or `@entry <id>` line (the id its second token, cut at a `(`) moves the attribution to that task, finding, or entry (a lane entry inside a lane's texts), even where it stands inside a recipe, a report, or another item's span, and a column-0 `@anchor` line of a main text moves it back to the session; any other column-0 `@` word leaves it unchanged. One result per (entity_type, entity_id, section), its snippet the first matching line in text order with its blanks trimmed, then a leading upper-case label and colon (`[A-Z_]+:`) with its following blanks removed, then one leading and one trailing double quote with their adjacent blanks; `total_matches` counts those pairs, results follow text order and stop at `--limit` (0 for every result), and every exact result scores 0. The unit module's `lib/search.awk` is this rule as code, run over the canonical render of the values the storage layer holds, so no driver implements it.

#### The descriptor and the handshake

`capability` answers `{"driver","version","contract":"3","store":[...],"search_modes":[...],"optional":[...]}`: contract 3 is the store-only card, so it carries no `functions` family; `store` the seven store data functions in the fixed order `list`, `get`, `put`, `delete`, `changes`, `batch`, `scan`, named unprefixed (the family carries the `store.` prefix); `search_modes` its mode registry, a list of objects each carrying a `name` and a one-line `description` (`exact` always among them); `optional` its optional capabilities (`store`, `store.changelog` where the driver keeps a log, `search.schema` where the driver consumes a declared search schema, and `store.promote` where the driver reads a declared fallback root and moves a key prefix from it to the root), and no other token. The store family is required and implies the `store` token, so a descriptor may omit the token; a name outside the seven refuses, and `store.changelog` or `search.schema` outside the family refuses. The store search entry is not a descriptor field: the family, the search modes, and the `search.schema` token declare it. `capability` and `storage.health` are the driver's own methods, never descriptor families: the handshake and `ctx unit diagnose` call them; the posix driver's `storage.leftovers` and `storage.sweep` are two more such methods, never descriptor tokens, so a driver without them answers its unknown function line. The driver version is `3.0.0`. Posix declares the seven, the one mode `exact`, and `["store","store.promote"]`; fts5 the seven, the modes `exact`, `hybrid`, and `trigram`, and `["store","store.changelog","search.schema"]`. Search modes are registered by the driver that provides them, never declared by a module: the resolver reads the registry through one pair reader (a description may hold any character a JSON string carries), `driver-resolver modes` prints it one `name<TAB>description` line per mode, and the library's `store_modes [<namespace>]` answers it, or with a namespace the modes that namespace can answer (`exact` always, a ranked mode only where the namespace's data file declares a search schema). The driver descriptor version is distinct from the package version: a storage-driver package's manifest declares the package version (install, upgrade) and names the driver, while the driver's `capability` answer declares the descriptor version and the capabilities.

Before a driver serves a call the resolver runs its handshake (stdin from `/dev/null`): the descriptor must read contract `"3"`, carry no record function family, declare the seven store data names in the fixed order, and register its search modes as name and description objects with `exact` among them; the family and the optional tokens must agree, and an optional token outside `store`, `store.changelog`, `search.schema`, and `store.promote` refuses (the resolver's `capability` and `check` hold the bundled posix driver to the same list); else the call halts rc 2 `ERR_DRIVER_PROTOCOL` naming what is missing, before the function runs. A record-only driver (no store family) refuses, because contract 3 serves the store family alone. The handshake runs at dispatch for every driver except the bundled posix driver, and its verdict is cached in the scratch drawer (`.contexture/tmp/driver-verdicts/`, one file per driver path) and stays valid while the driver executable exists and the verdict is strictly newer than it and than the workspace configuration (`.contexture/config`, when it exists), so a driver that reads configuration is verified again after a configuration change; `driver-resolver capability` and `check` (and `ctx unit diagnose`) run it afresh. A caller that needs an optional capability or a search mode asks first: `driver-resolver require <capability>...` exits 0 when the driver declares every one and 2 `ERR_CAPABILITY_UNSUPPORTED` naming the missing ones, `driver-resolver has <capability>` exits 0 or 1 and prints nothing; a search mode reads as `search.mode.<m>`, and the store family implies `store` even when the token is omitted. A passing `require` verdict is cached per driver path and capability set (sorted), apart from the dispatch verdict, which it never answers or overwrites, and `require` and `has` find the driver there and executable before any cached verdict answers, so a removed driver refuses rc 2 `ERR_DRIVER_NOT_FOUND` whatever verdict it left; `has` reads such a verdict and writes none, so the cache names exactly the sets callers required. A drawer that cannot hold a verdict caches neither kind: the resolver verifies on every call and adds nothing to stderr.

#### The storage layer

The storage core (`.contexture/storage/`) owns the driver resolver, the generic storage layer contract, the module-facing library, and the posix driver; it is not a module, so `ctx help` does not list it. Every caller (the unit and lane verbs and the docs module) resolves the configured driver and asks its capability questions through the core resolver directly; the session module's compatibility wrapper retired with the unit module. The storage layer serves module-owned data only: the docs corpus reaches the storage layer through the docs module's own typed layer, and the record's module-side implementation is the unit module at `.contexture/modules/unit`. Its data file declares the record as one store value per artifact (namespace `unit`, root `.contexture/units`, the deprecated fallback root `.contexture/sessions`, suffix `.md`, the key `<unit>/<path...>`, the document-set search rules, and `unsearched: <unit>/state`, the state as a document the search schema leaves out), and its data script answers the 35 record operations over the storage layer's `get`, `list`, and `batch` with the module's own parser and canonical render: the values are the current file shapes, a multi-key write lands through one `store.batch`, the exact search is the record rule over the canonical render, a ranked mode is the storage layer's document-set search filtered to the unit, and the canonical `unit#<unit>/...` refs resolve through the module's `data_get`. The driver is store-only under contract 3: it keeps capability, `storage.health`, the seven store functions, and the store search, and the unit verbs reach the record through the unit module data script over the storage layer; `ctx unit` is the record surface, and `ctx session` is retired naming it. The core reads and validates a module's data file; it never calls the module's code, and no module's parser enters base.

A module declares its data in a `data` file beside its `module` file, one `field: value` line per field and a line starting with `#` a comment. Only `key` is required; `root`, `fallback_root`, `suffix`, `changes`, the search keys, and the repeated `field` lines are optional. The namespace is never declared: it is the module's folder name, its installed module name, and a `namespace:` line refuses as an unknown field naming the fix (remove the line):

```text
key: <segment>/<segment>            # or a final <segment...> for a variable-depth key
root: <workspace-relative folder>   # optional; default: the namespace
fallback_root: <folder>             # optional; a deprecated root read after the root
suffix: <suffix>                    # optional; default: empty
changes: true                       # optional; default: false
search: flat|documents              # optional; the search schema form
format: text|json                   # optional; flat only; default text
fields: <field>, <field>            # optional; flat only; the JSON fields to rank
title: <field>|key|head             # optional; flat default key, documents default head
snippet: line                       # optional; default line
document: <key-pattern> <section> <entity-type> <head-marker|->   # repeatable
unsearched: <key-pattern>           # repeatable; a document the search schema leaves out
field: <name>: <required|optional> <line|block> [list] [one-of <A|B|...>] [default <value>]   # repeatable
```

A `field` line declares one field of the module's container in the field validator's grammar (below), exactly as a store declaration writes it, for example `field: status: optional line one-of OPEN|PICKED|DROPPED default OPEN`: the blanks after `field:` are the file's separator, while the declaration keeps its own, one blank between clauses and none trailing, so a trailing blank refuses. The data reader checks every field line through the library's field validator (`fields_decl_check` over a scratch copy of the field lines), its engine and its reserved names found beside the reader, at every read of the data file, and refuses a malformed line, a reserved name, or a name declared twice rc 1 naming the data file line (`store-data: line <N>: <the validator's reason>`); a data file without a field line never runs the validator, and a module declaring none (the unit and docs modules) never meets it. The flat search schema's `fields` key is a different key. An `unsearched` line names the key pattern of a document the module reads that its search schema leaves out (placeholders and literal segments, as a document rule's pattern; the unit module declares `unsearched: <unit>/state`, since every verb reads the state while no search returns it): the leftovers probe and the sweep count a key it names as a document, while every reader that does not ask never sees it.

The namespace is the module folder's name, a token of lowercase letters, digits, dot, underscore, and dash, starting with a letter or digit (the module name rule); the namespace `<ns>` is served by the data file of the module folder named `<ns>`, the workspace modules root first, then the extension root, as discovery resolves a module name. The key pattern carries one `<name>` placeholder per slash-separated segment, and its final segment may instead be `<name...>`, which admits one or more key segments (a module's main files and its deeper lane files share one pattern: `key: <unit>/<path...>` admits `unit/state` and `unit/lanes/x/report`). The root is a workspace-relative folder inside the workspace and defaults to the namespace; the fallback root, when declared, is such a folder too, neither equal to the root nor nested with it (one inside the other): a deprecated root a file store reads after the root and never writes, so a module can move its root while the data at the old one still reads; the suffix defaults to empty; `changes` is `true` or `false` and defaults to `false`. A module may override each default: the docs module declares root `docs`, suffix `.md`, and `changes` true, and the unit module's declaration, expressible before its install, is root `.contexture/units`, fallback root `.contexture/sessions`, suffix `.md`, key `<unit>/<path...>`, and `changes` false. A declared root and fallback root apply only under the module's own name: an extension module an install record names as installed under an alias stores under its namespace, the alias, with no fallback root, so two installs of one module never share a store; the data reader reads the install records for an extension module, and an install record area it cannot read refuses rc 2, never guessing the root.

The search schema has two forms. `flat` makes one document per key, section `body`: `format: text` indexes the raw value, `format: json` with `fields` extracts those top-level JSON fields, and `title` names the field whose value titles the document (`key` keeps the key). `documents` declares one repeated rule per document group: the key pattern (placeholders and literal segments, with the final `<name...>` admitted), the section, the entity type, and the `-` or a column-0 head marker such as `@task`; a marker with an id starts a new entity, a marker whose entity type is the section's default joins the default document (the journal's `@anchor`), and a key no rule covers stays searchable as one generic document. `snippet: line` is the only snippet rule. A data file names no search modes: the modes are the configured driver's registry, and a `modes` line refuses as an unknown field naming the fix (remove the line). A duplicate field, an unknown field, a document rule without the document form, and a flat field with a document rule all refuse. The module directory beside the data file is the owner, and a second data file declaring the same namespace refuses. A module's data file ships beside its module file; the docs module's values and root are in its module README.

A module's script sources `.contexture/storage/scripts/library` and calls the storage layer through it (`store_list`, `store_get`, `store_get_into`, `store_put`, `store_delete`, `store_changes`, `store_batch`, `store_scan`, `store_search`, `store_promote` where the driver declares it, `store_require`, `store_has`, and `store_leftovers` with its text form `store_leftovers_text <answer> <summary|kinds>`, the read only leftovers probe of the caller's own namespace that `ctx unit diagnose --leftovers` and `ctx store check --leftovers` print, and `store_sweep [--dry-run] [--delete] [--stamp=<stamp>] [--prefix=<prefix> | --loose]` with its text form `store_sweep_text <answer> <summary|kinds|close> [<answer>...]`, the sweep of the caller's own namespace that `ctx unit migrate --sweep` and `ctx store check --leftovers --sweep` print); the module never names the driver, and never names a namespace. At the first storage call, never when the library is sourced (a lane verb sources the unit verb library by path), the library takes the calling script's path (`$0`, which a sourced file shares with the script that sourced it), folds its `.` and `..` segments lexically with no symlink resolved (a linked module folder answers by the link's name, as discovery names modules), and walks up to the nearest folder holding a `module` manifest: its name is the caller's namespace, kept for the rest of the shell and passed to the driver, whose contract keeps the namespace argument; `store_namespace` prints it. A relative script path (a later `cd` would misattribute it) or no module folder above the script refuses rc 1 with one line; the engine runs every verb, hook, and part hook by its absolute path, and the lane verbs' writes of unit data still land in `unit`, since the unit data script they run lives in the unit folder. `store_modes [--own]` answers the mode registry, or with `--own` the modes the caller's namespace can answer. `store_get_into <targets>` is the batched read into files: one `<key><TAB><path>` line per key in the targets file, one `store.get` call for them all (the one key form for a single key), each present value written to its path byte for byte through the storage core's codec (`store-pack unpack`), and one `1<TAB><key>` or `0<TAB><key>` line per key on stdout, a refused call passing its rc and its one line through. `store_roots` reads the declarations instead of the driver: one line per declared root, the namespace and the root separated by a tab, sorted by namespace, a declared fallback root on its own line after its root, from the core's data reader in its listing mode (`store-data --list`, one `<namespace><TAB><root>` line per valid declaration with a declared fallback root as a third column, a name both roots hold answered once, the workspace module's, which leaves out a declaration it cannot read (a malformed one, or an extension module's whose install record area cannot be read) and a module folder whose name is no namespace token, each with one line on stderr, then exits 1 with the rows it read, and answers rc 2 with no module drawer). It answers the whole list or none: a listing that left a module out, or failed, refuses rc 2 with one `store.roots: error:` line quoting the reader's first reason (`ERR_STORAGE_READ`), so no caller takes a partial list for the whole. The per-namespace answer `store-data <namespace>` is eleven fixed lines and the document rules, never the fallback root, so a parser reading by position ignores the field; `store-data <namespace> --with-fallback` answers the fallback root as line 12 (an empty line when none is declared) and the rules from line 13, the form the posix driver reads; `store-data <namespace> --with-fields`, alone or beside `--with-fallback` in either order, answers after the rules one tagged line per declared field, `@field<TAB><name>: <spec>`, in declaration order, the form the library's `fields_own` reads, a family no document rule can open: a reader that does not ask never sees it, so the plain and fallback answers stay byte for byte as before (the fts5 driver hashes every line past the fixed ones into its search schema signature, and a field line never reaches it); `store-data <namespace> --with-unsearched`, beside the other flags in any order, answers after the rules and before any field line one tagged line per `unsearched` line, `@unsearched<TAB><pattern>`, in declaration order, the form the posix driver's leftovers probe and sweep read, every other answer byte for byte as without it; any other argument after the namespace, or a repeated flag, refuses rc 1. The docs module's nudge reads it to refuse a backlog file inside another module's storage root, and refuses rc 2 on a base whose library lacks it or when it refuses (a module data file it cannot read refuses the whole list). A new write's canonical unit refs are checked by the unit data script through its own entity reads (the `unit-record` project's module data cases pin it). The docs module reads its corpus through the library. The library also carries the shared checks a module asks for, each validating a value and storing nothing: the UTF-8 check (`lib_utf8_ok <string>`, `lib_utf8_file_ok <file>`, and its awk text `LIB_UTF8_AWK`, silent, rc 0, 1, or 2 when the check cannot run) and the full address shape check `lib_ref_ok <label> <ref>` (one token `<owner>#<path>`, the owner the text before the first hash in the module name rule, the path non-empty with any further hash in it; rc 1 prints `<label>: error: malformed ref '<ref>': a reference is <owner>#<path>, one token without blanks, control characters, or double quotes (ERR_INVALID_ARGUMENT)`). The ref check reads the shape alone, so an old short unit ref passes it; the unit and lane verbs keep their own two shape check below. The drivers project's `library-checks.test.ts` pins both. The library lock serializes a module's writers of its namespace across a check and a write: `lib_lock`, which takes no argument (it locks the caller's own namespace, found by the caller lookup, and refuses an argument), takes `.contexture/tmp/locks/lib/<namespace>.lock` (its own family, beside `locks/unit/` and the drivers' `locks/store-<namespace>.lock`, so a holder's own `store_put`, `store_batch`, or `store_delete` never waits on it), writes the holder's pid, and names it in `LIB_LOCK`; `lib_unlock` removes it, and the caller calls it from its exit trap too. The wait is the namespace lock's (below), its refusal `lib.lock: error: the library lock of '<namespace>' is held (60 s timeout) (ERR_STORAGE_LOCKED)` rc 2; an argument, a caller with no namespace, a malformed namespace (a module folder named outside the rule), or a second lock in one process refuses rc 1, an unwritable lock folder rc 2 `ERR_STORAGE_WRITE`. The drivers project's `library-lock.test.ts` pins it on both drivers, the store calls inside a held lock included. The field validator is the library's last shared piece, opt in, so a module that declares no fields (the unit and docs modules) never meets it: the module stages the files and calls `fields_decl_check <declaration>`, `fields_apply <declaration> <old record> <actions> <new record>`, `fields_effective <declaration> <record>`, `fields_conforms <declaration> <record>`, or `fields_reserved_ok <name>`, which run the storage core's engine `scripts/store-fields.awk` and read or write no storage. A declaration is one field line per field, `<name>: <required|optional> <line|block> [list] [one-of <A|B|...>] [default <value>]` (a lowercase name never reserved: `json`, `limit`, `type`, `mode`, `container`, `id`, `ref`, `unset`, `stdin`, and any `add-` or `remove-` name; a block taking no list, one-of, or default, a list no default, a required field no default, `today` the one dynamic default). An actions file carries the write forms one to one, tab separated: `set`, `add`, `remove` with a value in the payload escape, `unset`, and `block` with a base64 body. A record is the unit record dialect (`name: "value"`, a list one line per item, a block `name ::` indented two spaces, declaration order with leftovers after), so it prints back as stored. `fields_apply` checks in a fixed order and refuses one line, `ERR_INVALID_ARGUMENT` for malformed input (an action, UTF-8, a newline in a line value, an empty value, the wrong form for the field's shape) and `ERR_SCHEMA_VIOLATION` for a broken declaration (an unknown field, a value outside its one-of set, a required field absent), writing nothing; defaults fill at create only, an update leaving an absent field absent. `fields_effective` fills an absent static default at read and never stores it, and `fields_conforms` prints one `<field>: <reason>` line per field breaking the current declaration, exit 1 when any prints. A module that declares its container's fields as `field` lines in its data file writes through the checked record entry (the store reads its declarations from its own records instead; both feed the one validator): `fields_own <declaration>` writes the caller's declared field lines to the file, one per line in declaration order, through `store-data <namespace> --with-fields` (an empty file when none is declared, the reader's refusal re-framed under `fields.own`); `fields_put <key> <actions> <record>` creates and `fields_set <key> <actions> <record>` changes one record of the caller's own namespace under the library lock (the one the caller holds, else its own for the call), an existing key refusing a put rc 1 `ERR_ENTITY_EXISTS` and a missing key refusing a set rc 1 `ERR_ENTITY_NOT_FOUND`, the actions applied by `fields_apply`'s rules (the defaults at create, an absent field left absent on a change) and the canonical record put at the key and written to the record file; `fields_get <key> <record>` writes one record with its static defaults filled at read, never stored, read only and lock free. A namespace whose data file carries no field line refuses each rc 1 `ERR_INVALID_ARGUMENT`; the validator's refusal carries the entry's label, a store function's or the lock's passes through as its own line, a refusal writes nothing, and the scratch beside the record file is removed on return; a `ref` stays the module's own, a reserved name. The drivers project's `library-fields.test.ts` pins every rule, the checked record entry on both drivers, and `store-data.test.ts` the field lines.

The seven data functions and the search entry are the contract 3 card itself: the store family is required, since the record reaches a driver only through it, so a driver without it fails the handshake and serves nothing, the record included. Keys are exact: a key that ASCII-case-folds onto another in the namespace refuses, a read or delete acts on the exact key alone, list is bytewise, and no key holds a blank, a control character, a leading slash, a backslash, or a `.` or `..` segment. The module pattern filters list and scan and refuses a key outside it; a final `<name...>` placeholder admits one or more key segments, so a variable-depth declaration covers a module's main and deeper keys under one pattern. The bounded `--op` and `--head` flags are checked before the module data file and the key, so a malformed argv answers the same first refusal on every driver. The posix mapping is `<root>/<key><suffix>` under the workspace root, written by a same-directory temp moved over the key under one namespace scope lock, so a put lands whole or not at all. A namespace declaring a `fallback_root` reads from its root first, then from the fallback: `store.get`, `store.list` (the union, each key once, the root's copy shadowing), `store.scan`, `store.search`, and the key probe; `store.put` and `store.batch` write the root alone, and a delete, alone or as a batch action, removes the key from both roots, so an old value never resurfaces, then each folder it emptied above the key in either root, from the key's own folder upward until the first folder still holding an entry and never the root itself (`store_prune`; a batch prunes only after its whole commit landed, so a rolled back batch restores every key into its folder, and a dropped store container or a deleted unit's last artifact leaves no empty folder); before it writes, a put, a delete, or a batch (after its validation) moves each written key's top segment folder from the fallback to the root under the namespace lock it already holds, when the fallback alone holds it, by one `mv` (the root made first when absent), so a module's write moves its folder whole with no call of its own, and the move that empties the fallback root removes that root in the same call (one `rmdir`, which refuses silently while any folder or file remains, so a root still holding one stays), while a folder already in the root or a namespace without a fallback costs one folder check at most and no process, and a folder both roots hold refuses rc 1 `ERR_ENTITY_EXISTS` naming the prefix (a batch in its action line) with nothing written; a call that served a key from the fallback and answers rc 0 prints one stderr line, `<function>: notice: namespace '<ns>' was read from its deprecated fallback root`, naming no folder, while a refusal keeps its one line. `store.promote` moves one prefix's folder from the fallback to the root by one `mv` under the namespace lock, the root's parent folders made first and a killed writer's residue moving with the folder, and removes the fallback root as the write path does when its move empties it, and an empty fallback root when it answers `none`; fts5 holds namespace and key with no root, never reads a fallback, and does not declare the token. The batch holds that lock once, validates its whole action list against the live keys, stages a value per put, and commits every key under one store-scope undo log, so a planted second-action failure restores the first and prints only that action's line; fts5 runs the whole list in one `BEGIN IMMEDIATE` transaction with one `store_changes` row per action. A filesystem can fold more than ASCII (a Unicode case variant): the posix store refuses a key its root cannot represent exactly beside a stored key, and removes what it just wrote, so a successful put always lists the key it echoes; fts5 holds the two exact keys. `store.changes` is optional per namespace: a namespace declaring `changes: false`, or a driver without the log, refuses rc 1 `ERR_CAPABILITY_UNSUPPORTED`. The posix driver keeps no change log (the module's delta is git); fts5 keeps the generic log.

`store.search` answers one shape on every driver. `exact` is the record rule over the raw stored value: a line of the value matches when the query is a substring of it after ASCII case folding, a column-0 comment never matches, one row per entity and section, its snippet the first matching line with its upper-case label and quote pair trimmed, every score 0. The answer carries the entity identity the document rules derive: `entity_type` and `entity_id` beside the key, the flat and generic fallbacks answering the one document with its key as the id. The exact walk collects every match before printing, so `total_matches` counts every entity and section pair and the limit applies after the walk, results following bytewise key and line order; `limit` 0 answers every result, the unlimited read a module uses to sort into its own text order and cap there. The searched text is the stored value: the canonical source is the module's canonical render, which the module writes through the storage layer, and the core never re-renders a module's grammar (a legacy value is searched as stored). The document set follows the schema: the flat form is one document per key in section `body` (the raw value for text, the declared fields for JSON), the document-set form is the per-entity extraction the data file declares, derived at write time by the fts5 store and indexed in its store FTS tables; a key no rule covers and a module with no schema use the generic raw value. A ranked mode (`hybrid`, the RRF of the fts5 porter and trigram indexes, or `trigram` alone) answers only where the driver registers it in `search_modes` with the optional `search.schema` token, and only over a namespace whose data file declares a search schema; a mode the driver does not register refuses rc 1 `ERR_CAPABILITY_UNSUPPORTED` naming the registered modes, and a ranked mode over a namespace with no search schema refuses rc 1 `ERR_CAPABILITY_UNSUPPORTED` naming `exact` as the answerable mode. The fts5 store re-derives a namespace's documents whole when its stored schema signature differs.

The descriptor is the contract 3 store-only card: the seven store data functions in `store` (unprefixed, fixed order), with the optional tokens `store` (implied by the family), and, where the driver keeps one, `store.changelog`, and, where the driver consumes a declared search schema, `search.schema`, and, where the driver reads a declared fallback root, `store.promote`; the driver version is `3.0.0`, and the card carries no record function family. The drivers project's `store-contract.test.ts` pins the card and checks the seven-name family and the token agreement; the record itself runs through the unit module data script in the `unit-record` project. The vitest drivers project (`tests/drivers`) holds both drivers to the seven functions in one parameterized set over a docs-shaped synthetic namespace: the exact list answer and order and the optional key prefix, the raw bytes of a document, the key rule, the data file grammar, the namespace lock, the atomic put, the all-or-none batch and its first-failure line, the scan's base64 values, empty namespace, and staged answer, the exact rule with its entity identity and the document-set extraction, the limit after the walk and the unlimited read, the ranked modes' identity and the generic fallback, the search schema's shape refusals, the re-framed search-engine failure, each with a planted difference where the instrument needs a null check (the no-base-to-docs census is the governance project's `base-docs-census`); the plugin's own project (`plugins/storage-fts5/tests`) carries the fts5 store cases. Its `library.test.ts` proves the library's store seven and its ref interface (`data_get` and `data_emit`, the depth-8 and cycle refusals) over a fixture module on both drivers. The committed store fuzzer (`tests/drivers/store-fuzz.test.ts`) is the standing differential proof beside the fixed cases: a seeded write sequence over both stores, every answer and every read compared byte for byte, a run that writes nothing reading as an instrument blind rather than SAME, and a planted extra byte on the fts5 list reading DIFF; its unit-shaped profile drives the store calls the unit module makes (unit keys, prefix lists, multi-put batches of record-sized values).

#### Driver discovery hierarchy

The driver resolver (the storage core's `scripts/driver-resolver`) discovers storage drivers through this hierarchy:
1. Workspace custom drivers: `.contexture/drivers/<name>/driver` (transitional)
2. The storage core's drivers: `.contexture/storage/drivers/<name>/driver`
3. The extension root's package drivers: `.contexture/extensions/storage/drivers/<name>/driver`
4. Module-owned drivers: `.contexture/modules/<module>/drivers/<driver-name>/driver` (transitional; the module system moved the fts5 driver to the extension root, and the tier stays for a workspace driver a module still carries)
5. The base mirror's core, extension, and module drivers (transitional)
6. PATH executables: system binaries named `ctx-storage-<name>` (transitional)

The name in `storage.driver` is the driver name, not the package name: the package `storage-fts5` installs the driver `fts5` at tier 3 through its package manifest (`kind: driver`, `driver: fts5`, `part: driver storage/drivers/fts5`), so the package name and the driver name may differ. A driver package ships no module file, so the engine never lists a driver as a module; the storage core resolves it. The resolver passes stdin through to the driver untouched. The adoption retires the transitional tiers.

#### Configuration precedence

Driver selection follows deterministic precedence:
1. `CTX_STORAGE_DRIVER` environment variable
2. `.contexture/config` key `storage.driver` (the contract; the legacy `session.storage.driver` key and `.contexture/storage.conf` read as transitional compatibility)
3. Default baseline: `posix`

The same file carries the package declaration, one `package.<name>: <source> [--as=<module>=<alias>]...` line per package, which `ctx package install` writes (the source as given, a path inside the workspace relative to its root, and every alias the install record holds) and `ctx package uninstall` removes, every other line kept byte for byte; an uninstall the file holds no line for writes nothing, so an absent file stays absent. A dedicated reader in the package verb reads it (the first token the source, the rest flags, a `#` token starting a comment); the value reader above never meets it, since its key match is `storage.driver`. A write to the file retakes the storage handshake once, as any change of the configuration does.

#### Exit tiers, atomicity, and interruption

Every function answers in three tiers: `0` success; `1` a semantic refusal (the input or a record rule); `2` a storage or driver failure (driver not found, a failed handshake, an IO error, lock contention, a write the backend refused). A backend never prints a success answer for a write that did not land: a replace the storage layer refuses removes its temp and exits 2 `ERR_STORAGE_WRITE`. Each write function lands whole or not at all: the unit module reads the unit under its unit lock, stages every artifact the write changes, and lands them through one `store.batch` (posix: a temp file and a rename per key under the namespace lock, and an undo log: every file a step replaces or removes is first hard-linked into the stage, so a failed rename or removal rolls every earlier step of the batch back before the call exits 2 `ERR_STORAGE_WRITE`; fts5: one `BEGIN IMMEDIATE` transaction), and concurrent writers of one unit serialize. An interrupted call (HUP, INT, TERM) exits through its cleanup on every sh, dash included: the unit module's write removes its scratch and releases its unit lock, a store driver's call, a read included, removes the scratch files it made (each named for the cleanup the moment it exists), a posix batch interrupted among its renames is rolled back the same way, and a held namespace lock is released, while a writer interrupted as it still waits for a lock removes nothing, so the live holder keeps it; a SIGKILL cannot be trapped, so a posix batch killed among its renames can leave part of its write, but its locks are recoverable: each lock folder carries its holder pid, a waiter removes a lock whose pid is gone (`kill -0`) and proceeds, and a live holder still ends in `ERR_STORAGE_LOCKED` after 600 polls 0.1 s apart (60 s of sleep). The unit lock, each driver's namespace lock, and the module library's lock (`lib_lock`, below) share that one wait, never a folder (the unit locks keep their own and the library locks theirs, so no unit name meets a namespace lock and no library lock meets either): the recovery clears every dead holder, so the wait only bounds a live one, busy or hung, and it is sized from measured holds so six writers queued on a 1 MB unit under load still land (the unit module's README carries the numbers). The wait is a poll, not a queue: whoever polls first after a release wins, so bursts land while writers looping without pause can starve to the bound; that bound is the accepted design, revisited if parallel writers start ending in `ERR_STORAGE_LOCKED`. An interrupted write may or may not have landed, and the exit code of an interrupted call does not say which: the fts5 driver interrupted after its `COMMIT` has landed the write though the call exits with the signal's code before its answer prints. The rule for every caller: rc 0 means the write landed; after an interrupt, any other exit means check with a read (`ctx unit board`, `entry show`, `task show`, `lane show`) before writing again, since a retried write can repeat an act that already landed.

#### Split-brain prevention

If a non-posix driver is configured (such as `fts5`) and its executable cannot be resolved or fails its handshake, the engine halts immediately with exit code 2 (`ERR_DRIVER_NOT_FOUND`, or `ERR_DRIVER_PROTOCOL` when the capability call fails or the descriptor is not a complete contract 3; a driver whose capability call refuses with its own line has that line passed through the handshake's one line, its code ending it). The engine never falls back silently to `posix` when another driver was configured, and no verb opens an artifact outside the driver, so records never diverge between storage engines. Two guards hold every verb to the driver: the governance project's static store-bypass check reads every module line that names the record store, a driver, the resolver's answer, sqlite3, or the lock area against an exact allow-list, and the pre-release SQLite smoke set (`bun run test:sqlite-smoke`, in `bun run test:prerelease`) drives every command family under fts5, so a verb re-pointed at the files turns both red. Beside them the governance drawer literal census holds the storage core and the drivers (and the engine, the composer, the package overlay, and the module roots) to the drawer layout's owners: the record root, the fts5 database name, and the lock literals appear only on their owner lines (The drawer layout, below).

#### Available drivers

- Baseline POSIX driver (`posix`): zero-dependency POSIX sh and awk driver in the storage core at `.contexture/storage/drivers/posix/`, keeping each key of a declared namespace as a file under its root (`<root>/<key><suffix>`), so the unit module's values are the record's markdown files under `.contexture/units/<unit>/`, a unit not yet moved read from `.contexture/sessions/<unit>/` (`store`, `store.promote`; no change log, `store.changes` refuses and the module's delta is its own). A module's declared data file maps its keys under its root through the storage layer, so the module's verbs read and write the same files they always did; the module's delta stays on its own source (git under posix). It runs on the system awk, written to the common subset of BWK awk, mawk, gawk, and busybox awk (no container matrix runs; the governance awk census guards the known trap statically), and every payload and JSON encoder doubles a backslash by concatenation, since a `gsub` replacement of four backslashes yields one backslash under busybox awk and `gawk --posix` (the authoring rule in `docs/modules.md`).
- SQLite FTS5 driver (`fts5`, from the `storage-fts5` storage-driver package): a SQLite-backed store-only driver (schema 5: the generic store, its change log, and the derived store documents) holding the module data, the record among it as the unit module's values, with dual full-text indexing and the ranked modes `hybrid` and `trigram` beside `exact` (the store documents derived per key at write time from the module's declared search schema, `search.schema`); the record's typed tables left with contract 3; it needs the system sqlite3 with FTS5, ships no module file (the engine never lists it as a module), and carries no verb of its own (the v0.54.0 `ctx storage-fts5 migrate` retired); a record reaches it through the ordinary verbs and its corpus through the `ctx docs` write verbs. The [plugin README](../plugins/storage-fts5/README.md) carries adoption and needs; the [driver README](../plugins/storage-fts5/.contexture/extensions/storage/drivers/fts5/README.md) carries the schema, the SQL layout, and the store cases.

### Semantic CLI verbs

Every unit and lane verb is a thin sh script over the shared verb library (`.contexture/modules/unit/lib/verb.sh`): it checks the input shape, makes one storage call, and renders the answer through the storage core's one flattener (`.contexture/storage/scripts/json.awk`) and the module's one renderer (`lib/render.awk`), so every backend prints the same text for the same record; `--json` prints the function's answer unchanged (compact, in the contract key order). The typed flags are the only write inputs: no verb reads a markdown block from stdin, so no markdown crosses the command interface (a lane report, the one document, travels whole; `lane create` takes the brief as one line flags and composes the recipe itself). Every verb refuses an unknown flag or an extra positional argument rc 1 (`<verb>: error: unknown option '<flag>'` or `unexpected argument '<arg>'`, `ERR_INVALID_ARGUMENT`), and every one-line value refuses an embedded newline or carriage return before any write. Every REF and REFS element a write carries (`record --ref`, `finding add`, `update`, and `supersede --ref`, `lane record --ref`, `lane create --ref`, `task add` and `update --refs`) is a full address of the laws (@record references), `<owner>#<path>` (`unit#<unit>/entry/<slug>`, `unit#<unit>/task/<slug>`, `unit#<unit>/finding/<NAME>`, `unit#<unit>/lane/<lane>/<recipe|journal|report>[/<SECTION or slug>]`, `store#<container>/<id>`, `docs#<repo>/<slug>/<id>`, `file#<path>[#<symbol>]`); one token, no blank, no control character, no double quote (an ASCII control byte counts as a blank, and so does a Unicode blank of the White_Space set: NEL, NBSP, U+1680, U+2000 to U+200A, U+2028, U+2029, U+202F, U+205F, U+3000), held by the storage library's `lib_ref_ok`. A retired short or legacy form (`journal#<slug>`, `knowledge#<NAME>`, `backlog#<slug>`, `lane#<lane>/<art>[#<claim>]`, `task#`, `finding#`, `entry#`, the `.md` spellings, `lanes/<lane>/...`, a bare path, an `IDEAS.md` pointer) refuses rc 1 before any call naming the full address `ctx unit migrate` writes for it (`<verb>: error: malformed ref '<value>': a reference is a full address <owner>#<path>; write <full address> (ERR_INVALID_ARGUMENT)`), a `~/` token copied from a compressed view names its unit address the same way, and anything else malformed refuses with the library's line. Then, before the storage call and so before any lock, each target is checked: a `file#` path by the core (inside the workspace it must exist, outside it the shape alone counts, the symbol after a further hash never), every other owner through `ctx <owner> get <path>`, a miss refusing rc 1 `ERR_ENTITY_NOT_FOUND` naming the ref (target not found, owner not installed, or owner has no get verb, each owner probed once and a ref given twice checked once; a path starting with a dash reads target not found before any get). A value already stored reads as it stands until `ctx unit migrate` rewrites it. The record rules (a `CLOSED` unit, the status moves, repeated keys, closer targets) are the unit module's, the same under every driver: such a refusal prints the function's one fixed line, `<function>: error: <message> (<CODE>)`, with the texts of the contract above. The engine names one per-verb scratch root under the workspace drawer and exports it as `CTX_SCRATCH_ROOT`; a verb stages its scratch inside it and removes it on return, and the next dispatch sweeps a root whose holder pid is gone (a SIGKILLed verb).

#### Task operations: ctx unit task
- `ctx unit task add <unit> <slug> --objective="..." [--desc="..."] [--criteria="..."] [--details="..."] [--refs="..."]`: creates a `TODO` task; `--refs` takes the references blank or comma separated, brackets optional.
- `ctx unit task update <unit> <slug> [--objective="..."] [--desc="..."] [--criteria="..."] [--details="..."] [--refs="..."]`: replaces the given fields (an empty value leaves its field as it is); `--refs` replaces the list and `--refs=""` clears it. The flags are its only input (stdin is not read): an update carrying no field refuses rc 1 `ERR_INVALID_ARGUMENT` before any driver call. The task is stored in its canonical lines from its fields (a legacy task too, every value it holds kept, its extra fields, head text, and extra lines among them); every other item keeps its bytes.
- `ctx unit task start <unit> <slug>`: moves a `TODO` task to `IN_PROGRESS`; the state is not written, since the next move is derived from the backlog at presentation. An extra argument, `--pointer` included, refuses rc 1.
- `ctx unit task complete <unit> <slug> --evidence="..."`: moves a `TODO` or `IN_PROGRESS` task to `DONE` and appends its receipt entry in the same write: slug `<date>-<slug>-completed` (a same-day repeat takes `-1`), `WHAT: "backlog/<slug>: DONE (<evidence>)"`, `THREAD: none`, the current anchor.
- `ctx unit task reopen <unit> <slug>`: moves an `IN_PROGRESS` or `DONE` task back to `TODO`.
- `ctx unit task drop <unit> <slug> [--reason="..."]`: removes the task and appends its receipt (`<date>-<slug>-dropped`, `WHAT: "backlog/<slug>: DROPPED (<reason>)"`, the reason defaulting to `task dropped`) in one write; an `IN_PROGRESS` task refuses (reopen it first); the slug can be added again afterwards.
- `ctx unit task list <unit> [--status=todo|progress|done|all]`: one `  [<status>] <slug>: <objective>` line per task in backlog order; the verb maps the words to `TODO`, `IN_PROGRESS`, `DONE`, and every status and refuses another word rc 1.
- `ctx unit task show <unit> <slug> [--json]`: prints the task's canonical block (its `REFS` included, as a bracketed list; a legacy task prints canonical too, every value it holds kept, its extra fields and lines among its canonical lines, never its stored bytes); `--json` prints `task.get`'s answer.

Every other move refuses `ERR_INVALID_TRANSITION` with the task unchanged. `add`, `start`, `complete`, `reopen`, and `drop` fire the task-landing hooks (`CTX_ACT` naming the act, [Modules](modules.md)); `update` fires none. A malformed slug (letters, digits, underscore, dash; starts alphanumeric) refuses rc 1 before any driver call.

#### Journal event recording: ctx unit record
- `ctx unit record <unit> --what="..." [--group=...] [--thread=...] [--rhythm="<name> <N> <GATE>"] [--ref=...]... [--closes=...]... [--supersedes=...]... [--knowledge] [--slug=...]`: appends an immutable event. The unit module takes the unit's current anchor, composes the slug `<date>-event-<epoch>` from the date and time the verb sends (a slug the journal holds takes `-1`), and writes the canonical field order (`ANCHOR`, `WHAT`, `GROUP`, `RHYTHM`, `THREAD`, `REF`, `CLOSES`, `SUPERSEDES`, `KNOWLEDGE`). `--thread` defaults to `none`; `--rhythm` must name a step and gate of the named rhythm, checked through the rhythm module's resolve (the workspace copy first, then the installed one; the rhythm's `@rhythm` line must name its file, else `ERROR: RHYTHM <name> declares @rhythm <declared>; a rhythm's file name and its @rhythm line must agree`; a missing rhythm reads `ERROR: no such rhythm: <name> (ctx rhythm list names them)`, a missing step `ERROR: RHYTHM step <N> not in <name>`), and a stamped write prints, after `recorded entry: <slug>`, the next gate line `rhythm: <name> at <N> <GATE>; next gate: <N+1> <GATE>: <outcome>` (at the last step `rhythm: <name> at <N> <GATE>, its last gate`); `--ref`, `--closes`, and `--supersedes` repeat, one line each. A closer takes only the explicit form `<slug> (<verdict>: <reason>)`: one or more date-slug targets, then the parenthesis with a verdict of `done`, `superseded`, `dropped`, or `folded` and a non-empty reason holding no parenthesis (the law puts the resolution in the closer, so nothing is copied from the WHAT); a bare target list, a missing or unknown verdict, an empty reason, or text after the parenthesis refuses rc 1 `ERR_INVALID_ARGUMENT` naming that form (`record: error: --closes takes <slug> (<verdict>: <reason>) ...`), and a reason holding a parenthesis refuses naming the rule (`a closer reason holds no parenthesis`), before any write. Every closer target must name an entry the journal already holds, else rc 1 and nothing is written. `--slug` takes today's date as a prefix when it carries none and refuses a slug the journal holds.

#### Journal entry inspection: ctx unit entry
- `ctx unit entry show <unit> <slug> [--json]`: prints the entry's canonical block (`REF`, `CLOSES`, `SUPERSEDES`, `RHYTHM`, and `KNOWLEDGE` included; the last occurrence of a repeated legacy slug); `--json` prints `entry.get`'s answer, the closure (`closed`, `closed_by`, `close_reason`) derived by position: the first later closer naming the occurrence.
- `ctx unit entry list <unit> [--anchor=A<N>] [--group=<token>] [--json]`: one `  [<anchor>] <slug>: <what>` line per entry occurrence in journal order, open or closed; `--group` is the topic thread across anchors, `--anchor` one period; the unit module filters by the exact values, so the text and the JSON agree.
- `ctx unit entry closure <unit> <slug> [--json]`: `closure <unit> <slug>: open`, or `closed (<verdict>)` with the first closer's verdict, then per closer an empty line, `closer <slug> (<anchor>)`, and the closer's line; positional, so only a closer standing after the entry counts; an absent slug refuses rc 1.

#### Finding lifecycle CRUD: ctx unit finding
- `ctx unit finding add <unit> <NAME> --summary="..." [--ref=...]... [--supersedes=...]`: adds a finding; a new NAME is upper case letters, digits, and underscores, a NAME the knowledge carries refuses rc 1 (`ERR_ENTITY_EXISTS`), and a `--supersedes` predecessor must exist.
- `ctx unit finding show <unit> <NAME> [--json]`: prints the finding's canonical block, with `SUPERSEDED_BY: <successor>` after its head line when a later finding supersedes it.
- `ctx unit finding update <unit> <NAME> [--summary="..."] [--ref=...]...`: replaces the summary, the references, or both (either flag alone works); `--ref` replaces the whole list; stdin is not read, and an update carrying no field (an empty `--summary` alone included) refuses rc 1 `ERR_INVALID_ARGUMENT`. The finding is stored in its canonical lines from its fields (`SUPERSEDES`, `REF`, `SUMMARY`, then any extra field), a legacy finding too, every value kept; every other item keeps its bytes.
- `ctx unit finding supersede <unit> <old-name> <new-name> --summary="..." [--ref=...]...`: records forward-only supersession; a missing predecessor or a held successor NAME refuses rc 1.
- `ctx unit finding drop <unit> <NAME>`: removes an invalidated finding.
- `ctx unit finding list <unit> [--active-only] [--json]`: one `  <NAME>: <summary>` line per finding, `--active-only` leaving out every finding a `SUPERSEDES` names.

Every finding write refuses a `CLOSED` unit.

#### Search across modules: ctx search
- `ctx search "<query>" [--type=<type>] [--mode=<mode>] [--limit=N] [--json] [--module=<name>]`: the engine builtin over every module that carries a verb named `search` (the verb's name is the declaration), found by the quiet validated discovery in discovery order, the workspace modules first. Each module's search runs as a child, one after another: the dispatch exports (`CTX_ROOT`, `CTX_MODULE_DIR`, `CTX_BIN`, `LC_ALL=C`), its own per-verb scratch root, no stdin, the marker `CTX_SEARCH_FANOUT=1`, the query, the shared flags in the `--flag=value` form (a module's own scope flags, such as `--unit` or `--repo`, are never forwarded), and `--json`; its stdout and stderr land in files of a sibling folder, never a pipe a surviving process could hold open. The time bound is `search.timeout` in the workspace configuration (`.contexture/config`, a positive whole number of seconds, default 10, in the configuration's own grammar); the engine polls the child every 0.1 s, and a child past the bound is stopped with every descendant from one `ps -A -o pid= -o ppid=` snapshot, `TERM` then `KILL` 0.2 s later, and reaped with its stderr discarded, so the shell reports no killed job; a hangup, interrupt, or termination of the engine itself stops the running child the same way and removes the run's scratch before the engine exits 129, 130, or 143, so the arm leaves no process behind (the stated limits: a process forked between the snapshot and the kill may escape, and so may a descendant reparented before the snapshot, such as a double fork). Each answer is checked before it is trusted with the storage core's flattener (`json.awk`): rc 0, well formed JSON, `total` and `rows` present, every row carrying `module` (its group's name), `container`, `type`, `id`, `address`, `snippet`, and `read`; a miss marks the group failed with the first stderr line, or the check's line, as its reason. The answer groups by module with no ranking across them: an `ok` group carries `{module, status, mode, total, rows}`, a failed one `{module, status, error}`, and a module with no search verb `{module, status}` read `not searched`. `--json` prints `{query, groups}`; the text form prints each searched group (`<module>: <shown> of <total>`, the mode when it fell back to `exact`, then each row's type, address, label, and snippet with its read beneath) and ends with one line, `searched N, failed M (names), not searched K (names)`. A child's stderr on success prints after the results, each line prefixed with its module's name. `--limit` is a positive whole number per module (default 20), `--mode` defaults to `exact` and takes a registered mode (a module unable to answer it falls back to `exact`, which its group says), `--type` passes to every module (a module that does not hold the type answers zero hits), and `--module=<name>` searches one module. `ctx search --modes [--json]` lists the registry with its descriptions through the resolver. Exit codes: 0 when every searched module answered (zero hits included, or no module carries a search verb, which the closing line says), 2 when any failed (the other groups still printed), 1 for a bad argument (an unknown flag, a bare value form, a second, empty, or blank query, a carriage return or newline, a bad limit, an unknown or empty module, a module without a search verb, an unregistered mode, `--modes` beside a query or any flag but `--json`, a malformed `search.timeout`), each one stderr line with nothing run. A query cannot begin with a dash: it reads as a flag and refuses, since no end of options marker exists (a stated limit). A sole `--help` or `-h` answers from the arm on stdout rc 0, and `search` is reserved statically, so removing the unit's search verb never frees the name. A module installed under an alias (`ctx package install --as=<module>=<alias>`) answers as its installed name: its group carries the `alias` key after `module`, the original module name read from the install record, and its text header reads `<alias> (alias of <module>)`; `--module` takes an installed name, or an origin name no module is installed under when exactly one module is installed under an alias of it (several refuse, naming them). A module's rows name its installed name, which a module's search verb reads from its own folder.

#### Search: ctx unit search
- `ctx unit search "<query>" [--unit=<unit>] [--all] [--type=<type>] [--mode=<mode>] [--limit=N] [--json]`: searches the record entities in the shared search syntax, the query first. It covers the active units by default, `--all` every unit, and `--unit=<unit>` any one unit, closed ones included, the rows of a CLOSED unit carrying the label `closed`. The verb lists the units through the active listing's one call, asks each unit's `search.query` uncapped (`--limit=0`), keeps one entity type with `--type` (task, entry, finding, lane, lane_entry, session, all), merges the units in the board's unit order with each unit's rows in their order, and applies `--limit` (a positive whole number, default 20) once, `total` counting every merged row. Each row carries `module` (unit), `container` (the unit data declaration's key pattern for the row's section and entity type, the unit filled in, such as `<unit>/backlog`; a lane row's the address form `<unit>/lane/<lane>/<recipe|journal|report>`, since the lane key names the record's file layout), `type`, `id` (the address path after the type segment: a task slug, an entry slug, a finding NAME, `<lane>/<recipe|report>`, `<lane>/journal/<slug>`), `address` (`unit#<unit>/<kind>/<id>`), `snippet`, `read` (`ctx unit get <path>`), and `label` when the unit is closed; no score and no section key. A row with no addressable entity (an artifact preamble, an anchor line, a lane journal outside an entry) carries no address, its id the unit (or the lane) and its read the artifact's whole view (`ctx unit load <unit>`, `ctx lane show <unit> <lane> journal`). `--json` answers `{query, mode, total, rows}`; the text view prints a count line, one line per row (its type, its address or container, its label, its snippet), and a read hint; zero hits is rc 0. `--mode` defaults to `exact`: a line of the record text matches when it carries the query as a substring, ASCII letters compared without case (every other byte matches exactly) and a column-0 comment never matching, one row per matching entity and section, in record order, its snippet the first matching line with its field label and quotes trimmed. A ranked mode is a driver's own, asked for by the name its descriptor registers; a mode the unit's records cannot answer refuses rc 1 `ERR_CAPABILITY_UNSUPPORTED` naming the answerable modes (posix registers `exact` alone). The unit state is never searched. Under the `ctx search` fan-out marker the unit answers entities only (tasks, entries, findings, lane recipes and reports), a type it does not hold answers zero hits, and a mode the driver does not register falls back to `exact`. A sole `help` (or `--help`, or `-h`) prints the usage, while `help` with arguments after it is the query, as `ctx search` hands it; a query cannot begin with a dash, which reads as a flag and refuses (no end of options marker, a stated limit). The retired positional unit, `--entity`, and `-l` refuse rc 1 naming the new form, as do an unknown flag, a bare value form (`--limit 5`), `--all` beside `--unit`, an empty query, and a limit that is not a positive whole number; a `--unit` no store holds refuses rc 1 `ERR_ENTITY_NOT_FOUND`.

#### Reading one entity: ctx unit get
- `ctx unit resolve` is retired into `get`: the engine keeps the name on its static list of retired record verbs, so a call refuses rc 1 printing `ctx unit resolve retired: use get <unit>/<kind>/<id>, the path everything after unit# in an address`, and no module can claim the name; the section cut and the lane journal entry form it carried live in `get`.

#### One entity by its path: ctx unit get
- `ctx unit get <unit>/<kind>/<id> [--json]`: prints exactly one record entity whole in its canonical layout, the path being everything after `unit#` in the entity's address: `<unit>/task/<slug>` (with its `REFS`, which the `task show` text view leaves out), `<unit>/entry/<slug>`, `<unit>/finding/<NAME>`, `<unit>/lane/<lane>/recipe` and `<unit>/lane/<lane>/report` (whole, or one section with `/<SECTION>`, the span of the section's last head), `<unit>/lane/<lane>/journal` (the whole lane journal, as `ctx lane show` prints it), and `<unit>/lane/<lane>/journal/<slug>` (one lane journal entry). It never prints a container listing or the unit state (such a path refuses rc 1 naming the forms), takes no lock, so a `get` inside a write is safe, and a missing entity refuses rc 1 with `get: error: '<path>' not found (ERR_ENTITY_NOT_FOUND)`, so a dangling reference reads gone. `--json` prints the one entity as JSON: the storage function's answer for a task, an entry, a finding, or a whole recipe, report, or lane journal; `{unit, lane, artifact, section, content}` for a section, its content the lines the text form prints; and `{unit, lane, artifact, entry}` for a lane journal entry, that entry's object alone, never the lane journal. `get` is the shared read verb: a module that answers search answers get, so a search row's read is always `ctx <module> get <path>`; the docs module answers `ctx docs get <repo>/<slug>/<key>` the same way. `resolve` stays beside it.

#### The named looks: ctx unit list and refs-to
- `ctx unit list [--active|--all] [--repo=<repo>]`: the default and `--active` print each ACTIVE unit bytewise by name, its slug, `current_anchor`, derived `next:` line, and objective lines, a blank line between units, then `closed: <n>`; `--all` prints one line per unit, ACTIVE and CLOSED, `<slug> [<STATUS>] <current_anchor>`, the status as stored; `--repo=<repo>` keeps the units whose repos name the repo in either form (the `--active` closed count then counting the CLOSED units touching it), and a repo no unit touches refuses rc 1 naming the repos the units know; when the storage layer is not made yet the listing prints `no units yet` whatever the flags; `--active` with `--all`, a repeated flag, an empty `--repo`, any other flag (`--json` among them), or an argument refuses rc 1 with the usage; a refusal prints its line alone, never the deprecation warning. The leftovers nudge rides the listing: the first listing of the day (the local date) runs the leftovers probe once (`storage.leftovers` over the unit namespace, the count `ctx unit diagnose --leftovers` prints) and, when the record's storage holds anything beyond its documents, a rc 0 run prints after its answer one line, `NUDGE: the record's storage holds <n> items (<bytes> bytes) beyond its documents; the human's word comes first: tell them, show them the dry run ctx unit migrate --sweep --dry-run --all, and sweep only on their word, moving the leftovers into a backup or deleting them (--delete)`, the counts every kind of both roots summed with their bytes, so equal to the dry run's closing line; every other listing that day probes nothing and prints no nudge. The day's mark is `.contexture/tmp/unit-leftovers.stamp` (`<date> <items> <bytes>`, `<date> unknown` for a refused probe, so a driver without the probe pays one refused call a day, `<date> probing <pid>` while a listing probes, or `<date> sweeping <pid>` while a sweep runs); a sweep run writes the sweeping mark with its own pid before it sweeps and removes the stamp after, a stop by a signal included, so no listing probes during a sweep and the next one measures again, while a sweeping mark whose pid is gone, or that names none, reads as no mark; the count is written, and the nudge printed, only while the stamp still reads the listing's own probing claim, so a sweep's mark or clear, or another listing's claim, made during the probe stands; a drawer that cannot keep the mark probes nothing. The retired `active` and `units` verbs of `ctx unit` each refuse rc 1 as an unknown verb, and `list` takes their place among the reserved module names.
- `ctx unit refs-to <unit>|<full address> [--all] [--json]`: `refs-to <target>: <n> referrers`, then one row per referrer item, `  <unit> <kind> <id> <ref>`: every REF and REFS value naming the target (a unit name matches every ref into that unit, a full address itself and every address below it, a `file#<path>` its symbols `file#<path>#<symbol>` too) and, for a unit target, every unit whose `ref_sessions` name it (`<unit> session <unit> ref_sessions`); the active units by default, `--all` every unit, closed ones included, which reads the whole record (about 0.2 s per unit); none refuses rc 1 with `ERROR: no unit references <target>`, and a retired short or legacy form refuses rc 1 naming its full address as every write does (`journal#x` names `unit#<unit>/entry/x`).

Together with `entry show`, `entry list`, `entry closure`, `finding show`, and `get`, these answer the foreseeable questions over the record in bounded form, so no one improvises a grep that over-reads: every miss is loud, rc 1 with a named error, never a plausible empty.

### Subagent lane management: ctx lane

Subagent operations are governed through the dedicated top-level `ctx lane` module:

```bash
.contexture/ctx lane create <unit> <lane-slug> --goal="..." --branch="..." --writes="..." --scope="..."... --report="..."... [--ref=...]... [--task=unit#<unit>/task/<slug>]... [--decision=unit#<unit>/entry/<slug>]... [--rhythm="<name> <N> <GATE>"] [--fact="..."]... [--substrate="..."]
.contexture/ctx lane show <unit> <lane-slug> [recipe|journal|report] [--json]
.contexture/ctx lane record <unit> <lane-slug> --what="..." [--slug=...] [--thread=...] [--ref=...]...
.contexture/ctx lane report <unit> <lane-slug> [--body="..." | stdin] [--json]
```

- `create`: the dispatcher's act: the verb composes the recipe from the brief flags (the five required ones, `--goal`, `--branch`, `--writes`, `--scope`, and `--report`, the last two repeatable, and the optional `--ref`, `--task`, `--decision`, `--rhythm`, `--fact`, and `--substrate`, each as `--name=value` or `--name value`), writes the fixed `BOUNDARY`, `BOOT`, `JOURNAL`, and `REPORT` blocks from its own text, stores the recipe with an empty lane journal (`lane.create`, the composed recipe its one document), and prints `lane created: <lane> in <unit>`, an empty line, the label line, and the three line dispatch prompt, which is never stored. It never reads stdin. Before its one storage call it refuses rc 1 with one stderr line: the missing required flags in one line naming each with its purpose (`lane create: error: missing --goal (...), --scope (...); the brief comes only as flags, stdin is never read: ctx lane help create (ERR_INVALID_ARGUMENT)`), an empty value counting as missing; an empty `--ref`, `--task`, or `--decision`, refused as malformed like every other REF write; an unknown flag or an extra argument; a trailing flag with no value; a single flag given twice; a value holding a newline or a carriage return; a value that is not valid UTF-8 (`lane create: error: <flag> is not valid UTF-8`); a malformed unit, lane, ref, task (`unit#<unit>/task/<slug>`), or decision (`unit#<unit>/entry/<slug>`); and a rhythm by the rule `ctx unit record` checks it by, with its refusal lines. Every ref, task, and decision is then looked up through its owner's `get` before the storage call. An existing lane refuses rc 1 (`ERR_ENTITY_EXISTS`) with its recipe unchanged. The recipe lands through this command, never as a file the dispatcher writes.
- `show`: prints the recipe, the journal, or the report (the report by default) as stored, its trailing newlines collapsed to one; an absent document prints one empty line rc 0.
- `record`: logs action traces into the subagent's lane journal; the unit module composes the slug from the date and time the verb sends, a second event in the same second taking `-1`; a given slug the lane journal carries refuses rc 1; `--ref` repeats; an absent lane refuses rc 1.
- `report`: writes the lane report from `--body` or stdin, printing one line with the stored size (`lane report written: <lane> in <unit> (<bytes> bytes)`), or reads it back when neither is given; the body reaches the unit module raw on stdin and the storage layer as one value, so a report of any size lands (a 2 MB report is a gate case). With no `--body`, it reads stdin whenever stdin is not a terminal, and no POSIX sh tells an idle open pipe from a slow writer, so under an open pipe it waits until the writer closes. The scripted read path is `ctx lane show <unit> <lane-slug> report`, which never reads stdin; `report`'s read mode is for a terminal (or a call fed `</dev/null`).

A refusal the shared verb library prints for a lane verb (a value or a document that is not valid UTF-8, a NUL byte, a missing unit module data script) names the verb as its own refusals do (`lane <verb>: error: ...`). Every lane write refuses a `CLOSED` unit with rc 1, and a report holding a NUL byte or bytes that are not valid UTF-8 refuses rc 1 (`lane report: error: the report holds a NUL byte (ERR_INVALID_ARGUMENT)`, or `is not valid UTF-8`) before any write: the document lands in a file before any other read, so a NUL is refused rather than dropped. `--json` prints `lane.get`'s answer for a read (`content` holds the document) and `lane.write_report`'s for a write.

Isolating lane operations into `ctx lane` prevents accidental pollution of the unit's main journal upon argument omission.

### ctx unit load: the load and the refs form

Returns the map plus one page of the load: state, backlog, knowledge, the live journal, and any declared `ref_sessions` under read-only banners. The unit module answers the unit whole over the storage layer (`session.load`, or `session.refload` for the refs form) and base renders and pages it. The map names each section with its line count and pages, then the write-scope trailer, which names the unit (`WRITE SCOPE: unit <unit> + repos: [...]`), never a storage location; pages cut at block boundaries, never mid-body: a page ends before the block that would pass about 500 lines or about 40KB, whichever binds first, and a single block larger than the budget renders whole on its own page. The backlog section renders its DONE task blocks compactly, keeping only the task line, `STATUS`, `OBJECTIVE`, and `DESCRIPTION`; open and statusless blocks render whole, and the record itself is never edited, so the full body stays one `get` away. An incomplete call opens with `LOAD INCOMPLETE` and instructs the next call in its last line; the final page opens with `LOAD COMPLETE` and hands off to stamping the new period (`stamp the new period: ctx unit stamp <unit>`).

The load and the board compress the viewed unit's own addresses: their callers pass the render flag `RV_COMPRESS=1` to `lib/render.awk`, whose output function prints every `unit#<unit>/` of the viewed unit as `~/` under one legend line, `legend: ~/ stands for unit#<unit>/ (ctx unit get prints the full address)`: the load prints it at the end of its map block, before the page header, and the compression runs before the paging, so the section line ranges and the page boundaries are counted over the compressed lines; the board prints it one line after its head (the board section inside a load prints none). The item reads (`task show`, `entry show`, `finding show`, `get`, `lane show`) never pass the flag, so they print the full canonical form, and stored data is always full; a `~/` token copied from a view, with or without its quotes, refuses at every write and as a `refs-to` target as a compressed view form, naming its full address. A literal `~/` in stored prose (a home path) prints the same as the compressed token, never escaped, as the help of both verbs states.

```bash
.contexture/ctx unit load <unit>
.contexture/ctx unit load refs <ref_1> ... <ref_N> [<page>]
```

Read every page the map reports. A missing state is fatal (`ERROR: missing state: unit <unit>`); a missing backlog, knowledge, or journal is loud and nonfatal, with a placeholder standing in its section; the warning names the artifact and its unit (`WARNING: missing knowledge: unit <unit>`), never a storage location, so a reference unit the storage layer does not hold reads the same under every driver. Every verb message follows that form: an error or warning names the artifact and its unit (`<artifact>: unit <unit>`, a lane artifact as `lane <lane> <artifact>: unit <unit>`), never a record path, whatever the driver. The journal section renders the board from the same answer, so the extraction has one home; the board's open threads and open tasks ride that section unchanged.

The cut is budgeted twice, about 500 lines or about 40KB, whichever binds first, so a page stays under the harness's output cap in practice; the one residual is a single block that exceeds the budget alone, and it renders whole on its own page. If a harness still truncates such a page, it prints a notice naming its saved copy of the command's output: that copy is the command's own output, and reading it is sanctioned by `@laws#workspace-confinement`, read-only, that named file alone. Routing the same content through temp files stays unsanctioned. The in-workspace fallbacks need nothing outside: `ctx unit board`, `ctx unit task show`, and `ctx unit get` recover the same content through the verbs.

The refs form is the on-demand consult: it streams the named units alone, each composed exactly as the unit load composes a reference, and pages them locally with its own map, banner, and tail, so a large reference never truncates. A missing ref is fatal; zero refs, or a numeric token in a ref position, prints the usage at rc 1; a unit named `refs` stays reachable through the escape hatch `ctx unit load refs refs`.

### ctx unit stamp: the new period

The unit module moves `current_anchor` from `A<N>` to `A<N+1>` and appends the anchor line `@anchor A<N+1> <date>` (today's date, which the verb sends) in one atomic write (`session.stamp`); the verb prints the transition after the stamp hooks. The anchor carries the period's number and date, no receipt text: a text argument refuses rc 1 `ERR_INVALID_ARGUMENT` naming the form (`stamp: error: stamp takes the unit alone (ctx unit stamp <unit>) ...`), a `CLOSED` unit rc 1, and a malformed stored anchor rc 2 (`ERR_STORAGE_CORRUPT`), with no partial write. An anchor written by an earlier release with its receipt text (`("continues A<N-1>", attention: ...)`) keeps that text as content and reads back as stored.

```bash
.contexture/ctx unit stamp <unit>
```

`.contexture/ctx unit entry list <unit> --anchor=A<N>` lists the entries written in one period; `entry list` without a filter prints every entry with its anchor, the map of periods.

### ctx unit board: the board

Returns the live board: every unclosed entry with its body whole, then the open task slugs and the open threads with their targets, each list under its nudge line; an empty list prints nothing. Live means unclosed: the set is the journal entries that no later closure names. Takes one form, a unit slug:

```bash
.contexture/ctx unit board <unit>
```

The unit module answers the board (`session.board`): the live entry occurrences in journal order with their spans, the backlog slugs whose status is not DONE, and the live threaded entries; base renders them under the opener that names the counts, and a missing backlog is loud on stderr with no tail. Liveness is positional: a closer closes the occurrences of each target slug that stand before it, and the closure parse reads the target field only, so a slug mentioned in a closure's reason prose can never close anything. The output is the set, whole, with no hand-picking and no per-entry reads. Any other invocation of `ctx unit board` fails loudly: a path, an extra argument, or a flag.

`ctx unit load` renders this board for the load's journal section; run directly, `ctx unit board` is the updated board: the open entries, the open threads, and the open tasks in one stream. The refs form renders the board per reference unit, so a consulted unit streams its live entries too.

The board ends with the rhythm in force line, the line `ctx rhythm current <unit>` prints, at no added dispatch: `session.board`, which already reads the whole journal, also answers the unit's last stamp in record order, open or closed (`rhythm`: its slug and stamp, null when none), and the board verb turns it into the line through the rhythm module's resolve, run by path after the render, never a nested ctx call or a second entry listing. So a board served from the deprecated root still prints one warning, a board run outside ctx keeps a silent stderr, and with the rhythm module absent the board prints its view alone. `ctx unit refresh` carries the line through the board; the load's journal page renders the board view without it, since the load reaches the rhythm in force one boot step later through `ctx rhythm current`.

### The state acts: refs, close, reopen

```bash
.contexture/ctx unit refs <unit> [<unit> ...]
.contexture/ctx unit close <unit>
.contexture/ctx unit reopen <unit>
```

The next move is not a state act: `ctx unit list` derives it from the backlog (the first `IN_PROGRESS` task, else the first open task, the board's rule of every status but `DONE`; a legacy or unknown status reads as stored), and the load's backlog page carries it, so no verb stores a pointer and `ctx unit next` retired (below). `refs` sets the read-only mounts; every named unit must exist and differ from the unit, no name twice; zero units clears them. `close` marks the unit `CLOSED`: the unit module answers the unit's audit and its open tasks with the move, base prints them as warnings on stderr (it never refuses for them), then the close hooks fire. `reopen` marks a `CLOSED` unit `ACTIVE` again so its work can resume; each refuses a unit already in the target status (`ERR_INVALID_TRANSITION`). Every form validates its inputs before any write: a refusal is loud, rc 1 with zero partial writes, and a landing prints what it wrote.

### Retired verbs

`append`, `amend`, `query`, `flip`, and `drop` left `ctx unit` in v0.55.0 with the record contract, since no markdown crosses the interface and every act has its typed verb; `next` left when the pointer became a presentation-time derivation, since it had nothing to write. The names stay reserved (no module may claim them), and each call, or `ctx unit help <name>`, prints its replacement with rc 1:

| retired | its replacement |
|---|---|
| `append` | `record`, `task add`, `finding add` |
| `amend` | `task update` |
| `query` | `entry show`, `entry list` (`--group`, `--anchor`), `entry closure`, `finding show`, `get`, `search`, `list`, `refs-to`, `lane show` |
| `flip` | `task start`, `complete`, `reopen` |
| `drop` | `task drop` |
| `next` | `list` (the next task is derived from the backlog) |

The raw block stdin inputs of `record`, `task add` and `update`, `finding add` and `update`, and `ctx lane record` retired with them.

### Moving a record between backends

No command moves a record between storage backends, since a move can need judgment a verb would hide (legacy shapes only a posix file holds, files outside the record, a write one backend refuses and another accepts). A record reaches another backend through the agent re-entering it with the ordinary verbs under that backend (`bootstrap`, `task add` and its moves, `finding add` and `supersede`, `record`, `stamp`, `lane create`, `lane record`, `lane report`), and a docs corpus through the `ctx docs` write verbs; switching `storage.driver` stays the human's act. So an fts5 store holds only what the verbs write, and legacy record shapes live in posix files alone. `unit.export`, `unit.import`, and the dump format, added while v0.55.0 was built and never released, left the contract before it shipped. Today's `ctx unit migrate` is no backend move: it moves units between the declared roots of the one posix store (below, The record root and its deprecated root), and its backend flags are no unit and refuse rc 1.

### The record root and its deprecated root

The record lives under `.contexture/units/`; releases before the move kept it under `.contexture/sessions/`, which the unit module now declares as its fallback root. The move is gradual and needs no step of its own: the posix store reads a unit from the root first and then from the fallback, and its own write (the unit module's one `store.batch`) moves the unit's folder from the fallback to the root by one rename under the namespace lock it already holds, before it writes, so a unit moves whole at its first landing write, usually the boot stamp, and a write stays the one store call it was before the move; a refused write and every write to a CLOSED unit move nothing, and a unit both roots hold refuses the write with nothing written. The move that empties the fallback root removes `.contexture/sessions/` in the same call (one `rmdir`, which refuses silently while any folder or file remains, so a root still holding one stays). A run whose reads came from the fallback and that ends rc 0 prints, after its answer, one line, `WARNING: the record was read from its deprecated root; each unit moves at its next write, and ctx unit migrate --all moves the rest when the human chooses`, which every verb relays (audit, board, and diagnose among them); a refusing run prints its refusal alone. The line is a reminder, not an instruction to an agent: the sweep is the human's choice. `ctx unit migrate <unit>...` or `ctx unit migrate --all` sweeps the units nobody writes, the closed ones among them: it applies the record's migrations to each unit under its unit lock, the root move first, then the pointer rewrite (below, The record's migrations), prints the census and `migrated: <n>` (a second run `migrated: 0`), stops at its first refusal naming the unit, removes the deprecated root once it is empty, even when it moves nothing (a fully moved workspace keeps no empty `.contexture/sessions/`, while the storage layer keeps its empty root when it holds no unit, the sweep then promoting nothing), and when the storage layer keeps no fallback root (fts5) prints that nothing moves before its census. The fallback read and the promotion are temporary; a later release retires them once no unit remains under the old root. The fts5 database keeps its name, `.contexture/sessions.db`.

### The record's migrations

`ctx unit migrate [--dry-run] [--forward=<old prefix>=<new prefix>] (<unit>...|--all)` is the record's migrations: each run applies every pending migration per unit under the unit lock, the root move first, then the pointer rewrite, which turns every pointer in every field into its full address, `<owner>#<path>`. The rewrite is the data function `unit.migrate` beside the record's 35 operations: it reads each artifact value as stored, runs `lib/migrate.awk` over it, and writes the changed values back through one `store.batch`, never through the record operations, so a CLOSED unit is reached (the one named exception to the CLOSED freeze: the rewrite changes how a pointer is written, never what it points to). The tokenizer splits a line on blanks, trims surrounding quotes, backticks, brackets, backslashes, and trailing punctuation, and rewrites a token in place keeping the trimmed characters; a token gluing pointers together is cut at a comma, a semicolon, or the punctuation before a later pointer start (never at a slash or a hash, so `lane#l/journal#x` stays whole), a trailing possessive `'s` is cut when the pointer without it rewrites, and a rewrite whose address holds a segment outside letters, digits, dot, underscore, and dash, or breaks its owner's form, is kept and counted as a pointer glued to text (`journal#x/journal#y`). The rules per class: the short unit forms (`journal#x`, `knowledge#N`, `backlog#x`, `lane#l/art`, `lane#l/art#C`) and their legacy spellings (`lanes/l/art[.md][#C]`, `journal.md#x` and its two kin, under `file#` or `./` too, ahead of the root file rules, `task#`, `finding#`, `entry#`, `lane#<unit>/<lane>/<art>`, `../<unit>/journal.md#x`, `../<unit>/lanes/l/art`, and a pointer into a record storage path of a unit the storage layer holds, in either root, active or closed (the verb lists the held units once per run and hands the list to the library), `[.contexture/](sessions|units)/<unit>/journal.md#x` and its two kin or `[.contexture/](sessions|units)/<unit>/lanes/l/art[.md][#C]`, in a REF value and in free text alike) become `unit#<unit>/entry|finding|task/<id>` or `unit#<unit>/lane/<l>/<art>[/<SECTION or slug>]`, a dangling one too, while a storage path naming a unit the storage layer does not hold (another workspace's record cited by path, counted as `storage path of a unit this record does not hold`, since a local `unit#` address would change its meaning) and a storage like path under a backup, another repository, or an absolute path keep their bytes, `file#` of the same path in a REF value and prose in free text; `IDEAS.md#<slug>` under any prefix becomes `store#ideas/<slug>` and a bare `IDEAS.md` mention `store#containers/ideas`, the ideas container's declaration record, which stays readable after a later drop of the container; a corpus doc path `docs/<repo>/<slug>.md[#<id>]` of a repo the docs module lists becomes `docs#<repo>/<slug>/<id>` (`header` when no id; a `path:line` spelling in a REF value takes the header address and leaves the token in NOTE, and in free text stays prose); in a REF or REFS value every other file path takes the `file#` owner with its bytes as written (a bare root file name `file#./<name>`, a lane relative `recipe.md` the enclosing lane's address, a `path:line` spelling `file#<path>` with the token in NOTE, a path followed by a colon, as in `src/a.ts: the parser`, the path's own address with the whole value in NOTE), while file paths in free text stay prose. A REF or REFS value keeps only a full address (an owner shaped `<owner>#<path>` whose owner is no retired short owner, so a dangling owner stays like a dangling `file#`): the text beside its pointer, and a whole value no rule rewrites (prose, a stray word or number, a placeholder, a law pointer, a URL, a completion receipt prefix, a pointer glued to text, a lane relative token whose anchor holds blanks), moves word for word to a `NOTE: <text>` line on the same item, which the canonical layout keeps as an extra field; a `lane#` or `lanes/` section anchor followed by more words (`lane#l/report#A B`) leaves the artifact's address, `unit#<unit>/lane/l/report`, and the whole value in NOTE; a REFS list splits only at commas outside double quotes and parentheses; only migrate writes NOTE. In a lane recipe line the annotation stays beside the rewritten token: a REFS block line is a comma separated list, split outside double quotes and parentheses, each item's first token rewritten by the REF rules and the rest of the item free text, every separator and annotation kept in place (an item whose first token is no pointer stays free text whole), and a TASKS or DECISIONS line is free text, its prose never rewritten. Kept, each counted and named: the placeholder list (`task#nope`, `finding#NAME`, `lane#L`, `lane#L/journal#X`, any `lane#` naming a one letter lane's artifact, and any token holding `<`, `>`, `*`, or `...`), the completion receipt prefix `backlog/<slug>`, law pointers `@laws#<slug>`, URLs, prefix mentions with no target, CLOSES and SUPERSEDES lines, the text NOTE holds, the reference units, column-0 `#` heading and comment lines, column-0 `@` head lines (the bootstrap `@anchor` line copies the unit objective; its tokens are counted as `excluded: head line`), slash words and system paths in free text. The exclusions stand in a table inside the library, each pinned by a test. The verb prints the census before (every pointer shaped token of every field and every REF and REFS value, by class, as rewritten, kept, or moved to NOTE, the three summing to the total), the census after (what is left to rewrite, any REF value that is no full address included, 0 after a run), the residual scan (the data function's own awk, apart from the tokenizer, over what each unit is left holding: every token still holding a retired short owner, its `.md` spelling, a `lanes/` artifact, a record storage path to a lane artifact (after a path character too), a `../<unit>/lanes/` path, or `IDEAS.md`, outside NOTE, CLOSES, and SUPERSEDES lines and the reference units, tallied by the class the census after gives the same token on the same line, trailing colons stripped on both sides (the scan cuts the colon a census row keeps, as on a kept `REF: "store#memos/x:"`), or `not in the census`, so the census is checked by an instrument that does not share its blind spots), one line per unit, the paths of the full token lists in the workspace scratch (`.contexture/tmp/migrate/<run>/`, `before.tsv`, `after.tsv`, and `residual.tsv`, each census row ending with its line), then `migrated: <n>`, the units either migration changed. `--dry-run` computes the same rewrite and census, takes no lock, and writes nothing, the proof before a live run.

`--forward=<old prefix>=<new prefix>`, given once per run beside `--dry-run` and before the units, forwards the addresses of entities that moved to a new owner (a store container's records adopted by a module, say). Each side is a full address prefix, an owner, a hash, and an optional path prefix, ending in a slash or a hash (the side plus one character passes `lib_ref_ok` and names no retired short form), the value split at its first equals sign; a side that is no such prefix, a side holding a placeholder character (an angle bracket, a star, or three dots, which the rewrite excludes ahead of the forward, so such a forward would rewrite nothing), a side ending in neither a slash nor a hash (it cuts inside a name: an old `store#memos` would take `store#memosx/n1` too), a `file#` new prefix naming a path outside the workspace (absolute outside the workspace root, or climbing above it, by the write check's own rule, where a `file#` address answers by its shape alone, so no forwarded target would be checked), two prefixes where one starts with the other (equal ones included, since a forwarded address that still started with the old prefix would be forwarded again by the next run), and a second `--forward` refuse rc 1 before anything is read (`migrate: error: malformed forward '<value>': <why> (ERR_INVALID_ARGUMENT)`, the why naming the prefix and its fault, or `migrate: error: --forward is given once per run (ERR_INVALID_ARGUMENT)`). Every pointer token starting with the old prefix and holding more after it, in a REF or REFS value, a lane recipe's REFS block item, and free text alike, becomes the new prefix plus the same rest: the class sits ahead of the rule that keeps a full address as written, after every exclusion, so a placeholder (`store#memos/<id>`) stays, and a token equal to the prefix alone is no target; a pointer an earlier class rewrites into an address the forward takes is forwarded in the same run (its class gaining `, address forward`), except a lane section split, and a path followed by a colon keeps its whole value in NOTE word for word, byte equal to the run without the forward; a REF value whose first token ends in a colon is tested for the forward without its colon, and when it forwards the colon goes to NOTE as the path rule sends it (`path with a trailing colon, address forward`: the whole value for an annotated one, the token for a bare one, a recipe REFS item keeping the colon beside the forwarded address), while one whose address does not answer keeps its bytes. Before any rewrite and before any lock, the verb calls the data function `unit.migrate --collect` over the same units (no lock, nothing written, `lib/migrate.awk` in its collect mode appending each candidate's forwarded address to `forward.cand` in the census folder), then checks each distinct forwarded address once through `vb_ref_state`, the write check's own probe (each owner probed once per run, `ctx <owner> get <path>` once per address, `file#` by the core), and writes the answers to `forward.tsv`, which both engine passes read, as the held set is handed to both. A token whose address answered is rewritten (`address forward`); one that did not keeps its bytes, counted as `address forward, target not found`, `owner not installed`, `owner has no get verb`, or `target not checked` (written after the check; the next run checks it), and a REF value keeps it as the full address it already is. The verb prints `forward: <old prefix> to <new prefix>, <n> distinct addresses checked through their owner's get, <a> answer, <m> do not; the answers in <run>/forward.tsv` before the census, and the residual scan also lists every token still holding the old prefix, tallied by its census class. A second run forwards nothing: no forwarded address starts with the old prefix, and only the targets that did not answer are checked again.

`ctx unit migrate --sweep [--dry-run] [--delete] (<unit>...|--all)` runs the sweep alone: no other migration runs and no ref is rewritten. What the record's storage holds beyond its documents (the keys the unit verbs read: each unit's state, backlog, knowledge, and journal, and each lane's recipe, journal, and report, which the unit data file's document rules and its `unsearched: <unit>/state` line name) is moved into `.contexture/backups/sweep-<stamp>/unit/<root|fallback>/<relative path>`, the stamp `<YYYYMMDD-HHMMSS>-<pid>` one per run and the folder made only when something moves, or with `--delete` removed outright with no backup kept; a folder holding no document below it goes as one item, and a deprecated root the sweep leaves empty is dropped. Every kind the leftovers probe names is taken but one: stray files, folders outside the key shape, empty folders, symbolic links (moved or removed as links, never followed), special files, lock or write remnants, keys the root shadows, and the keys outside the document rules (old lane scratch written as `.md` files under a unit, say); a folder the sweep cannot read or enter is never moved or removed, nor any folder above it, and its rights are never touched: the sweep leaves it and names how many it left, the rights the human's to fix. A name holding a newline anywhere in a unit's reach refuses the sweep rc 2 naming the count, and so does a symbolic link at a document's key path in what it would take, since a read follows the link; the dry run refuses alike. The storage layer acts in bounded batches that release the namespace lock between them, so a lane journaling into another unit during a sweep lands within a batch. The data function `unit.sweep` sweeps each named unit (one the storage layer holds), or with `--all` every first key segment the storage layer lists in either root, under its unit lock through the library's `store_sweep --prefix=<unit>/` (that folder of both roots), then with `--all` the entries at the top of each root that hold no key (`--loose`), so the two together cover both roots whole; CLOSED units are reached, since the sweep is no record operation. Before any walk or write the sweep refuses rc 1 `ERR_INVALID_ARGUMENT` unless the installed unit declaration, as the storage core's data reader answers it, declares the state unsearched (`unsearched: <unit>/state`), since without that line every unit's state reads as a key outside the document rules (a partial payload sync, say); and before anything of a unit is swept, the dry run alike, it refuses rc 1 `ERR_ENTITY_EXISTS` a unit, or a key segment, whose keys the storage layer holds in both roots (a key of the deprecated root that the root holds too, which the sweep would otherwise take as a key the root shadows), as the migration's root move refuses such a unit: a dry run reads the count from its own answer, a run asks the storage layer's dry run of that unit first while the deprecated root is walked. The verb prints one line per unit, `unit <unit>: <kind> <n> (<bytes> bytes), ...; <e> folders emptied` or `unit <unit>: nothing beyond the documents`, a first key segment holding no unit state `outside the units, key segment <segment>: ...`, one for the top of the roots, `outside the units: ...`, then one closing line: `swept: moved <n> items (<bytes> bytes) into the backup stamped <stamp> and emptied <e> folders`, `swept: deleted <n> items (<bytes> bytes) with no backup kept and emptied <e> folders`, or `swept: nothing beyond the documents; nothing moved`; a line whose sweep left unreadable folders ends `, leaving <n> unreadable folders untouched (their rights need fixing)` (`nothing swept, leaving ...` on a unit line, `swept: nothing moved, leaving ...` when only those remain); `--dry-run` takes no lock, writes nothing, and prints the same lines, its closing line `dry run: would move|delete <n> items (<bytes> bytes) and empty <e> folders; nothing written`. A second run moves nothing, and every document, and so every unit view, reads byte equal after. The first item the sweep cannot move or remove stops it rc 2, its line naming the unit, the kind, and the items swept before it, which stay swept; a refusal midway first prints the line of every unit swept before it and one line with the run total swept before the stop (those units' items and the items the refused call swept before it) and the backup's stamp when one was made: `stopped: swept <n> items before the stop, moved into the backup stamped <stamp>`, `stopped: swept <n> items before the stop, deleted with no backup kept`, `stopped: nothing swept before the stop`, or for a dry run `dry run: would stop after sweeping <n> items; nothing written`, then the refusal. A hangup, an interrupt, or a termination of the verb stops the sweep: the verb runs its data script as a held child, sends it and every descendant a termination (a background child ignores an interrupt), waits for each to end at its next step with its locks released (killing any still running after 10 s), names the stop on one stderr line with the run's stamp in the move form, and exits 129, 130, or 143. `--delete` without `--sweep` and `--sweep` beside `--forward` refuse rc 1; a storage layer without the sweep (fts5) refuses rc 2. The output names no path; the backup's place is this guide's to name. A run, never a dry run, holds back the leftovers nudge of `ctx unit list` while it sweeps (the day's mark reads sweeping with the verb's pid, so a mark whose verb is gone holds nothing back) and removes the mark after, a stop by a signal included, so the next listing measures again. The sweep is the human's act: the dry run first, then the move or the delete on the human's word.

### ctx unit diagnose: the storage view

`ctx unit diagnose [--leftovers] [--json]` prints the workspace root, the configuration, the resolved storage driver with its source and status, then the driver's descriptor as lines (`contract`, `driver`, the version, the store function count, the registered search modes' names, the optional capabilities), the storage health (`storage.health unit`: the backend alone, over the unit namespace's own store and lock, so a docs write never reads as a locked record; a probe that cannot answer prints `error` with the store absent), and the ACTIVE unit count from the record's own listing (`session.list`), never from the health answer; a listing that refuses leaves the count unknown, never 0: the line reads `active units: unknown (<message>)`, carrying the listing's refusal message and code (for example `unknown (cannot read key '<unit>/state' in namespace 'unit' (ERR_STORAGE_READ))`), and nothing reaches stderr. `--json` prints one compact object `{workspace_root, config {status, driver}, driver {name, source, status, descriptor}, storage {health, detail, store, active_units}}`, the descriptor being the capability answer and `active_units` the record's count, `null` when the listing refused. Every line prints whatever a read answered, a part it could not read named in its own line (a driver error, a health error, an unknown count), and diagnose exits 0; an unrecognized option exits 1, and a missing storage resolver or scratch folder 2. The descriptor is read through the resolver's handshake, afresh on every call. `--leftovers` adds what the record's storage holds beyond its documents: the library's `store_leftovers` over the unit module's own namespace (the posix driver's `storage.leftovers`, a read only whole walk of the record's root and its deprecated root, so it runs only on the flag) rendered by `store_leftovers_text` in its summary form, a `leftovers:` line and one indented line per root, `root: <documents> documents in <entries> entries, nothing beyond them` or `; beyond them:` with each kind found and its count and bytes (stray files, folders outside the key shape, empty folders, symbolic links, special files, unreadable folders, lock or write remnants, keys the root shadows, keys outside the document rules), or the root's state (`absent (not made yet)`, unreadable, a symbolic link), never a path; `--json` adds `storage.leftovers`, the probe's answer whole; a probe that refuses (the fts5 driver keeps no file tree and answers its unknown function line) prints `leftovers: unknown (<message>)`, `null` in `--json`, and diagnose still exits 0. Without the flag the output and the cost are unchanged. `ctx unit migrate --sweep` clears what it names (The record's migrations).

### ctx unit audit: the repair instrument

Returns the record's defects, each flagged with a line or a slug, and exits nonzero when any fires. Takes one form, a unit slug:

```bash
.contexture/ctx unit audit <unit>
```

The unit module checks the record (`session.audit`) over the stored values and answers its findings as data; base prints them in a fixed order (the line-ordered grammar group first, then each record check ordered by position), so the output never depends on an awk's hash order. The record checks (dangling closer, unharvested knowledge, done without event, missing thread, the legacy duplicate warning) and the grammar checks (dateless slug, inline marker, bracketed field, slugless closer) run alike under every driver, the grammar checks finding broken text only a posix store can hold (a hand edit or a legacy file), and a finding that stands on a journal line prints its ` at line <n>`, the line of the stored journal value, under every driver. When the run is clean the verb also prints the open-thread tail: the entries whose `THREAD` names an act outside the unit and that no later closure names, each with its target. The tail is a display, never an enforcement: a thread that pauses stays open, and its line in the tail is the reminder it exists. The presence check runs from the enforcement era: an entry dated at or after `2026-09-18` that carries no `THREAD` line flags `MISSING THREAD` (the constant lives in the unit module's audit), so pre-era records stay quiet.

A task whose status is a legacy or unknown spelling is open by the board's rule (every status but `DONE`) and the derived next reads it, so the audit neither flags nor normalizes it.

The classes, and what each one asks for:

| flag | the defect | the repair |
|---|---|---|
| dangling closer | a `CLOSES:` or `SUPERSEDES:` names a slug no entry carries | the human's edit of the slug or the closer |
| slugless closer | a closer carries no valid date-slug target | the human's edit, pointing it at real entries |
| dateless entry slug | an entry name does not match the date-slug grammar | the human's edit of the entry's slug to the date-slug grammar |
| inline marker | `THREAD:` or `KNOWLEDGE:` sits on the `@entry` line | the human's edit, moving it to its own field line |
| bracketed field | a field line wrapped in brackets, as a shape's optional marker copied verbatim | the human's edit, writing the field bare or omitting it |
| missing thread | a post-era `@entry` with no `THREAD` line | the human's edit, declaring the `THREAD` line: what it awaits, or `none` |
| unharvested knowledge | a `KNOWLEDGE: true` entry that no closer names | harvest it at the next refresh; the entry then closes by reference |
| done without event | a `STATUS: DONE` task with no `backlog/<slug>: DONE` line in the journal | record the completion event |
| legacy duplicate slug (warning) | an older journal repeating an entry slug | nothing: it reads by position and leaves rc unchanged; a new repeat is refused at the write |

The audit is a repair instrument: fix what it flags and fill what is missing before the period ends; a note about a flag is not a repair. The verbs repair two classes: unharvested knowledge (a closer at the next refresh, `ctx unit record --closes`) and done without event (the completion event through `ctx unit record`, or `ctx unit task reopen` then `complete`, which writes the receipt). Every other class is a finding no verb can repair: it goes to the human, never to an agent's hand edit of the record or to an entry minted only to quiet it. The audit runs at refresh, close, and handoff, and close and handoff expect exit 0.

### ctx rhythm: the rhythm module

The rhythm module ships with the base in the workspace modules root, beside the lane module, and is the one surface for rhythms: an agent selects, reads, and resumes a rhythm through it and never reads a rhythm file by its path. Its three verbs:

```bash
.contexture/ctx rhythm list
.contexture/ctx rhythm show <name>
.contexture/ctx rhythm current <unit>
```

- `list`: one line per effective rhythm, `<name> | <origin> | use when: <trigger> | activation: <propose|auto>`, the workspace rhythms (`.contexture/rhythms/`) before the extension rhythms (`.contexture/extensions/rhythms/`), each in name order; a name both carry lists once, its origin reading `workspace, shadows the extension copy`. A rhythm is named by its file name; a file with no `use when:` line prints `(missing)`, and an activation the file does not state, or states as anything but `auto`, reads `propose`. The last line is the select line: a propose match is proposed and waits for the human's confirm, an auto match applies and says so, no match runs the design loop, and `ctx rhythm show <name>` reads a rhythm. Each grammar defect of a listed rhythm warns on stderr (`rhythm list: warning: <name> (<origin>): <defect>`) and the rhythm still lists; a file holding no `@rhythm` line is no rhythm and warns that it holds none. Two absent roots print the select line alone rc 0: the base payload ships no rhythms, and a workspace may carry none, so a bare base-only install completes its boot step. An argument refuses rc 1 with the usage.
- `show <name>`: the effective copy byte for byte (the workspace copy when it shadows an installed one), then the stamp line, `stamp: ctx unit record <unit> --rhythm="<name> <N> <GATE>" on each entry that advances this rhythm`; an unknown name refuses rc 1 (`ERR_ENTITY_NOT_FOUND`), and a name failing the slug rule (a slash, a leading dot) refuses rc 1 before any file is read (`ERR_INVALID_ARGUMENT`).
- `current <unit>`: one line from the unit's last stamped entry in record order, open or closed, read from `ctx unit entry list <unit> --json` through the storage core's flattener (`.contexture/storage/scripts/json.awk`), never a search snippet: `rhythm in force: <name> at <N> <GATE> (entry <slug>); next gate: <N+1> <GATE>: <outcome>`, `rhythm completed: <name> at its last gate <N> <GATE> (entry <slug>)`, `rhythm stale: <stamp> (entry <slug>) matches no step of the effective rhythm; read it: ctx rhythm show <name>` (a step that no longer reads its gate, a rhythm that no longer resolves, or a legacy stamp of another shape), or `rhythm none in force in <unit>: the design loop runs until the human confirms a rhythm (ctx rhythm list)`. A malformed unit refuses rc 1 before any read; a missing unit refuses with the listing's own line, and a unit served from the deprecated root prints its line with the one warning.

The module's one rule lives in its private `scripts/resolve`, which carries no summary line, so ctx never lists or dispatches it: the verbs run it by path, the unit verb library runs it by path (found as it finds the storage resolver) for the stamp check of `ctx unit record` and `ctx lane create` and for the board's closing line, and the governance grammar census reaches it through `ctx rhythm list`. It reads the two rhythm roots of the drawer it sits in and answers tab separated lines: the origin, whether the copy shadows the other root, the declared `@rhythm` name, the use when and activation values, one line per step (number, gate, outcome), and one line per grammar defect. The grammar: a step line is any line opening with a number, a dot, and a blank, its gate the text before the first colon in `[A-Z][A-Z_+]*`, the steps numbered 1 to N; the defects are a missing use when line, an activation neither propose nor auto, an `@rhythm` name that is not the file name, a break in the numbering, a gate outside the stamp grammar (counted once, never also as a gap), and no step line. Each verb answers a sole `--help` or `-h` with the table `ctx rhythm help <verb>` prints. The module holds no laws file (the `@rhythms` law stays in the core) and no data file (it reads no store).

### ctx store: the store module

The store module ships with the base in the workspace modules root, beside the lane and rhythm modules, on the builtin list (never the reserved list), so every workspace has it and no extension takes the name. It is the free container module: a workspace keeps generic data in a container it declares, with no module of its own. Its grammar is verb first, the operand being the path after `store#` in an address:

```bash
.contexture/ctx store put containers/<name> --description="..." --minting=given|generated [--add-fields="<field line>"]...
.contexture/ctx store get <container>/<id> [--json]
.contexture/ctx store list <container> [--<field>=<value>]... [--json]
.contexture/ctx store list containers [--dropped] [--json]
.contexture/ctx store put <container>/<id> | <container> [--<field>=<value>]... [--add-<field>=<item>]... [--unset=<field>]... [--stdin=<field>]
.contexture/ctx store set <container>/<id> [the same write forms, --remove-<field>=<item> too]
.contexture/ctx store delete <container>/<id>
.contexture/ctx store check <container>
.contexture/ctx store check --leftovers [--sweep [--dry-run] [--delete]]
.contexture/ctx store search "<query>" [--container=<c>] [--type=<t>] [--mode=<m>] [--limit=<n>] [--json]
```

- Declarations: `containers` is the one reserved container name; each of its records is a declaration: a one-line `description` (printed by `list containers`), a `minting` (`given` or `generated`), and `fields`, one field line per field in the storage layer's grammar (`<name>: <required|optional> <line|block> [list] [one-of <A|B|...>] [default <value>]`), plus the store kept `retired` ids and `dropped` state, which no write may name. `set containers/<name>` changes a declaration forward only; `delete containers/<name>` drops it, its records removed (the container's folder going with the last one) and every id they used retired, and a later `put containers/<name>` starts fresh with the retired ids inherited.
- Records: every write is checked against the declaration by the field validator under the library lock of the `store` namespace, and every refusal is one line `store <verb>: error: <message> (<CODE>)` with nothing written (`ERR_INVALID_ARGUMENT` for malformed input, `ERR_SCHEMA_VIOLATION` for a write breaking the declaration or naming an undeclared or dropped container, `ERR_ENTITY_EXISTS` for a used or retired id, `ERR_ENTITY_NOT_FOUND` for a missing record). A record prints in the unit record dialect; `ref` is every container's built in list of full addresses. Ids are unique whatever their case and never handed out again; a generated id is the date and five random characters (`2026-11-13-k3x9m`).
- Reads: `get` prints one record whole with its absent defaults read in, `list` filters by exact field values (complete and uncapped), `check` names every record breaking the current declaration (rc 1 when any does), `check --leftovers` reads the store's own storage instead through the library's `store_leftovers` (one `root: <kind>: <count> (<bytes> bytes)` line per kind found beyond the records' keys, such as an empty folder an older release left after a container drop (a delete now removes the folders it empties), rc 1 when any prints, nothing and rc 0 when nothing does, a whole read only walk that names no path and removes nothing, text only; a driver without the probe refuses rc 2), `check --leftovers --sweep` clears it through the library's `store_sweep` over the store namespace, under the storage layer's namespace lock (every kind moved into `.contexture/backups/sweep-<stamp>/store/root/<relative path>`, or removed with `--delete`, a record or declaration never touched, a folder holding no record below it moved or removed whole as one item and counted as emptied; a folder it cannot read or enter is never moved or removed, in either form, nor any folder above it, but left untouched and named, and a name holding a newline in its reach refuses the sweep rc 2, the dry run too; one `root: <kind>: <count> (<bytes> bytes)` line per kind swept, `root: folders emptied: <n>` and `root: unreadable folders left: <n>` when any, then the closing line `swept: moved <n> items (<bytes> bytes) into the backup stamped <stamp> and emptied <e> folders`, `swept: deleted ...`, or `swept: nothing beyond the documents; nothing moved`, a line ending `, leaving <n> unreadable folders untouched (their rights need fixing)` when the sweep left any, rc 0; `--dry-run` takes no lock and writes nothing, its closing line `dry run: would move ...`; `--dry-run` or `--delete` without `--sweep` refuses rc 1), and `search` answers the shared search shape, one group under `ctx search` whose rows read through `ctx store get <container>/<id>`, the container's name as each row's type.

The module keeps one value per record under the key `<container>/<id>` (declarations at `containers/<name>`) in its own root, `.contexture/store`, through the storage core's library alone: its verbs are thin wrappers over a private engine (`scripts/store`) and a private record reader (`lib/record.awk`), and it never names a driver. Its law fragment carries the `store-data` and `store-no-promise` clauses: the store stores and finds data and promises no freshness, accuracy, or injection.

### ctx unit fold: the consolidation fold

`ctx unit fold` is one stateless verb over the record; the command keeps no cursor, file, config, or table. The record is the state: a fold start entry (the plan JSON, the carried threads, and the batch rule), the lanes' ordinary consolidated entries, and the finish receipt. The consolidated entry is a normal journal entry: the `WHAT` is the batch's synthesis, the `REF` lines name every constituent (the carried open threads included) plus any external report, and the `CLOSES` lines fold the same constituents except the open threads. A fold compacts history, never obligations: open threads stay live and are carried.

```bash
.contexture/ctx unit fold <unit>                 # plan (first call) or progress
.contexture/ctx unit fold <unit> --lane=<lane>   # fetch: the next batch, its entries, the lane's remaining chunks, and the next act
.contexture/ctx unit fold <unit> --lane=<lane> --merge   # the same fetch plus the immediately following chunk's entries, the only merge partner
.contexture/ctx unit fold <unit> --check         # the read-only coverage, partition, and audit check
.contexture/ctx unit fold <unit> --finish        # the receipt; the fold start closed done
```

The first no-lane call computes the live scope of the unit (every live entry at that call), partitions it once into chunks in journal order at the mechanical seams (task receipts, releases, decisions, part and lane series, group switches), coalesces the mechanical series, splits any chunk still over 12 constituents at the last seam in its first 12 (or at the last entry with `(cap split: no seam)` recorded), records the fold start, and prints the plan with the carried open threads listed, the first lane's `ctx lane create` command and its manual, and the first act. The open threads stay in the scope and in the chunks. A chunk ends at the next semantic milestone (`TASK_DONE`, `RELEASE`, `DECIDE`, `HANDOFF`, `PERIOD_CLOSE`, `HARVEST`, `LANE_REPORT`, `HUMAN`); the live entries after the last milestone are one `TAIL` chunk; an anchor with no milestone is one `ANCHOR` chunk. Each anchor's chunks share a deterministic lane (`fold-<epoch>-<n>`); the orchestrator creates each lane with the `ctx lane create` command the plan and the progress print. A fetch returns the lane's next unclosed chunk, its entries, the lane's remaining chunks (never another chunk's entries), and the next act, and never advances; a `--merge` fetch adds the immediately following chunk's entries, the one permitted merge partner; at a lane boundary it returns the next lane's instruction instead. The lane writes one ordinary entry with `ctx unit record`; the command does not write it. A merge covers only that next chunk and records its same-topic reason in the `WHAT` as `(merged: <reason>)`; the check refuses a whole-anchor batch. A carried open thread is `REF`'d as context and never closed. `--check` reads the fold start's plan and the live post-plan entries: a consolidated entry is a live entry whose `CLOSES` target scoped slugs; its closer set is the batch. A scoped live entry carrying `THREAD` other than none is carried, never `SCOPED_LIVE`. Every target must be in the scope and carry a `unit#<unit>/entry/<slug>` REF (a legacy `journal#<slug>` one still counts), every closer must be `folded` with a reason, the batches must partition the scope into whole consecutive chunks in one lane, every batch `REF`s the carried threads in its chunks, the closed receipts are the scope minus the carried threads, and the audit must be clean (its open-thread tail prints); the defect classes are named in docs/the-record.md. `--finish` re-runs the check and, when clean, writes the receipt `FOLD FINISH v4 <fold-start> batches=<b> covered=<n> carried=<m> open threads :: coverage zero; audit clean` and closes the fold start done; the carried threads stay live and a live receipt refuses a second one. The command reads and writes only through the existing record operations (`session.board`, `entry.get`, `entry.record`, `session.audit`, and `lane.get` for the lane names); the storage SPI is unchanged. The operational protocol and the synthesis standard live in docs/the-record.md; the plan call prints the lane manual, and `ctx unit fold --help` prints the command manual.

### One audit per grammar

The runtime and the built-in modules are payload instruments, shipped with the convention and identical everywhere. A unit can also carry an audit of its own for a grammar the payload does not know yet; the unit's bank audit is the precedent. It stays unit-local until its grammar proves generic, then it can promote to the payload as a sibling. The separation is deliberate: no experimental checks inside a shipped script, and each audit derives its siblings rather than being handed their paths. Refresh and handoff run every audit in play, and the receipt carries the results.

## The completeness loop

The loop is what the machinery does with the record: it makes gaps visible at fixed points and demands repair instead of notes. Taking the stations in the order a unit meets them:

- **Boot** runs `ctx unit list` and `ctx rhythm list` for the proposal, then `ctx unit load` and `ctx rhythm current`. The load is the subtraction, not a judgment call, so the agent pays for what is open and nothing else; the rhythm in force names where the process stood.
- **Work** journals events as they happen and flags knowledge-worthy entries where they land. The flag is the harvest's input; nothing needs to be collected later.
- **Refresh** runs at every rhythm boundary and inside close. It sweeps the artifacts: events journaled, backlog statuses advanced, the derived move read from the backlog. It runs the harvest: every open flag, one candidate each; a candidate that meets the bar lands in knowledge and its entry closes by reference, and a candidate that does not drops. Then it runs the audit, and what it flags is fixed.
- **Close** closes the period's done events by reference and requires the audit to exit 0.
- **Handoff** runs before context death, whether that is a compaction, a tool change, or a long break. The period-end writes run if they are not done, then the bounded cold read: run `ctx unit load` and read the map and the state page, the backlog section with its open tasks whole, the journal's tail (this period's entries), and the knowledge tail when this period landed findings; the full-body pass belongs to the next boot, a fresh context. While the context is still full, improve the quality and fix what was missed; the gaps close now, never after compaction. `ctx unit audit` exits 0.

Why this holds together:

- The record is append-only and schema-driven, so "missing" is a mechanical fact rather than a memory test: an absent closer, an unrecorded done event, a task absent from the board are all visible to a small script.
- The checks run at fixed points, and they are cheap: a few awk commands, no model tokens, the same answer every time. Frequency is the point; the open-flag sweep at each refresh is the check, not a rare batch at the end. When harvesting waited for period end, older flags slipped past every close.
- An instrument earns trust by failing on the defect it guards. A check that returns the same answer whether or not the failure is present proves nothing, so the instruments are proved against planted defects before they are trusted, and a green run means exactly the classes it checks are clean. It is never a claim that the record is complete.

## The drawer layout

Everything the convention installs or uses lives under `.contexture/`, except the files that sit at the repository root: the loader a harness must find there, the overlays, and the generated law layer beside them:

```text
AGENTS.md            the loader: compose or verify, then load the generated layer whole; delivered every turn
AGENTS.workspace.md  the shared overlay
AGENTS.local.md      your amendments
AGENTS.generated.md  the generated law layer: composed by ctx compose at install and boot; gitignored, never edited
plugins/             the tracked catalog of packaged overlays (fallback when .contexture/plugins/ is absent)
.contexture/
  ONBOARDING.md      the adoption guideline (removed when the adoption closes)
  ctx                the runtime: discovery, help assembly, dispatch, the run engine, and hooks
  package-install    the package overlay installer, private behind ctx package install: overlays a package's .contexture/extensions tree, records it, runs the part hooks and package install hook
  package-uninstall  the package overlay remover, private behind ctx package uninstall: runs the stashed package uninstall hook and part hooks, removes the recorded files, preserves a changed file
  plugins/           the workspace catalog of packaged overlays (checked ahead of ./plugins/)
  laws/              the law sources: core.md the core law source, and the composer, private behind ctx compose
  modules/           unit (the record engine), run (stream filters), lane (the subagent lanes), rhythm (the process surface), store (the free containers), and workspace additions
  extensions/        the package overlay root: modules/ for package feature modules, storage/drivers/ for package drivers, rhythms/ for package rhythms, .state/ for the installed-path records
  rhythms/           your process patterns
  units/             the units of work (sessions/, the deprecated root, holds a unit until it moves and is removed once it is empty)
  tmp/               gitignored scratch: engines and agents prefer it over system temp (created on demand; each verb stages under its own root, removed on return and swept by the next dispatch after a kill)
```

Three drawer facts each have one owner, and the rest of the product reaches them through it. The record root and its deprecated fallback root are the unit module's data file (its `root` and `fallback_root` lines, read by the storage core's `store-data`; the posix driver maps the record's keys under the root, reads the fallback after it, moves a written unit's folder from it, and probes its health over both, and the docs module's backlog file guard lists both through the library's `store_roots`). The fts5 database's default name, `.contexture/sessions.db`, is the fts5 driver's (`storage.database` relocates it). The lock layout is the unit data script's unit lock (`locks/unit/<unit>.lock`, its `u_lock`) beside each driver's namespace lock (`store-<namespace>.lock`, its `store_lock` and `store_lock_held`), both under the drawer's scratch folder while it is writable, else under the per-user `contexture-<user>` folder in the system temp. The governance drawer literal census (`tests/governance/drawer-literals.test.ts`) refuses the record roots, the database name, and the lock literals anywhere else in the storage core, the plugin drivers, the engine, the composer, the package overlay, and the module roots; the tests read the same facts through one helper, `tests/support/drawer.ts` (the record root and the fallback root parsed from the unit module's data file), and the census refuses the literals in every other test file.

The root belongs to the harness: AGENTS.md has to sit where the harness looks for repository instructions, and the overlays and the generated law layer sit beside it. Everything else lives in the drawer. An adopting workspace keeps its own files at the root, freely; the drawer's contents are the convention's, and the two never mix. The repository that builds the convention tracks this layout mirrored under `base/` (`base/AGENTS.md`, `base/.contexture/`); its own installation at the root is untracked working state.

### One home, three classes

Placement follows the class of the file, never convenience:

| class | paths | fate |
|---|---|---|
| update payload | `base/`: the mirrored core (`base/AGENTS.md`, `base/.contexture/{ctx,package-install,package-uninstall,storage,laws,modules/lane,modules/rhythm,modules/run,modules/store,modules/unit,ONBOARDING.md}`) | applied onto the live root from tags, byte for byte |
| catalog | `.contexture/plugins/` (and `plugins/` fallback): packaged overlays | copied into a workspace when wanted; never deleted at adoption close |
| live workspace | the untracked root: `AGENTS.md`, `.contexture/units/` (and the deprecated `.contexture/sessions/` while units remain in it), `.contexture/store/`, `.contexture/backups/`, `.contexture/rhythms/`, `.contexture/tmp/`, workspace-added modules under `.contexture/modules/`, and the drawer's top files: the configuration `.contexture/config` (and the legacy `.contexture/storage.conf`), an fts5 store's database `.contexture/sessions.db` with its `-wal` and `-shm` files, and a macOS Finder `.DS_Store` | never touched by an update |

The classes exist because the files have different lives. The payload evolves with the convention and must stay identical across every workspace: it is tracked in one mirrored tree and applied onto the live root as-is, so what the tag tracks under `base/` is exactly what lands. The catalog holds the optional overlays: a workspace installs one when it wants it, and the folder is no longer deleted at adoption close. The record (units, and the deprecated sessions folder while units remain in it), the store module's records, the stamped backups a leftovers sweep keeps, rhythms, tmp, workspace-added modules, and the drawer's top files are the workspace's own state, and no update may touch them. `.contexture/ONBOARDING.md` rides the payload as adoption material; it is used once and removed when the adoption closes.

### The sync derives from the tag

There is no manifest. `base/` is the payload: `git archive <tag> base/` copies it, `git ls-tree` enumerates it, and a comparison per file verifies it. Whatever the tag tracks under `base/` is the set; a file cannot silently join or leave the payload without changing the tag.

### The layout bounds the load

The drawer is also the context mechanism, and the reason is structural. When the agent works a unit, it reads that unit (`.contexture/units/<unit>/` under posix, through the verbs) and the convention's files it needs, never a global blob of everything. The filesystem is the index, and the folder is the boundary: no rule has to say "do not read the rest", because the layout has already said it.

The record page covers what the artifacts hold and how liveness works; units and subagents covers the container and the dispatch; rhythms covers the process layer; overlays covers the amendment grammar; adoption covers the install.
