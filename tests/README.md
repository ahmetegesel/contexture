# tests: the filter test material

Upstream only: this folder is not part of the shipped payload, and adopting workspaces carry no test material. The root README navigates here; read this page before maintaining the filters or the pairs.

## Why this exists

The stream filters are byte-sensitive: one edited branch silently changes what every session sees, and nothing errors when it does. This folder is their regression net, adapted from rtk's strongest practice: static input and expected-output pairs, byte-compared by the harness. It is hermetic (POSIX sh, awk, cmp, mktemp; no toolchain, no installs, no network). The subject under test is the shipped core: the core suites run the base runtime (`base/.contexture/ctx`) and its modules, never the live drawer (the vitest projects stage `base/` as shipped); the plugin suites exercise each plugin's own copy under `plugins/<name>/`, never the adopted copy in the live drawer, because the two drift. Every harness stages its sandbox under the workspace's gitignored `.contexture/tmp/` when that drawer is writable, and falls back to TMPDIR only when it is not; each run makes a sandbox of its own (mktemp, never a fixed name) and keeps its locks, stores, and scratch inside it, because the runner starts the suites concurrently and two gates may run at once.

## What is here

- `run.sh`: the runner: the one core shell suite (`core:base-only-tests.sh`, the shipped base alone; every other core area is a vitest project below, run with `bun run test`, which `run.sh` does not start), then every plugin suite by convention (`plugins/<name>/tests/run.sh`; a plugin whose tests are a vitest project reports INFO), one line per suite plus a final verdict; non-zero when any suite fails; a suite exiting 77 (a need absent) reports SKIP. The suites run concurrently: each is a background job with its own output file in one gate scratch folder, its exit code written by the job itself (never read through a pipeline); when all have ended the runner prints every suite's output and outcome line in the fixed order above, then the suite times and the verdict. A suite still running after `GATE_SUITE_TIMEOUT` seconds (default 3600) is stopped with its whole process tree and fails. A suite that fails or times out prints one notice line on stderr the moment it ends, so a red surfaces without waiting for the long jobs; a green run's output is unchanged. `GATE_JOBS=<n>` caps how many run at once (default 5, the four to six lanes the host's cores allow; `0` runs all; `GATE_JOBS=1` runs the suites one after another, same order, same output).
- `fast.sh <area> [<arg>]`: the fast inner loop by area; see "Layers and the fast loop" below. It never replaces the gate.
- `base-only-tests.sh [--keep]`: the shipped base alone, with no plugin. It stages `base/` only (no `docs/`, no `plugins/`, no config, no rhythms directory; the base's extension root carries the lane module) and proves the payload a bare adoption carries: the no-plugin help surface (unit and the extension-root lane module listed; docs and storage-fts5 unknown rc 1; an absent extension root silent and unlisting lane), the absent-rhythms index rc 0 with an empty answer (with and without the directory), the posix descriptor (the contract 3 store-only card: version 3.0.0, the seven store data names in `store`, exact, optional store, no record function family), the record, lane, and store smoke over a synthetic data module (bootstrap through close and reopen, tasks, journal with a closer, findings, lane create/record/report/show, board, load to completion, audit, exact search, resolve of every entity, entry closure, fold, stamp, active, refresh), the store data-file grammar and the seven functions over a synthetic namespace (the exact answers, the key rule, the case twin, the refusals, the no change log on posix, no temp or lock residue), the owner scan in both module roots, the resolver's extension tier, the no-base-to-docs census with a planted reference. The core's own suites run once in their vitest projects (the engine, the filter pairs, and the hooks; the store contract in the drivers project, over a docs-shaped synthetic namespace with no plugin data; the record logic and the audit in unit-record; the unit and lane verbs in unit-verbs), so none is rerun here. The descriptor check and the census are null-checked by a planted difference (a missing store name, a planted functions field, a planted docs reference). It excludes the docs suite and every plugin suite by design: those are plugin gates. The run is `pass=163`. The gate reads red on BG1 before the index fix and green after (journal of 2026-10-28).
- `fixtures/`: committed fixtures shared by the projects: the worked example package (`fixtures/worked-package/`, its test in the packages project) and `fixtures/compliance/` (the legacy markdown units the posix-alone cases plant (`units/`), the legacy fixture's golden answers and item notes (`golden/legacy-u/`, `legacy.notes`), the verb-built unit's golden answers (`golden/verb-u/`, written with `COMPLIANCE_WRITE_GOLDENS=1` and read by hand), the exact search answers of TC39 and TC69, TC61's expected posix journal, the canned fts5 store answer the ranked mapping reads (`ranked/`), and the expected texts of the views (`views/`); all of them the vitest unit-record project's).

Plugin pairs live under the plugin (`plugins/toolchain-filters/tests/`) and run through a staged sandbox. The plugins' own tests are vitest projects rooted at the plugin (see the vitest harness below): `storage-fts5` (`plugins/storage-fts5/tests`), `ast-doc-graph` (`plugins/ast-doc-graph/tests`: the schema over seeded rows, the query CLI, the extractors and the loader in process, and the full and delta index of a committed mini repository with the query's freshness check), and `docs-discipline` (`plugins/docs-discipline/tests`: the docs engines alone over files and committed expected output, the census, the grammar agreement, the verbs end to end on posix, the read refusal on a driver without a store, and the store mode cases on fts5; its module README carries the detail).

## Layers and the fast loop

Three layers, from the smallest proof to the full one:

- The fast inner loop is the vitest project of the area under change, or one file or one test of it (`bun run test:engine`, `bun run test:filters`, `bun run test:hooks`, `bun run test:governance`, `bun run test:unit-record`, `bun run test:drivers:posix`, `bun run test:docs-discipline`, `bun run test:ast-doc-graph`). It is the smallest set that proves the kind of change at hand, never a replacement for the gate.
- The pre-commit layer is the fast loop plus the owning integration suite: a record or verb change adds `bun run test:unit` (the unit-record and unit-verbs projects); an fts5 change adds the storage-fts5 suite; a docs change adds `bun run test:docs-discipline` (its `store/` files on fts5; `VITEST_DRIVERS=posix` skips them); a plugin change adds that plugin's project; a base module change adds `tests/base-only-tests.sh`; a law change adds `bun run test:laws`; a package overlay or install change adds `bun run test:packages`.
- The full pre-land gate is `tests/run.sh` unchanged: the 1 run job plus the 1 skip and the 4 info, beside `bun run test`, every suite, every assertion, the fixed print order, and the fixed verdict. It stays mandatory before any commit, tag, or push.

The broad pre-push set is the fast loop plus `bun run test:unit`, `bun run test:docs-discipline`, storage-fts5, and base-only (`tests/base-only-tests.sh`); the full plugin matrix stays for pre-land. The fast loop shortens the inner loop, never the gate.

`tests/fast.sh <area>` runs the fast inner loop by area (POSIX sh and awk, no dependency, no fixed scratch, 77 a skip, 1 on any failure):

- `tests/fast.sh plugin <name>`: `plugins/<name>/tests/run.sh`.
- `tests/fast.sh base`: the shipped base alone (`tests/base-only-tests.sh`).

Every other area is a vitest project: `bun run test:<project>` from this folder.

`plugin:toolchain-filters` is INFO (its tests are the vitest project `toolchain-filters`), and so are `plugin:storage-fts5`, `plugin:docs-discipline`, and `plugin:ast-doc-graph` (their tests are vitest projects); `plugin:starter-rhythms` is SKIP (no tests directory), and the retired lane-isolation package is no longer a catalog entry. storage-fts5 is integration: it proves the plugin's own copy of the fts5 driver. docs-discipline is unit and integration on posix with its store mode on fts5; ast-doc-graph is unit plus the integration of its own pipeline; base-only is end-to-end-like.

## Roots

Core pairs (`filters/pairs/`):

- `diff-show-trimmed`: a `git show` of a long commit message.
- `list-ansi`: a colored `ls` capture (ANSI-bearing).
- `log-repeat`: a repeated-line log capture.
- `compact-recovery` (`filters/mechanics/`): synthetic input plus its probe (mechanics case).

Plugin pairs, and `compact-false-green` (a tsc shim emitting a JS TypeError, the notice-only mechanics case): see `plugins/toolchain-filters/tests/README.md`.

## How to maintain

- The ship gate: `tests/run.sh` must end green before any commit, tag, or push; a red run holds the ship breath. The runner reports one line per suite plus a final verdict, a planted failure must exit non-zero, and a planted hang must end as a failure at the suite timeout with no process left behind.
- A new suite (core or plugin) stages in a sandbox of its own (mktemp under the scratch drawer, removed on exit) and never writes a fixed name or a path outside it: the runner starts every suite at once, so a shared path turns into a race.
- A base change (a module script, the resolver, the store, a help surface) runs the base-only gate as well: `tests/base-only-tests.sh`, and the ship gate runs it as `core:base-only-tests.sh`; a base-only regression that passes the plugin suites must fail there.
- A law change (the core source, a module's laws or description, the composer, the loader) runs `bun run test:laws`; a version bump regenerates `tests/laws/fixtures/base-only.golden` with the compose, never by hand (the project's base-only byte comparison and its golden-version check both read it).
- A filter change is not done until its tests pass: `bun run test:filters` for a core filter, `bun run test:toolchain-filters` for a plugin filter.
- A new filter is not done until it carries at least one pair; the presence check fails otherwise.
- Update a `.expected` only with evidence: rerun the capture or reproduce the behavior. Never hand-edit an expected to match a surprise.
- Keep the pairs static and hermetic; a `.in` is a capture, never a live command.
- Portability: the suite carries no awk of its own choosing; it runs under whatever awk the system has. Before a change to an awk encoder, decoder, or regex string ships, run `tests/run.sh` under each supported awk (BWK awk on macOS, and in disposable Linux containers Debian with its default mawk, Debian with gawk, Alpine with busybox awk, with sqlite3 and git inside the container for the fts5 run and the governance probe); an assertion that only one awk turns red is the reason the matrix exists.
