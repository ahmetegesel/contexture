# tests: the filter test material

Upstream only: this folder is not part of the shipped payload, and adopting workspaces carry no test material. The root README navigates here; read this page before maintaining the filters or the pairs.

## Why this exists

The stream filters are byte-sensitive: one edited branch silently changes what every session sees, and nothing errors when it does. This folder is their regression net, adapted from rtk's strongest practice: static input and expected-output pairs, byte-compared by the harness. It is hermetic (POSIX sh, awk, cmp, mktemp; no toolchain, no installs, no network). The subject under test is the shipped core: the core suites run the base runtime (`base/.contexture/ctx`) and its modules, never the live drawer (the unit-data record compliance stages base's storage core and unit module, and the storage compliance harness resolves base's posix driver by path); the plugin suites exercise each plugin's own copy under `plugins/<name>/`, never the adopted copy in the live drawer, because the two drift. Every harness stages its sandbox under the workspace's gitignored `.contexture/tmp/` when that drawer is writable, and falls back to TMPDIR only when it is not; each run makes a sandbox of its own (mktemp, never a fixed name) and keeps its locks, stores, and scratch inside it, because the runner starts the suites concurrently and two gates may run at once.

## What is here

- `run.sh`: the runner: every core suite (the unit suite twice, `core:session-tests.sh` on the posix driver and `core:session-tests.sh:fts5` on the fts5 driver, the record compliance twice through the unit data script, `core:unit-data-tests.sh:posix` and `core:unit-data-tests.sh:fts5`, `core:store-fuzz.sh` and `core:record-fuzz.sh` over both drivers, `core:law-tests.sh`, the law compose, and `core:base-only-tests.sh`, the shipped base alone), then every plugin suite by convention (`plugins/<name>/tests/run.sh`; the docs-discipline suite twice as well, `plugin:docs-discipline` on posix and `plugin:docs-discipline:fts5` with `--driver=fts5`, skip 77 without sqlite3 FTS5), one line per suite plus a final verdict; non-zero when any suite fails; a suite exiting 77 (a need absent) reports SKIP. The suites run concurrently: each is a background job with its own output file in one gate scratch folder, its exit code written by the job itself (never read through a pipeline); when all have ended the runner prints every suite's output and outcome line in the fixed order above, then the suite times and the verdict. A suite still running after `GATE_SUITE_TIMEOUT` seconds (default 3600, raised for the unit-data data modes) is stopped with its whole process tree and fails. A suite that fails or times out prints one notice line on stderr the moment it ends, so a red surfaces without waiting for the long jobs; a green run's output is unchanged. `GATE_JOBS=<n>` caps how many run at once (default 5, the four to six lanes the host's cores allow; `0` runs all; `GATE_JOBS=1` runs the suites one after another, same order, same output; the unit suite still runs its groups at once inside its own run).

## Layers and the fast loop

Three layers, from the smallest proof to the full one:

- The fast inner loop is the unit-like set: `filter-tests.sh`, `ctx-tests.sh`, `governance-tests.sh`, `record-audit-tests.sh`, `store-compliance.sh` on posix, the unit-data smoke on posix, and `plugins/ast-doc-graph/tests/test-ddl.sh`. It is the smallest set that proves the kind of change at hand, never a replacement for the gate.
- The pre-commit layer is the unit-like set plus the owning integration suite: a record or session change adds the owning session group; an fts5 change adds the storage-fts5 suite; a docs change adds docs posix and docs fts5 when the store mode is touched; a plugin change adds that plugin's suite; a base module change adds base-only's B1 to B5 checks; a package overlay or install change adds module-tests.
- The full pre-land gate is `tests/run.sh` unchanged: all 19 run jobs plus the 1 skip and 1 info, every suite, every assertion, the fixed print order, and the fixed verdict. It stays mandatory before any commit, tag, or push.

The broad pre-push set is the unit-like set plus session posix, docs posix, storage-fts5, and base-only's unique checks (`tests/base-only-tests.sh --skip-core`); session fts5, docs fts5, and the full plugin matrix stay for pre-land. The fast loop shortens the inner loop, never the gate.

`tests/fast.sh <area>` runs the fast inner loop by area (POSIX sh and awk, no dependency, no fixed scratch, 77 a skip, 1 on any failure):

- `tests/fast.sh unit`: the seven unit-like suites (about 42 s isolated, 290 assertions), with the unit-data smoke in place of the long data-mode compliance.
- `tests/fast.sh engine`: filter, ctx, governance.
- `tests/fast.sh law`: the law compose suite (`law-tests.sh`).
- `tests/fast.sh record <1|2|3|4>`: one unit suite group; the owning group is required because it is not derivable.
- `tests/fast.sh unit-data [posix|fts5]`: the full record compliance through the unit data script on one driver (default posix; the selective inner loop). The fts5 half and the full 66/60 stay for pre-land.
- `tests/fast.sh driver posix`: the unit-data smoke, store compliance, and session posix.
- `tests/fast.sh driver fts5`: the record compliance through the unit data script on fts5 and the storage-fts5 plugin's own store compliance.
- `tests/fast.sh fuzz`: the differential fuzzers, store-fuzz and record-fuzz, posix against fts5 (skips 77 without sqlite3).
- `tests/fast.sh module`: the package overlay installer suite (`tests/module-tests.sh`).
- `tests/fast.sh docs` and `tests/fast.sh docs-fts5`: the docs-discipline suite on the files driver and on fts5.
- `tests/fast.sh plugin <name>`: `plugins/<name>/tests/run.sh`.
- `tests/fast.sh base`: base-only's B1 to B5 checks (`tests/base-only-tests.sh --skip-core`).

The layer map: session group 1 = V R S C P F H S E; group 2 = X E3 Y B W WH WA K Q; group 3 = Z L RF U UP CL N D; group 4 = FC. `plugin:toolchain-filters` is INFO (its fixture pairs ride filter-tests); `plugin:starter-rhythms` is SKIP (no tests directory), and the retired lane-isolation package is no longer a catalog entry. Session fts5 and storage-fts5 are integration, classified once here: both prove the fts5 driver from different angles (the verb surface and the plugin's own copy), and the shared storage-compliance harness is the stated overlap. docs posix is integration; docs fts5 and base-only are end-to-end-like.

Core pairs (this folder):

- `diff-show-trimmed`: a `git show` of a long commit message.
- `list-ansi`: a colored `ls` capture (ANSI-bearing).
- `log-repeat`: a repeated-line log capture.
- `compact-false-green`: a tsc shim emitting a JS TypeError (mechanics case).
- `compact-recovery`: synthetic input plus its probe (mechanics case).

Plugin pairs: see `plugins/toolchain-filters/tests/README.md`.

## How to maintain

- The ship gate: `tests/run.sh` must end green before any commit, tag, or push; a red run holds the ship breath. The runner reports one line per suite plus a final verdict, a planted failure must exit non-zero, and a planted hang must end as a failure at the suite timeout with no process left behind.
- A new suite (core or plugin) stages in a sandbox of its own (mktemp under the scratch drawer, removed on exit) and never writes a fixed name or a path outside it: the runner starts every suite at once, so a shared path turns into a race.
- A base change (a module script, the resolver, the store, a help surface) runs the base-only gate as well: `tests/base-only-tests.sh`, and the ship gate runs it as `core:base-only-tests.sh`; a base-only regression that passes the plugin suites must fail there.
- A law change (the core source, a module's laws or description, the composer, the loader) runs `tests/law-tests.sh`; a version bump regenerates `tests/fixtures/law-compose/base-only.golden` with the compose, never by hand (the suite's base-only byte comparison and its golden-version check both read it).
- A filter change is not done until the harness passes: `tests/filter-tests.sh`.
- A new filter is not done until it carries at least one pair; the presence check fails otherwise.
- Update a `.expected` only with evidence: rerun the capture or reproduce the behavior. Never hand-edit an expected to match a surprise.
- Keep the pairs static and hermetic; a `.in` is a capture, never a live command.
- Portability: the suite carries no awk of its own choosing; it runs under whatever awk the system has. Before a change to an awk encoder, decoder, or regex string ships, run `tests/run.sh` under each supported awk (BWK awk on macOS, and in disposable Linux containers Debian with its default mawk, Debian with gawk, Alpine with busybox awk, with sqlite3 and git inside the container for the fts5 run and the governance probe); an assertion that only one awk turns red is the reason the matrix exists.
