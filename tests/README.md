# tests: the upstream test suite

Upstream only: this folder is not part of the shipped payload, and adopting workspaces carry no test material. The root README navigates here; read this page before maintaining any test.

## Why this exists

The product is POSIX sh and the system awk, and its failures are quiet: one edited filter branch, record rule, or lock path silently changes what every unit sees, and nothing errors when it does. This folder is the regression net: vitest projects written in TypeScript that run the shipped product as child processes, staged from `base/` and `plugins/` exactly as shipped, one area per project, so a change runs the tests of its own area in seconds and the whole suite before a release. The subject under test is the shipped core: every project stages the base runtime (`base/.contexture/ctx`) and its modules, never the live drawer; the plugin projects exercise each plugin's own copy under `plugins/<name>/`, never the adopted copy in the live drawer, because the two drift. Every test stages its sandbox under the workspace's gitignored `.contexture/tmp/` (one run root per project run, a fresh folder per sandbox, never a fixed name) and keeps its locks, stores, and scratch inside it, because the files of a run execute in parallel and two runs may share the host.

## What is here

- `fixtures/`: committed fixtures shared by the projects: the worked example package (`fixtures/worked-package/`, its test in the packages project) and `fixtures/compliance/` (the legacy markdown units the posix-alone cases plant (`units/`), the legacy fixture's golden answers and item notes (`golden/legacy-u/`, `legacy.notes`), the verb-built unit's golden answers (`golden/verb-u/`, written with `COMPLIANCE_WRITE_GOLDENS=1` and read by hand), the exact search answers of TC39 and TC69, TC61's expected posix journal, the canned fts5 store answer the ranked mapping reads (`ranked/`), and the expected texts of the views (`views/`); all of them the vitest unit-record project's).

Plugin pairs live under the plugin (`plugins/toolchain-filters/tests/`) and run through a staged sandbox. The plugins' own tests are vitest projects rooted at the plugin (see the vitest harness below): `storage-fts5` (`plugins/storage-fts5/tests`), `ast-doc-graph` (`plugins/ast-doc-graph/tests`: the schema over seeded rows, the query CLI, the extractors and the loader in process, and the full and delta index of a committed mini repository with the query's freshness check), and `docs-discipline` (`plugins/docs-discipline/tests`: the docs engines alone over files and committed expected output, the census, the grammar agreement, the verbs end to end on posix, the read refusal on a driver without a store, and the store mode cases on fts5; its module README carries the detail).

## The vitest harness

TypeScript tests that drive the shipped product (sh and the system awk, staged from `base/` and `plugins/` as shipped) as child processes. Every command runs from this folder; the first time, `bun install --frozen-lockfile` restores the tooling.

- `package.json`: the test tooling, installed with bun from this folder (`bun.lock` is tracked, `node_modules/` is not); its only dev dependencies are vitest, typescript, and @types/node, pinned exactly. The commands:
  - `bun run test`: every default project (all but `sqlite-smoke`, through vitest's negated project filter `--project '!sqlite-smoke'`); the whole suite during the work.
  - `bun run test:prerelease`: the release gate: every project, `sqlite-smoke` included, with `VITEST_PRERELEASE=1`, which makes sqlite3 with FTS5 a requirement (the run fails at its global setup without it, and `VITEST_DRIVERS` is ignored), so no fts5 case, fault, fuzz, or bypass guard can skip; the fault-injection and fuzz tests live inside their area projects, so this is every test there is.
  - `bun run test:<project>`: one area, one script per project, each `vitest run --project <project>` (`test:harness`, `test:governance`, `test:filters`, `test:engine`, `test:hooks`, `test:laws`, `test:packages`, `test:base`, `test:integration`, `test:sqlite-smoke`, `test:unit-record`, `test:unit-verbs`, `test:drivers` (which also runs `storage-fts5`, below), and the plugin projects `test:storage-fts5`, `test:toolchain-filters`, `test:docs-discipline`, `test:ast-doc-graph`); the governance `projects` check fails a project without its script.
  - area groups: `bun run test:unit` (the `unit-record` and `unit-verbs` projects, the unit module area), `bun run test:drivers` (the `drivers` and `storage-fts5` projects, every store driver), `bun run test:drivers:posix` (the drivers area on posix alone: `VITEST_DRIVERS=posix` drops the fts5 parameters, and every fts5-only file skips).
  - `bun run test:changed [<ref>]`: the projects the change touches, from `support/areas.ts` (below): the working tree against HEAD, or everything since the merge base with `<ref>` plus the working tree (`bun run test:changed main`); any other argument passes through to vitest.
  - one file or one test: `bun run test:<project> <file filter> -t "<name pattern>"` (for example `bun run test:harness exec -t "own timeout"`), or `./node_modules/.bin/vitest run --project <project> <file> -t "<name pattern>"`; a file filter alone also narrows `bun run test`.
  - `bun run typecheck`: `tsc --noEmit` over every TypeScript file here.
- `.reports/` (gitignored): every run of the commands above leaves `last.json` (vitest's JSON reporter: every test with its state, duration, and failure messages, the file to read when a console is compacted) and `timing.json` (the timing reporter's per-project walls and every test's duration, slowest first); the same timing summary prints at the end of the run (the run's wall, each project's wall and its place in the run, the ten slowest tests). A second run in the same checkout overwrites both, so copy `.reports/last.json` before the next run to keep it: the config gives the JSON reporter its own `outputFile`, which wins over a command-line `--outputFile.json=<file>` or `--outputFile=<file>`, so no flag writes a private path. A `--reporter` on the command line replaces the configured reporters: the timing summary and `timing.json` drop out, and `last.json` is written only when `json` is among them (still at `.reports/last.json`).
- `vitest.config.mts`: one vitest project per area; `harness` holds the harness smoke tests, `drivers` the store driver tests (`bun run test:drivers`), `unit-record` the unit module's record logic (`bun run test:unit-record`), `unit-verbs` the `ctx unit` and `ctx lane` verbs (`bun run test:unit-verbs`), `governance`, `filters`, `engine`, `hooks`, `laws`, and `packages` the engine and tooling areas, `base` the shipped base alone (`bun run test:base`), `integration` the connections between components (`bun run test:integration`), `sqlite-smoke` the pre-release SQLite smoke set (`bun run test:sqlite-smoke`), and the plugins' own projects rooted at `plugins/<name>`, declared by convention: every `plugins/<name>/tests/` that holds a test file is a project named for its plugin (today `ast-doc-graph`, `docs-discipline`, `storage-fts5`, `toolchain-filters`; `bun run test:<name>`), which imports these helpers as `@support/<helper>` (the project's `resolve.alias`, mirrored by the tsconfig `paths`). Every project keeps 16 tests in flight per file (`maxConcurrency`), since each test is a few independent processes. The settings are measured (the default set on a 16-core host, the load under 8 at each start): `maxWorkers: '50%'`, 8 files at once here, the knee: the wall fell from 4 workers (167 to 189 s) to 8 (145 to 147 s) and stayed flat at 12 and 16 (145 and 146 s), since the host saturates and more workers only lengthen each test; `testTimeout` 120 s, about twice the longest test at 8 workers (the fold protocol chain, 56 s); `hookTimeout` 120 s, about four times the longest `beforeAll` seed (30 s); a project-order switch (`sequence.groupOrder`) and a slowest-first sequencer were measured and bought nothing, so files run in vitest's own order. A global setup makes one fresh sandbox root per project run under the workspace's `.contexture/tmp/` and removes it when the run ends (and, under `VITEST_PRERELEASE=1`, fails the run when sqlite3 lacks FTS5); every sandbox is a fresh folder inside it; the setup file `support/setup.ts` sweeps the process groups after each file; the reporters are vitest's default, its JSON reporter into `.reports/last.json`, and the timing reporter `support/timing.ts`.
- `tsconfig.json`: the type check over every TypeScript file here.

- `sqlite-smoke/`: the runtime half of the store-bypass guard (the static half is `governance/store-bypass`), in the pre-release set only: `bun run test` leaves it out, `bun run test:sqlite-smoke` runs it. Each test drives one command family on a sandbox staged with the storage-fts5 plugin's driver copy and `storage.driver: fts5` (`families`: SF1 the unit lifecycle, SF2 tasks, SF3 the journal, SF4 findings, SF5 lanes, SF6 the read views, SF7 the three search modes, SF8 the descriptor through diagnose and the resolver, SF9 the worked notes module's store) and asserts that the reads answer the writes, that no namespace root folder (`.contexture/sessions`, a module's root such as `notes`) appears beside `sessions.db`, and that the store lists the family's keys through the resolver (`smoke.ts`). `planted-bypass` swaps the unit module's `record` verb in the sandbox for one that appends to the posix journal file: it answers rc 0 with a receipt, yet the same instrument reads the entry unlisted and the posix residue present, then the real verb restored lands again. A sqlite3 without FTS5 fails the set, never skips it, since a skipped guard proves nothing.
- `harness/`: one smoke test per invocation kind, each with the null check its instrument needs (a shared sandbox sees the planted leak; the inherited env carries the planted variables; the fts5 probe reads absent without sqlite3; a leader killed alone leaves its hung tree alive), and the runner's own guarantees: `exec` stops a hung call's whole process tree at its own timeout, and `runner` drives an inner vitest run over `fixtures/` (its own config, test files named `*.fixture.ts` so no project collects them): a planted failing test exits 1, and a planted hang fails at its test timeout with no process of its tree left behind, while the same run without the sweep leaves the tree alive (the null check).

## Layers and the fast loop

Three layers, from the smallest proof to the full one:

- The fast inner loop is one test, one file, or the vitest project of the area under change (`bun run test:engine`, `bun run test:filters`, `bun run test:hooks`, `bun run test:governance`, `bun run test:unit-record`, `bun run test:drivers:posix`, `bun run test:docs-discipline`, `bun run test:ast-doc-graph`). It is the smallest set that proves the kind of change at hand.
- The change's set is every project the change touches: `bun run test:changed` selects them from the changed paths through `support/areas.ts` (a record or verb change runs both unit projects, the hooks, base, integration, and the SQLite smoke; an fts5 driver change runs the drivers, storage-fts5, and the SQLite smoke; a base module change adds `base` and `integration`; a law change runs `laws`; a package overlay or install change runs `packages` and `laws`; a change to the harness itself runs every default project). The named groups do the same by hand: `bun run test:unit`, `bun run test:drivers`, or several projects at once (`./node_modules/.bin/vitest run --project base --project integration`).
- The whole suite: `bun run test` runs every default project during the work; `bun run test:prerelease` is the release gate (every project, the SQLite smoke set included, FTS5 required), run before a release only, on the staged payload, and a red run holds the ship breath.

storage-fts5 is integration: it proves the plugin's own copy of the fts5 driver. docs-discipline is unit and integration on posix with its store mode on fts5; ast-doc-graph is unit plus the integration of its own pipeline; the base project is end-to-end-like. A catalog plugin with no tests directory (`starter-rhythms`) carries its no-suite reason in the governance `projects` check.

## Writing a test

A test is a `<subject>.test.ts` file in the folder of its area's project (`tests/<area>/`, or `plugins/<name>/tests/` for a plugin, where the helpers import as `@support/<helper>`). The logic is tested once, on posix; a driver is tested against the store contract in `drivers/`, never by rerunning the logic under it. A shape to start from:

```ts
import { beforeAll, describe, expect, it } from 'vitest';
import { fresh, seed } from '../support/snapshot';
import { must, seedUnit, unit } from '../support/unit';

describe.concurrent('ctx unit task complete', () => {
  let snap = '';
  beforeAll(async () => {
    snap = await seed(async (sb) => {
      await seedUnit(sb, 'demo-unit');
      await must(unit(sb, 'task', 'add', 'demo-unit', 'demo-task', '--objective=the seeded task'));
    }, 'posix', 'task-complete');
  });

  it('[the-record-r8] lands DONE and its receipt in one write', async () => {
    const sb = fresh(snap);
    expect((await unit(sb, 'task', 'complete', 'demo-unit', 'demo-task', '--evidence=probe rc 0')).code).toBe(0);
    expect((await unit(sb, 'task', 'show', 'demo-unit', 'demo-task')).stdout).toContain('STATUS: DONE');
    expect((await unit(sb, 'board', 'demo-unit')).stdout).toContain('backlog/demo-task: DONE (probe rc 0)');
  });
});
```

The rules every lane of the port settled:

- Stage, never borrow: `stage()` copies the shipped `base/` into a fresh sandbox, `seed(build)` builds a seeded snapshot once per file in `beforeAll`, and `fresh(snapshot)` hands each test its own copy (`seedSteps` for a chain of named states). A snapshot is only ever copied: no product call runs inside it. The product runs through the sandbox's own `./.contexture/ctx` (`ctx`, `unit`, `lane`, `run`), its data script (`data`), one driver operation (`driverOp`), one awk program (`awk`), or one sourced sh function (`shFunction`), each with the sandbox as its working directory; never through a relative path that can climb into the live drawer of the checkout, where a stray call writes the real record.
- Concurrency is the default: the files of a run execute in parallel and the tests of a file concurrently (`describe.concurrent`, or the `{ concurrent: true }` option), so a test writes only inside its own sandbox and never a fixed name. A describe whose tests must keep their order takes `{ concurrent: false }` (vitest 5.1.0 has no `describe.sequential`); a sandbox shared by concurrent tests from `beforeAll` is safe only while no test lists its drawer; a probe that skips by condition is `describe.skipIf(cond)(name, { concurrent: true }, fn)`, since the types lack `describe.concurrent.skipIf`.
- Assert the data, never an exit code alone: the whole answer (`answer`, `answerLine`), the exact refusal line (`refused`), the bytes of a file, and "writes nothing" through an instrument (`treeState`, `unitChecksum`). Every instrument carries its null check: a plant the same assertion reads red (a planted byte, a planted bypass, a shared sandbox that sees the leak), so a green test cannot be an instrument that sees nothing.
- No timing luck: a deadline is a `waitFor` poll, never a sleep; a lock holder is planted with `holdLock`, and `sleepShim` shortens a real 60 s lock wait to about 3 s; a test that signals a lock waiter does so only once `catShim` shows the waiter read the planted lock's pid file; dates come from the written artifact or a fixed slug, never the clock; a test that kills a writer kills its process group (`launch`, and the sweep after each file), and a test that signals a process whose stdin it holds sends the signal only once the reader runs. Concurrent writers assert zero refusals, with no retry.
- A need the host may lack (sqlite3 with FTS5, a compiler API) is probed and skipped with `describe.skipIf`, its title naming the need; the pre-release set turns the missing FTS5 into a failure.
- A defect a test proves is fixed, not left pinned: an `it.fails` pin is only a stopgap that the fix flips into an ordinary test, and the flipped expectation is read against a green run first.
- Titles carry the id they prove: the corpus rule id in brackets (`[the-engine-r7]`) for a contract rule, or the old case id (`TC22`, `E-11a`) for a ported case, so a rule's proof is one grep away.
- Run it alone first (`bun run test:<project> <file> -t "<name>"`), then the area's project and `bun run typecheck`. Through `ctx run` the console is compacted, so read `.reports/last.json` for every result and failure message.

## How to maintain

- The ship gate: `bun run test:prerelease` must end green before a release; a red run holds the ship breath. A planted failure exits non-zero and a planted hang fails at its timeout with no process left behind, both proven by the harness project's `runner` and `exec` tests.
- A new test (core or plugin) follows Writing a test above: a sandbox of its own under the run root, never a fixed name or a path outside it. A new project is declared in `vitest.config.mts` with its `test:<project>` script and a line in `support/areas.ts`; a plugin's project is declared by its `tests/` folder alone. A new tracked path that no glob of `support/areas.ts` matches fails the governance `areas` check.
- A base change (a module script, the resolver, the store, a help surface) runs the base project as well (`bun run test:base`, the shipped base staged alone with no plugin) and the integration project (`bun run test:integration`); a base-only regression that passes the plugin projects must fail there (the BG1 index tests read red on a planted index line). A change to how module code reaches the store also runs `bun run test:sqlite-smoke`.
- A law change (the core source, a module's laws or description, the composer, the loader) runs `bun run test:laws`; a version bump regenerates `tests/laws/fixtures/base-only.golden` with the compose, never by hand (the project's base-only byte comparison and its golden-version check both read it).
- A filter change is not done until its tests pass: `bun run test:filters` for a core filter, `bun run test:toolchain-filters` for a plugin filter.
- A new filter is not done until it carries at least one pair; the presence check fails otherwise.
- Update a `.expected` only with evidence: rerun the capture or reproduce the behavior. Never hand-edit an expected to match a surprise.
- Keep the pairs static and hermetic; a `.in` is a capture, never a live command.
- Portability: the suite carries no awk of its own choosing; it runs under whatever awk the system has. No container matrix runs: the governance awk census (`awk-census`) statically guards the known portability trap (a `sub` or `gsub` replacement with a backslash before another character, which the awks read differently), and an awk-sensitive change states which awks it was reasoned against.
