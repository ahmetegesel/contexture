# tests: the filter test material

Upstream only: this folder is not part of the shipped payload, and adopting workspaces carry no test material. The root README navigates here; read this page before maintaining the filters or the pairs.

## Why this exists

The stream filters are byte-sensitive: one edited branch silently changes what every session sees, and nothing errors when it does. This folder is their regression net, adapted from rtk's strongest practice: static input and expected-output pairs, byte-compared by the harness. It is hermetic (POSIX sh, awk, cmp, mktemp; no toolchain, no installs, no network). The subject under test is the shipped core: the core suites run the base runtime (`base/.contexture/ctx`) and its modules, never the live drawer (the vitest projects stage `base/` as shipped); the plugin suites exercise each plugin's own copy under `plugins/<name>/`, never the adopted copy in the live drawer, because the two drift. Every harness stages its sandbox under the workspace's gitignored `.contexture/tmp/` when that drawer is writable, and falls back to TMPDIR only when it is not; each run makes a sandbox of its own (mktemp, never a fixed name) and keeps its locks, stores, and scratch inside it, because the runner starts the suites concurrently and two gates may run at once.

## What is here

- `run.sh`: the runner: every core suite (`core:law-tests.sh`, the law compose, and `core:base-only-tests.sh`, the shipped base alone, among them; the unit and lane verbs are the vitest `unit-verbs` project's), then every plugin suite by convention (`plugins/<name>/tests/run.sh`; the docs-discipline suite twice as well, `plugin:docs-discipline` on posix and `plugin:docs-discipline:fts5` with `--driver=fts5`, skip 77 without sqlite3 FTS5), one line per suite plus a final verdict; non-zero when any suite fails; a suite exiting 77 (a need absent) reports SKIP. The suites run concurrently: each is a background job with its own output file in one gate scratch folder, its exit code written by the job itself (never read through a pipeline); when all have ended the runner prints every suite's output and outcome line in the fixed order above, then the suite times and the verdict. A suite still running after `GATE_SUITE_TIMEOUT` seconds (default 3600) is stopped with its whole process tree and fails. A suite that fails or times out prints one notice line on stderr the moment it ends, so a red surfaces without waiting for the long jobs; a green run's output is unchanged. `GATE_JOBS=<n>` caps how many run at once (default 5, the four to six lanes the host's cores allow; `0` runs all; `GATE_JOBS=1` runs the suites one after another, same order, same output).
- `fast.sh <area> [<arg>]`: the fast inner loop by area; see "Layers and the fast loop" below. It never replaces the gate.
- `filter-tests.sh`: the filter harness. It pipes each `.in` through the runner (`ctx run --filter=<filter>`), byte-compares the output with the `.expected`, and fails when a filter carries no pair (the presence check). It also drives the mechanics cases: the ANSI strip, command identity in runner mode, the notice-only false-green output, and the recovery fallback to raw.
- `ctx-tests.sh`: the engine suite: discovery, the extension-root discovery (the workspace-then-extension order, the collision warnings, extension dispatch, help --all, hooks, and filters), the module-file grammar (the summary, version, and description readers; the refused requires, duplicate, unknown, malformed-version, and broken-description shapes; the discovery validation), assembly, dispatch, the run mechanics, shadow and bad-header sandboxes, the ideas module when the live drawer carries it.
- `base-only-tests.sh [--keep] [--skip-core]`: the shipped base alone, with no plugin. It stages `base/` only (no `docs/`, no `plugins/`, no config, no rhythms directory; the base's extension root carries the lane module) and proves the payload a bare adoption carries: the no-plugin help surface (unit and the extension-root lane module listed; docs and storage-fts5 unknown rc 1; an absent extension root silent and unlisting lane), the absent-rhythms index rc 0 with an empty answer (with and without the directory), the posix descriptor (the contract 3 store-only card: version 3.0.0, the seven store data names in `store`, exact, optional store, no record function family), the record, lane, and store smoke over a synthetic data module (bootstrap through close and reopen, tasks, journal with a closer, findings, lane create/record/report/show, board, load to completion, audit, exact search, resolve of every entity, entry closure, fold, stamp, active, refresh), the store data-file grammar and the seven functions over a synthetic namespace (the exact answers, the key rule, the case twin, the refusals, the no change log on posix, no temp or lock residue), the owner scan in both module roots, the resolver's extension tier, the no-base-to-docs census with a planted reference, and the posix core suites (filter, ctx, and hook; the store contract runs once in the vitest drivers project, over a docs-shaped synthetic namespace with no plugin data; the record logic and the audit run once in the vitest unit-record project and the unit and lane verbs once in the vitest unit-verbs project, so they are not rerun here). The descriptor check and the census are null-checked by a planted difference (a missing store name, a planted functions field, a planted docs reference). It excludes the docs suite and every plugin suite by design: those are plugin gates. `--skip-core` skips B6's three nested suites and their launches and runs B1 to B5 alone (`pass=163`); the full run is `pass=166` (a pass line per nested suite included). The gate reads red on BG1 before the index fix and green after (journal of 2026-10-28).
- `module-tests.sh`: the package overlay installer and manifest suite, staged from the shipped base. It covers the package manifest grammar (`ctx _package`: the summary, version, kind, parts, and driver; the refused requires, unknown fields, duplicate fields and paths, bad kinds and part paths, and the feature/driver mismatch); the six package shapes (module-only, module plus laws/rhythms, driver, filters-only with the installed filter resolving, rhythms-only, laws-only); the retired templates part refusing as an unknown type; the manifest refusals at install (no manifest, a malformed one, an uncovered payload path, a missing declared part, an undeclared module, a feature carrying a driver path); the extension-root-only overlay and the `.contexture/extensions/.state/<package>.files` record (modes, checksums, law fragments, package version, kind, driver); every collision class (a path outside the extension root, a core path, an existing non-recorded file, another package's file, a module name against a builtin, a workspace module, or a reserved name, a driver name against core posix, a duplicate namespace); the re-install as update and the upgrade with stale remove and changed-file preserve; the uninstall with its record and the changed-file preservation; the executable-bit modes; the part hooks' order and failure; the read-only refusal that writes nothing; the rhythm index over the extension root (with the workspace rhythm listing first) and the law-fragment record; the store-data owner scan and the docs store read under the extension root; the installed driver resolving from the extension root and not listed as a module; the real five package manifests, the fts5 driver descriptor (driver fts5, version 3.0.0, contract 3), the fts5 driver at its extension-relative path, and the retired lane-isolation package; the engine's `_reserved` reader; and a real package wrapper installing the docs package's extension-root shape (the grammar inside the module, no shared templates folder, docs-authoring and docs-drift landed, work.md owned by starter-rhythms). Every case stages its package under the sandbox catalog, never the real catalog or the live drawer. It also runs the worked example package's own test (`tests/fixtures/worked-package/tests/run.sh`): the manifests, the install, the landed laws and data files, the install part hook's seed, the store verbs, the re-install's no-overwrite rule, and the uninstall leaving the store data.
- `law-tests.sh [--keep]`: the law compose suite. It stages the shipped base and proves the core law source and the 15-block skeleton, the composer (append under an existing keyword, a new keyword custom section after `@update`, the `@module` preambles after `@layout`, `@append`-only fragments, the deterministic header and sources hash, the --check verify), the synthetic fixture (workspace and extension modules, a summary-only module, a no-laws module, standalone law parts, the package-version hash), the base-only golden (unit plus lane, no docs; byte-equal, with the golden's core version checked so a version bump forces its regeneration), and the planted failures (a duplicate slug, an edited core, a missing or unreadable fragment, an unreadable overlay or install record, a requires line, a nondeterministic input). It also proves the discovery filters (a reserved name and a workspace-shadowed extension), the loader's first instruction and the two wrong-loader plants, the boot behavior (an absent generated layer composes, a stale layer recomposes, an absent composer or core source stops rc2 naming the payload path), the docs module's eight laws and its layout, boot, and close clauses, the workspace overlay's absence of the docs and lane clauses, the retired docs plugin overlay, the lane clauses and boundary-warning, the docs composition (and its duplicate-slug refusal), and the installer's recompose (a law-bearing package installs and uninstalls with the layer updated and restored, a duplicate slug fails the install rc2, and an older core without the composer skips the recompose). The sandbox lives under the workspace scratch drawer.
- `hook-tests.sh`: the hook engine suite over the committed fixture modules in `fixtures/hooks/`; every shipped hook point fires.
- `governance-tests.sh`: the main-surface forbid grep, the payload path tables re-derived against `git ls-files`, the presence checks (verbs, hook points, filters, gate lines), and G5: no `sub` or `gsub` replacement in the awk and sh files of base, the plugins' module copies, and the suites carries a backslash before a character other than a backslash or `&` (`lib/awkrepl.awk`, null-checked by a planted file).
- `lib/awkrepl.awk`: the replacement census of G5: every `sub` or `gsub` replacement literal whose value carries a backslash before another character, one line per hit (Debian's busybox awk drops that backslash).
- `<filter>-<case>.in` / `<filter>-<case>.expected`: a real captured stream and the exact bytes the filter must emit.
- `compact-recovery.awk`: a synthetic probe filter for the recovery mechanics case.
- `fixtures/`: committed fixtures for the non-filter suites (hook modules, the ideas dump, and `fixtures/compliance/`: the legacy markdown units the posix-alone cases plant (`units/`), the legacy fixture's golden answers and item notes (`golden/legacy-u/`, `legacy.notes`), the verb-built unit's golden answers (`golden/verb-u/`, written with `COMPLIANCE_WRITE_GOLDENS=1` and read by hand), the exact search answers of TC39 and TC69, TC61's expected posix journal, the canned fts5 store answer the ranked mapping reads (`ranked/`), and the expected texts of the views (`views/`); all of them the vitest unit-record project's).

Plugin pairs live under the plugin (`plugins/toolchain-filters/tests/`) and run through a staged sandbox. The docs-discipline suite (`plugins/docs-discipline/tests/run.sh [--driver=posix|fts5]`) stages from `base/` and its own copies and carries, on each driver, the staging check, the module's install and uninstall part hooks (the seed once, never an overwrite, the data left on uninstall, the missing-context refusals), the audit, the unit-form nudge, the write verbs, the engine checks, the delta-source cases (the check's store and git modes, `ctx docs changes`, the gate's two halves), the single-door census, the gate matrix, and the grammar agreement check; its fts5 run adds the store seed (every staged doc through `ctx docs write`), the stored bytes (every doc read back unchanged through `ctx docs write --replace --dry-run`), and the capture parity against the files driver at one sandbox path, and runs its corpus checks in a second sandbox beside that chain (its module README carries the detail). The storage-fts5 tests are the vitest project `storage-fts5` (`plugins/storage-fts5/tests`, see the vitest harness below).

## The vitest harness

TypeScript tests that drive the shipped product (sh and the system awk, staged from `base/` and `plugins/` as shipped) as child processes, beside the shell suites: those run unchanged, and `run.sh` never discovers these files (its jobs are the named core suites and `plugins/<name>/tests/run.sh`).

- `package.json`: the test tooling, installed with bun from this folder (`bun install`; `bun.lock` is tracked, `node_modules/` is not); its only dev dependencies are vitest, typescript, and @types/node, pinned exactly. Scripts: `bun run test` (every project), `bun run test:<project>` (one area, for example `test:harness`), `bun run test:drivers:posix` (the drivers area loop on posix alone: `VITEST_DRIVERS=posix` drops the fts5 parameters, and every fts5-only file skips), `bun run test:unit-record` (the record logic), `bun run test:unit-verbs` (the unit and lane verbs), `bun run test:unit` (every `unit-*` project, the unit module area loop), `bun run typecheck` (`tsc --noEmit`). One file: `bun run test harness/wire.test.ts`; one test by name: `bun run test:harness -t "<name pattern>"`.
- `vitest.config.mts`: one vitest project per area; `harness` holds the harness smoke tests, `drivers` the store driver tests (`bun run test:drivers`), `unit-record` the unit module's record logic (`bun run test:unit-record`), `unit-verbs` the `ctx unit` and `ctx lane` verbs (`bun run test:unit-verbs`), and `storage-fts5` the plugin's own project rooted at `plugins/storage-fts5` (`bun run test:storage-fts5`): a plugin project lives in `plugins/<name>/tests` and imports these helpers as `@support/<helper>` (the project's `resolve.alias`, mirrored by the tsconfig `paths`). The driver and unit projects keep 16 tests in flight per file (`maxConcurrency`), since each test is a few independent processes. In a run of every project, `unit-record` and `unit-verbs` start after the others (`sequence.groupOrder: 1`): the record project's process load beside the drivers project pushed the shimmed lock-wait bounds (15 s) to 24 to 26 s. A global setup makes one fresh sandbox root per project run under the workspace's `.contexture/tmp/` and removes it when the run ends; every sandbox is a fresh folder inside it.
- `tsconfig.json`: the type check over every TypeScript file here.
- `support/`: the shared helpers, one concern per file: `sandbox.ts` (a fresh folder under the run root), `stage.ts` (`base/` copied as shipped, modes kept; fts5 adds the storage-fts5 plugin's driver copy and `storage.driver: fts5`, and its cases skip when sqlite3 lacks FTS5), `snapshot.ts` (`seed` builds a seeded sandbox once per file, `fresh` hands each test its own copy, and `seedSteps` is a chain of named snapshots, each step forking a copy of its parent, built lazily by the first worker that needs it and published once per project run under the run root by a lock and a rename, so a single test pays only its own prefix and a failed build fails every waiter), `exec.ts` (every child process with `LC_ALL=C` and an explicit env: PATH, HOME, USER, TZ, and the sandbox's own TMPDIR, nothing else inherited), `ctx.ts`, `awk.ts` (one awk program alone), `sh.ts` (one sourced sh function alone), `driver.ts` (one driver operation), `data.ts` (one unit data script call), `wire.ts` (the payload escape and its inverse, the payload builder with the closer records, base64, and the answer and refusal checks: an answer is one compact JSON line, `answerLine` returns it for a byte compare, `refusedLike` checks a refusal whose message the contract leaves free), `record.ts` (the record wire of the unit tests: `mk`, `rec`, `ok`, the read picture `reads`, the entry and receipt JSON, and the posix fixture plants `plantUnit`, `readArtifact`, `appendArtifact`), `engine.ts` (`engineCall` runs the record engine, or the exact search, alone over a manifest of the posix files built with the data script's parts plan and lands a staged write with `applyStage`, returning the data script's answer and refusal shape; `renderView` pipes an answer through `json.awk` into `render.awk`), `locks.ts` (the lock test plants: `holdLock` puts a unit or namespace lock folder in the sandbox with a live holder pid, a dead one, or no pid file, and `sleepShim` gives the env a PATH whose `sleep` is the `true` binary, so a 60 s lock wait of 600 polls runs in about 3 s with no product knob; the real wait already outlasts any test deadline, so no long-wait shim exists). `data` and `driverOp` take an optional env, the way a test passes the shim. For the store tests: `data-file.ts` (`DOCS_SHAPED`, a module data file in either module root), `store.ts` (the seven store calls, search and batch on one driver, the docs-shaped snapshots seeded through put, a storage core script plant), `search-fixture.ts` (the search schema fixtures and their exact answers), `plants.ts` (a chmod plant restored by the test's own `onTestFinished`, a PATH command plant), `sqlite.ts` (a direct sqlite3 call and a fake sqlite3 reporting a chosen version), and `fuzz.ts` (the differential store fuzzer: the Lehmer sequence, the key-value and unit-shaped profiles, the replay, the byte compare, the blind-spot check). `exec.ts` also has `launch`, the child handle for the interrupt cases (stdin held open, the signal sent to the process group). For the verb tests: `unit.ts` (`run`, `unit`, and `lane` call the staged ctx with an explicit stdin, an empty pipe by default, a document, or `null` held open; `execBytes` passes any byte string through argv by a printf decode, since a node argv cannot carry bytes that are not UTF-8; `plantArtifact` plants legacy text as a posix file; `unitChecksum` is a unit's read picture, every read function's answer plus its posix files, which a refused write must leave unchanged; `activeBlocks` splits the active listing into per-unit blocks; `plantRhythms` writes a workspace and an extension rhythm; `waitFor` polls a predicate to a deadline). A snapshot is only ever copied: every product call runs in a fresh copy, since a call inside the snapshot writes scratch that a concurrent copy would meet.
- `drivers/`: the store driver tests, the logic of the storage core once and each driver against the store contract. `store-data`, `store-search`, and `store-b64` call the storage core's readers directly; `store-contract` holds both drivers to one parameterized set (the reads, writes, key rule, wire refusals, module data files, search, batch, the encoder fault, the cards, the health); `store-posix` the posix store on disk; `store-faults` the write faults (read-only folders, a failing rename and a TERM between the batch renames, a read-only store on both drivers); `store-locks` the namespace lock's hold, release, interrupts (a TERM while holding releases it, a TERM while waiting leaves the live holder's lock in place), and concurrency; `store-fuzz` the differential fuzzer with its blind and planted null checks. `lock-wait.test.ts` proves the lock waits through the shipped scripts: the unit lock through the data script, the namespace lock through `store.put` on each driver; a live holder refuses `ERR_STORAGE_LOCKED` under the shim far below the real wait and nothing lands, a dead holder's lock is removed at once, and a pid-less lock after its grace.
- `unit-record/`: the unit module's record logic, once, on posix. The compliance families (`fresh-store`, `unit-lifecycle`, `tasks`, `entries`, `findings`, `lanes`, `search`, `refusals`, `listings`, `canonical-model`, `audit`, `concurrency`) call the data script over a staged store, every dependent case on a fresh copy of its named state in one snapshot chain (`chain.ts`: empty, U1, T0 to T37, SS31, SS32, the payload date 2026-09-27) and the legacy shapes planted as posix files; `module-data` and `ranked-search` carry the module's own cases (the ranked mapping over a canned fts5 store answer); `engine-differential` holds the engine equal to the data script for all 36 dispatched functions on the same snapshot (answers and landed files, with a planted-difference null check), which also guards the helper's parts plan; `engine-model`, `search-engine`, `render-views`, `payload`, and `b64` test the module's awk and sh programs alone. `COMPLIANCE_WRITE_GOLDENS=1` writes the goldens, the canned answer, and the view texts instead of comparing them; a changed golden is a contract change, read by hand. TC22's five concurrent writers assert zero refusals with no retry.
- `unit-verbs/`: the `ctx unit` and `ctx lane` verbs, once, on posix, one file per verb family or rule, each over its own snapshot seeded through the verbs (dates come from the written artifact or a fixed slug, never the clock). The families: `verb-surface` (the declared 21 verbs, the retired names, the help forms), `index`, `active` (the derived move, its no-work forms read in the unit's own block), `unit-lifecycle`, `load`, `board-audit`, `refresh`, `standalone`, `task`, `record`, `finding`, `search`, `resolve`, `units-refs-to`, `diagnose`, `lane` (with the rule that `lane show` never reads an open stdin), `fold`, `fold-protocol` (one test per protocol step over a snapshot chain in `fold-fixture.ts`), and `fold-defects` (every class the check names). The rules: `verb-library` runs the input matrices of `lib/verb.sh` one function at a time (`inputs.ts` holds the values), while `input-refs` and `input-bytes` keep one wiring test per write path, so a verb that stops calling a check still fails; `quote-rule`, `messages`, `canonical-layout`, and `static` (no sessions path in a message; every verb that reaches the record sources the verb library, `index` and `refresh` the two that do not). The faults: `storage-faults` (a read-only store, a TERM on a waiting method, a SIGKILLed holder, a live holder under the sleep shim, a killed waiter's scratch root swept, the kill taking the writer's process group) and `concurrency` (concurrent writers serialize with zero refusals, no residue, no torn block, and the residue patterns one by one against the retired one-ls probe).
- `harness/`: one smoke test per invocation kind, each with the null check its instrument needs (a shared sandbox sees the planted leak; the inherited env carries the planted variables; the fts5 probe reads absent without sqlite3).

## Layers and the fast loop

Three layers, from the smallest proof to the full one:

- The fast inner loop is the unit-like set: `filter-tests.sh`, `ctx-tests.sh`, `governance-tests.sh`, and `plugins/ast-doc-graph/tests/test-ddl.sh`, beside the vitest area loops (`bun run test:unit-record`, `bun run test:drivers:posix`). It is the smallest set that proves the kind of change at hand, never a replacement for the gate.
- The pre-commit layer is the unit-like set plus the owning integration suite: a record or verb change adds `bun run test:unit` (the unit-record and unit-verbs projects); an fts5 change adds the storage-fts5 suite; a docs change adds docs posix and docs fts5 when the store mode is touched; a plugin change adds that plugin's suite; a base module change adds base-only's B1 to B5 checks; a package overlay or install change adds module-tests.
- The full pre-land gate is `tests/run.sh` unchanged: all 10 run jobs plus the 1 skip and the 2 info, every suite, every assertion, the fixed print order, and the fixed verdict. It stays mandatory before any commit, tag, or push.

The broad pre-push set is the unit-like set plus `bun run test:unit`, docs posix, storage-fts5, and base-only's unique checks (`tests/base-only-tests.sh --skip-core`); docs fts5 and the full plugin matrix stay for pre-land. The fast loop shortens the inner loop, never the gate.

`tests/fast.sh <area>` runs the fast inner loop by area (POSIX sh and awk, no dependency, no fixed scratch, 77 a skip, 1 on any failure):

- `tests/fast.sh unit`: the four unit-like suites (the store driver, record, and verb tests run in vitest: `bun run test:drivers` and `bun run test:unit`).
- `tests/fast.sh engine`: filter, ctx, governance.
- `tests/fast.sh law`: the law compose suite (`law-tests.sh`).
- `tests/fast.sh module`: the package overlay installer suite (`tests/module-tests.sh`).
- `tests/fast.sh docs` and `tests/fast.sh docs-fts5`: the docs-discipline suite on the files driver and on fts5.
- `tests/fast.sh plugin <name>`: `plugins/<name>/tests/run.sh`.
- `tests/fast.sh base`: base-only's B1 to B5 checks (`tests/base-only-tests.sh --skip-core`).

`plugin:toolchain-filters` is INFO (its fixture pairs ride filter-tests), and so is `plugin:storage-fts5` (its tests are the vitest project); `plugin:starter-rhythms` is SKIP (no tests directory), and the retired lane-isolation package is no longer a catalog entry. storage-fts5 is integration: it proves the plugin's own copy of the fts5 driver. docs posix is integration; docs fts5 and base-only are end-to-end-like.

## How to maintain

- The ship gate: `tests/run.sh` must end green before any commit, tag, or push; a red run holds the ship breath. The runner reports one line per suite plus a final verdict, a planted failure must exit non-zero, and a planted hang must end as a failure at the suite timeout with no process left behind.
- A new suite (core or plugin) stages in a sandbox of its own (mktemp under the scratch drawer, removed on exit) and never writes a fixed name or a path outside it: the runner starts every suite at once, so a shared path turns into a race.
- A base change (a module script, the resolver, the store, a help surface) runs the base-only gate as well: `tests/base-only-tests.sh`, and the ship gate runs it as `core:base-only-tests.sh`; a base-only regression that passes the plugin suites must fail there.
- A law change (the core source, a module's laws or description, the composer, the loader) runs `tests/law-tests.sh`; a version bump regenerates `tests/fixtures/law-compose/base-only.golden` with the compose, never by hand (the suite's base-only byte comparison and its golden-version check both read it).
- A filter change is not done until the harness passes: `tests/filter-tests.sh`.
- A new filter is not done until it carries at least one pair; the presence check fails otherwise.
- Update a `.expected` only with evidence: rerun the capture or reproduce the behavior. Never hand-edit an expected to match a surprise.
- Keep the pairs static and hermetic; a `.in` is a capture, never a live command.
- Portability: the suite carries no awk of its own choosing; it runs under whatever awk the system has. Before a change to an awk encoder, decoder, or regex string ships, run `tests/run.sh` under each supported awk (BWK awk on macOS, and in disposable Linux containers Debian with its default mawk, Debian with gawk, Alpine with busybox awk, with sqlite3 and git inside the container for the fts5 run and the governance probe); an assertion that only one awk turns red is the reason the matrix exists.
